### 5-1. 引当: 安全在庫を使った先行引当(納期の影響を考慮)
**主語: 引当予約。対象: 安全在庫を使うかの判断。**
1. 現状(対応済み): `v_stock_status.available` は、安全在庫を必ず残す(出庫可能数 = 在庫 − 引当済 − 安全在庫)。`addview.sql` に、安全在庫を引かない数 `available_with_safety`(在庫 − 引当済。0 未満にならない)を足した。
1. 未対応(要設計): 先行している製品を引き当てるときは、**安全在庫を使ってもよい**。条件は「在庫が 0 にならない範囲」かつ「納期への影響が無い」こと。
   - 納期の影響: 安全在庫を使って在庫が減っても、補充(発注の入荷・生産計画の完了)が、**その品目の次の需要の納期より前に間に合う**なら許す。間に合わないなら許さない(または警告)。
   - 必要なもの: 品目ごとの**補充予定の日付別の集計**(ビュー例 `v_item_supply_forecast`: 品目、予定日、数量。発注明細の納期 `period`、生産計画の完了期限 `deadline` から)と、品目ごとの**需要の日付別の集計**(受注明細の納期・引当予約の予定日)。両者から、各日付の在庫の見込みが 0 を割らないかを判定する。
   - 引当の種類を、画面で選べるようにする(通常 = 安全在庫を残す / 先行引当 = 安全在庫を使う。先行引当は検査に通ったときだけ保存できる)。`invreq` に種類の列(例 `use_safety` BOOL)を足す案。
   - 画面: 上限(`maxFrom`)を、種類に応じて `available` / `available_with_safety` から取る。`entity_screens` に「別の項目の値で上限の元を切り替える」指定が要る(現状は固定)。または種類ごとに別の項目(`maxFrom` を 2つ)にする。
1. 判断が必要: 納期の判定を DB のビュー(推奨。画面と GraphQL で同じ結果)で行うか、アプリで行うか。需要の側(受注の納期・生産計画の資材所要)の範囲。

### 5-2. 受注キャンセル・発注キャンセル
**主語: 受注・発注。対象: キャンセルと、生産中の扱い。**
1. 現状: **未対応**。キャンセルを表す列が無い(`trans_order` / `trans_purchase` には `remove`(削除)があるだけ。削除は取り消しの記録にならず、生産・引当の後始末もしない)。
1. 仕様(指示): 
   - 生産を開始していない: キャンセルのフラグだけで足りる(引当予約は解除する)。
   - 生産中: 次の3つから選ぶ。(a) **完了まで進める**、(b) **現在の状態のまま**(以降の工程は止める。作りかけは仕掛品として残す)、(c) **現在の工程が完了するまで**(その工程を終えたら止める)。
1. 必要な DB の変更(提案):
   - `trans_order` / `trans_purchase`: `cancel_at`(キャンセル日時。NULL なら有効)、`cancel_mode`(SMALLINT: 0 = 生産前、1 = 完了まで進める、2 = 現在の状態のまま、3 = 現在の工程完了まで)、`cancel_reason`(備考)。
   - 「生産を開始したか」を返すビュー(`v_order_production_state`: 受注 → 受注明細 → 資材計画 → 生産計画 → 生産計画詳細 → 作業実績の有無、進行中の工程)。
   - 後始末: 引当予約の解除(`trans_inventory_request.remove`)、止める生産計画詳細の状態(列の追加が要る。例 `stopped_at`)。止める処理は、アプリではなく DB の関数(トランザクション)にするのが安全。
   - 発注キャンセル: 受入済みの数量は残し、未受入分を止める。キャンセルに伴う返却は 5-3。
1. 画面: 台帳の行のボタン(`rowActions`)が、いまは「別の実体の新規登録を開く」だけ。キャンセルは**確認と選択のダイアログを開いて、処理を実行する**操作なので、`entity_screens` の行のボタンに「コマンドを実行する」種類を足す(`RowAction` に、開く先の代わりに `Command` を指定)。生産中のときだけ3つの選択を出す。
1. 判断が必要: 3つの選択の意味(特に (b) の仕掛品の扱い、(c) の「現在の工程」の定義 = 開始済みで未完了の工程)と、キャンセルの取り消し(復活)を認めるか。

### 5-3. 顧客の無償支給(材料)
**主語: 材料の支給。対象: 顧客から無償で材料を受ける発注と、キャンセル時の返却。**
1. 対応済み:
   - 発注明細に `material_supply`(材料支給)と `paid_supply`(有償支給)の項目がある。**無償支給 = 材料支給あり かつ 有償でない**。
   - 利害関係者(`mstr_stakeholder`)は、`is_customer`・`is_supplier`・`is_logistics` が**独立したフラグ**で、1件が顧客と外部供給者の両方になれる。つまり**顧客を別の利害関係者として追加する必要は無い**。顧客の行の `is_supplier` をオンにすれば、発注先に選べる。
1. 未対応:
   - 発注先の選択肢(`supplier`)は `is_supplier` で絞っている。顧客の行を発注先にするには `is_supplier` をオンにする運用になる。**顧客のうち、無償支給の発注先にだけなれる**ようにする区別が無い(`is_supplier` を付けると、通常の外部供給者の一覧にも出る)。案: 無償支給のときは顧客(`is_customer`)も発注先に選べるようにする(選択肢の絞り込み `optionFilters` を材料支給の項目で切り替える)。
   - **返却**: 受注キャンセル(5-2)で、無償支給の材料を顧客へ返す処理が無い。必要なもの: 返却の実績(`trans_convey` の払出で足りるか、返却先 = 顧客の指定が要るか)、返却済みの数量、返却伝票。
   - **在庫の所有**: 無償支給の材料は顧客の資産で、自社の在庫(安全在庫・出庫可能数)に**数えない**、またはその受注にだけ使える。現状の `v_stock_status` は区別しない。`v_visiter_item` と同様に、受入実績 → 発注明細 → `material_supply` で判定できるので、ビューに「所有者区分」(自社 / 顧客支給)を足す案。
   - 単価: 発注明細の `unit_price` は必須。無償支給は 0 を認める(`ge: 0`)。
1. 判断が必要: 顧客の支給を、発注(購買)の仕組みで扱い続けるか、専用の「支給」の実体にするか(返却・所有の扱いは専用の方が自然)。
