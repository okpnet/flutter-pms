## A. `FieldDefinition` の役割の説明(未実施の2項目の前提)

**`FieldDefinition` とは**: `entity_screens` パッケージが持つ、**実体(台帳の1種類)の「1つの項目」の宣言**。人が書くのは画面ごとの定義だけで、台帳の列・編集画面の入力部品・入力の検証・保存の形は、すべてこの宣言から作る(`EntityDefinition.fields` に並べる)。表示名は持たず(多言語の辞書が返す)、キーと振る舞いだけを持つ。

| 持てるもの | 画面に起きること |
|---|---|
| `kind`(文字・数値・日付・選択・参照・真偽…) | 入力部品と、台帳の列の種類が決まる |
| `required` / `readOnly` | 必須の検査 / 表示だけ(集計・計算された値) |
| `ge` / `gt` | **数値の下限**(以上 / より大きい) |
| `reference` / `picker` | 他の実体の1件を選ぶ(リスト / 台帳から選んで戻る) |
| `disables` / `needUnless` / `lockedBy` | 別の項目のオン・オフで、他の項目を無効にする / 必須にする / 外せなくする |

**持てないもの = 今回の未実施の原因。** 下の「項目の関係」は、**1つの項目だけでは決まらず、同じ画面のほかの項目や選んだ行の値に依存する**ため、いまの `FieldDefinition` では書けない。

1. **`after`(日付の前後関係)** — 主語: 出荷予定台帳の「到着予定日」/ 出荷指示の「個別の到着日」。対象: 同じ画面の「予定日」。意味: 「到着日は予定日以降でなければならない」。`ge` は**固定の数値**との比較しかできず、**別の項目の値**とは比べられない。
1. **`le`(上限)** — 主語: 出荷指示の「進捗」、引当予約の「引当数量」。対象: 固定値(進捗は 100)または**ほかの項目・選んだ行の値**(引当数量は「選んだ在庫の出庫可能数」と「購買注文明細の未引当数量」の小さいほう)。`ge`/`gt` の対になる上限が無い。固定値の `le` は簡単に足せるが、「値が選択で変わる上限」(`setsLe`・`limit`)は別の仕組みが要る。
1. **`xor`(どちらか一方)** — 主語: 引当予約の「購買注文明細」と「生産計画」の2つの参照。意味: 片方を選ぶともう片方は空にして無効にする(必ず1つは選ぶ)。`disables` は真偽値の項目にしか付けられず、参照どうしの排他は書けない。
1. **動的な参照(`@srcPur`・`@srcOps`・`@stock`)** — 主語: 引当予約の「引当元の在庫」。対象: 画面案の中で「いま選ばれている引当先(購買注文明細 or 生産計画)」の品目で絞った在庫の一覧。`reference` は参照先の**実体キー1つ**を固定で持つので、選択肢を**別の項目の値で変える**ことができない。

## B. 提案: `entity_screens` の拡張内容と範囲

**主語: `entity_screens`(UI基盤パッケージ)。対象: 未実施の3項目(引当予約・日付/上限の制約・行のボタン・在庫状況)。**
段階に分け、**低コストで効果が大きい順**に行う。各段階は `FieldDefinition`/`EntityDefinition` に値を足すだけで、既存の定義は壊れない(新しい引数は省略可能)。

| 段階 | 主語(足すもの) | 対象 | 内容 | 影響 |
|---|---|---|---|---|
| 1 | `FieldDefinition.le`・`lt` | 数値の項目 | 固定の上限(進捗 ≤ 100)。`ge`/`gt` と対称 | 小(検証と台帳の入力) |
| 1 | `FieldDefinition.notBefore`(= `after`) | 日付の項目 | 別の日付の項目のキーを持ち、「それ以降」を検証 | 小(編集画面の検証) |
| 2 | `FieldDefinition.exclusiveWith`(= `xor`) | 参照の項目 | 排他の相手のキー。片方を選ぶと他方を空にして無効にし、どちらかは必須 | 中(編集画面の状態) |
| 2 | `FieldDefinition.referenceFilter`(= 動的な参照) | 参照の項目 | 選択肢を絞る条件(別の項目のキー → 参照先の項目)を宣言する | 中(`IEntityRepository` に条件つきの取得が要る) |
| 2 | `FieldDefinition.maxFrom`(= `setsLe`/`limit`) | 数値の項目 | 上限を、選んだ参照先の行の項目から取る(出庫可能数など) | 中(参照先の行の値を読む) |
| 3 | `EntityDefinition.rowActions`(= `action`) | 台帳の行 | 行ごとのボタン(ラベル・押したときの `Destination`/コマンド)。台帳が `Command` を実行するだけで、中身は機能・アプリが持つ | 中(台帳の列にボタンを足す。権限・ログ) |
| 3 | `EntityDefinition.viewOnly`(既存) | 在庫状況 | **すでにある**(ビューの台帳。「新規」を出さず、保存・削除を出さない)。計算列は `readOnly` で足りる。追加不要 | なし |

**判断の目安**
- 段階1だけでも、出荷管理(進捗の上限・到着日)と、現在の全生成物が正しく検証できる。**先に着手を推奨**。
- 在庫状況(`#/stock`)は**段階3の `viewOnly` で足りる**(台帳・読み取り専用・計算列)。行の選択でバーコード画面へ向ける遷移だけが、行のボタンと同じ仕組み(`rowActions`)になる。
- 引当予約は段階2が揃うまで生成しない(いまの `SKIP stockrez` のまま)。

## D. 提案: 取得元の GraphQL 化(0006 の 1)と件数の元(0006 の 3)

### 1. 取得元の GraphQL 化とは
**主語: 画面の取得元 `IEntityRepository`。対象: 機能ごとの実体(organization 13・item 13・resource 15・sales 2・purchasing 7 …)。**
現状は、実体の台帳・編集画面が読み書きする先が**メモリ上のサンプル**で、実サーバーの値が出ない。`access_control` だけが GraphQL 版(`accessControlRepositories`)。

**必要な値**: 各実体について、(a) 一覧の取得(ページング)、(b) 1件の取得、(c) 作成・更新・削除のミューテーション、(d) 参照(選択)の id ↔ 表示名の変換、(e) 呼称(多言語の辞書)の入れ子の読み書き。
**設計(提案)**:
- **主語: 機能ごとの窓口クラス**(`access_control_model` の `AccessControlClient` が前例)を、各 `model_providers/<機能>_model/lib/` に置く。生成された型は窓口の中に閉じ、機能へは平らな型だけを返す(「生成された型を機能の外に出さない」の規則)。
- **主語: 機能の `xxxRepositories(GraphQLClient)`**。窓口の平らな型と `EntityRecord` を変換する(Adapter)。実体ごとに1クラスだが、共通部分(必須の検査・ページング)は基底クラスで共有する。
- **主語: アプリの `graphqlOverrides`**。機能ごとの `xxxRepositories` を足す(`GRAPHQL_URL` の指定時だけ)。
- 実体の多い機能は、**定義から窓口を生成できる**か検討する(`tools/entity_gen` で `gql/*.yaml` と窓口の雛形を作る案。手書きでは約180実体になるため。要判断)。
- **進め方**: 実体の少ない `system`(1)→`sales`(2)→`shared_master`(2)で窓口の型を固め、残りを機能ごとに進める。各機能の完了条件は「実サーバーで一覧・作成・更新・削除が通る」こと。
- 同時に、権限のメニュー(`menuAccessProvider`)とダッシュボードの権限(`usecase_path`)を、実サーバーで確認する。

### 2. 件数の元とは
**主語: ダッシュボードの件数タイル(`ICountSource`)。対象: 当日出荷・進捗遅延・受注の件数と、区分・利害関係者のフィルタ。**
現状 `mockCountSources`(`dashboard_overrides.dart`)は**固定の数字**(12・4・40 など)を返す暫定。

**必要な値**: `RepositoryCountSource`(`dashboard_container`)が受け取る次の2つ。
- `IQueryState<int>`: 件数を返す取得元の指定。**GraphQL の `totalCount`** を返す。モデルには `ShippingTodayPage`(`sales_model`)・`WorkPlanDelayPage`(`production_plan_model`)が既にある。受注は対応する Page を足す。
- `IPageDataMediator`: 取得の窓口(`page_mediator_extension`)。メンテナンス・セッションの確認とログを通る。
- フィルタ(区分・利害関係者)は `CountFilterOption.predicate`(`Expression`)で絞り込みに変換する。当日出荷は `estimatedShippingDate` の範囲、区分・利害関係者は PostGraphile の関連の列。

**設計(提案)**:
- **主語: `GraphqlCountState`(新規)**。`IQueryState<int>` の実装。Page の `$filter` に述語を渡して `totalCount` だけを読む。
- **主語: アプリの `countSourcesProvider`**。`GRAPHQL_URL` の指定時は `RepositoryCountSource`、未指定時は現状のモックのまま。
- **確認**: 実サーバーでタイルの件数と、台帳の件数が一致すること。権限が無い(`permission denied`)ときは、タイルをエラー表示にする(0 にしない)。

## E. メンテナンス情報サーバー `/info` の接続確認

**主語: メンテナンス情報サーバー(nginx、`192.168.1.101:18480`)。対象: `GET /health`・`/info`(PUT・GET・DELETE)。**

| 確認 | 結果 |
|---|---|
| `GET /health` | 503(メンテナンス中のフラグがある) |
| `GET /info` | 404(情報なし) |
| `PUT /info`(認証なし) | 405 |
| `PUT /info`(Basic 認証あり) | **405** |
| `PUT /info/maintenance.json`・`/info/`・`/info/status.json`(旧パス) | 201・201・204(**書き込めた**) |
| `GET /info/maintenance.json` | 200 |

**判定**: **稼働中のサーバーは、新しい設定(`/info` だけ)ではなく、旧い設定(`/info/` の下にファイルを置く)のまま**。リポジトリの `default.conf.template` と `README.md` は新しい形で、コンテナが作り直されていない。
- 確認で旧パスに作った3つ(`/info/maintenance.json`・`/info/`・`/info/status.json`)は、すべて `DELETE`(204)で消して元に戻した。メンテナンスのフラグ(`/health` 503)は触っていない。
- **対応(利用者の作業)**: サーバーのあるホストで `cd tools/docker/maintenance; docker compose up -d --force-recreate`(設定の更新を反映)。そのあと `PUT /info` → `GET /info` → `DELETE /info` を再確認する。再確認は私に依頼できる。
- 旧い設定のままだと、アプリは `GET /info` を読めず(404)、メンテナンス中の表示は既定の文面になる(判定は変わらない)。

## B'. 拡張の段階1(`entity_screens`)の実施
**主語: `entity_screens`(`FieldDefinition`・`EntityFieldError`・`InMemoryEntityRepository`・編集画面・多言語)。対象: 数値の上限と日付の前後関係。**

1. `FieldDefinition` に省略可能な引数を3つ足した(既存の定義は変わらない)。
   - `le`(以下)・`lt`(より小さい): 数値の固定の上限。`ge`/`gt` の対。
   - `notBefore`: 同じ実体の別の日付の項目(キー)以降でなければならない。どちらかが空のときは検証しない。同じ日は可。
1. `EntityFieldError` に `aboveMaximum`・`notBelowMaximum`・`beforeOtherDate` を足し、サンプルの取得元(`InMemoryEntityRepository`)が検証する。編集画面は、文言を表示する(`$max 以下で入力してください`・`$other 以降の日付を入力してください` など。ja・en。`dart run slang` で生成)。`$other` は、相手の項目の呼称(`EntityLabels.field`)。
1. 生成ツール(`tools/entity_gen/gen.js`)が、画面案の `le` と `after`(日付の前後)を読んで `le:`・`lt:`・`notBefore:` として出力する。出荷予定台帳の「到着予定日」と出荷指示の「個別の到着日」は `notBefore: 'date'`、出荷指示の「進捗」は `ge: 0, le: 100` になった。
1. **範囲外(今回は行わない)**: GraphQL 版の取得元(`accessControlRepositories`)は、必須の検査だけを自前で行う作りのため、上限・前後の検査は含まない(サンプルの取得元と、DB 側の制約が担う)。GraphQL 化(D)の際に、共通の検証を `entity_screens` から使えるようにするか判断する。
1. テスト: `entity_screens` に `limits_test.dart`(上限・同日・前後・空・`toJson`)を追加。`entity_screens` 39件・`sales` 8件・`access_control` 10件・`pms_app` 37件が通り、`entity_screens`・`sales` の解析は問題なし。
