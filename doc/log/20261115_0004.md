# 更新者(ログイン中の担当者)・事業所の住所・DB に適用するものの一覧

## 1. 更新者
- **状態管理の確認**: ログイン中のユーザーの ID を保持しているのは、`packages/infra/pbapi` の `SessionService.current`(`AuthSession.appUserId` = アプリの DB の担当者の ID。`sessionServiceProvider`)。`feature_shared` の `userSummaryProvider` は表示用(名前・役割)で、ID を持たない。`mrpStaffIdProvider`(生産計画)は既定が空で、アプリが差し込んでいない(MRP の関数は JWT の `staff_id` を使う)。
- **生成器**(`tools/gql_yaml2graphql`): 定義に `withUpdater: true` を付けると、Edit・Remove の引数・Patch に更新者(`update_user_id`・`update_user_history_id`。任意)が入る(従来は監査列を含めなかった)。結果には含めない。`dart test` 23 件通過。営業・購買・生産計画の Edit(受注・受注明細・出荷オーダー・出荷オーダー明細・発注・発注明細・資材計画・生産計画)に付けた。
- **部品**(`pms_graphql`): `AuditUser`・`AuditUserSource`・`AuditUserResolver`(担当者の ID を関数で貰い、最新の履歴の ID を引いて使い回す。担当者が変わったときだけ引き直す)。`test/audit_user_test.dart` 4 件。
- **取得元**: `salesRepositories`・`purchasingRepositories`・`productionPlanRepositories` が `auditUser` を受け取り、登録・更新・論理削除で更新者を送る(渡されていない・ログインしていないときは送らない)。アプリ(`pms_app`)は、`auditUserProvider`(`pbapi` のセッションの `appUserId` から)を組み立てて渡す。
- **テスト**: `data_test_harness` に `TestToken.staffId`・`TestServer.staffId`・`TestServer.auditUser`(JWT の `staff_id` から)を足した。実サーバー(PostGraphile)で、更新者を渡さない取得元で登録した行は更新者が空、渡す取得元の更新・登録・論理削除で、JWT の担当者と最新の履歴の ID が記録されることを確認(営業・購買・生産計画)。
- **整合テストの修正**: `tools/gql_yaml2graphql` の `page_views_consistency_test` は、先の作業で足した 54 のノード(計画変更・精算・返品・支給・操作の関数・Create など)が `doc/page.md` から参照されておらず、失敗していた。末尾に追加して通した。

## 2. 事業所の住所
- 画面の項目を、DB の住所(`info_address`)の列に合わせた: 国・郵便番号・住所1・住所2・建物・電話番号・FAX(DB のコメントのとおり)。画面案の都道府県・市区町村は、DB に列が無いため、住所1 = 都道府県と市区町村(例 東京都千代田区)、住所2 = 町名・番地・号(例 千代田1-1-1)に統合した(`tools/entity_gen/handwritten.js` の住所の項目・サンプルの分け方。会社情報も同じ)。`gen.js` で再生成。
- 取得元(`organizationRepositories` の `site`): 住所1・住所2・建物(呼称。言語コード `ja` の値)を読む。建物は、これまでオブジェクトの文字列になっていた(不具合)ため直した。実サーバーで、試験用の住所・事業所(既存の呼称を借りる)を登録して読み、論理削除で後始末して確認した。
- 書き込みは、共通関数(`shared_appellation_save`)とミューテーション(住所 `info_address`・事業所 `info_office`)で行う方針(`tools/docker/postgresql/issue/20261115_0001.md`)。DB に共通関数が適用されてから。
