# 20261118_0002 MRP の手続き(調査 → 評価 → 判断 → 確定・破棄)と、関数群の評価

指示: `F5`(MRP は実行負荷が大きく、利用者が実行する。生産計画に再 MRP・MRP の実行がある。`packages/features` から、実行の順を確認し、「調査 → 判断/評価 → 実行」の手続きにできるかを調べ、関数群を評価する。必要なものは残し、MRP の実装を続ける)・`F5-3`(`mrp_purge` は案 2)・`F3`(サブ画面)。

## 調べた結果
1.  `production_plan` の画面は、「MRPを実行」(`mrp_execute` = 計算 + 要判断が無ければ確定)と結果の表だけで、**調査・要判断の採否・確定・破棄の操作が無かった**(要判断が残ると、計算済みのまま先へ進めない)。窓口 `IMrpGateway` は `execute` だけ。ほかの MRP の関数のモデル(`production_plan_model/lib/src/graphql/mrp_method/*.graphql`。手書き)は、あるが使われていなかった。
1.  MRP を起動する入口は、MRP の画面だけ。DB にもアプリにも、受注の決定などで自動に起動する仕組みは無い。新しい受注は、次の受注 MRP(`p_mode` 1。まだ計画していない受注だけ)で、自動で対象になる。
1.  既存の関数で、手続きにできる(追加の関数は不要)。状態は DB の実行(`trans_mrp_run`。ビュー `v_mrp_run` の boolean)が持つ。計算済みの間、計画データは変わらず、確定の 1 回(`mrp_commit`)だけが 1 トランザクションで書き換える。
1.  関数群の評価: `mrp_check_items`・`mrp_run`・`mrp_execute`・`mrp_set_decision`・`mrp_commit`・`mrp_discard` は手続きに使う。`mrp_purge` は `mrp_run` の中(案 2)。`mrp_equipment_load` は MRP から呼ばれず使われていなかったため削除。`mrp_check_order_import` は取り込み前の確認で、この手続きには使わない(取り込みの機能が無ければ削除の対象。判断 F5-1)。**前回の記述の訂正**: `mrp_run` は `mrp_check_items` を呼んで、不備を提案(`EXC_MASTER`)にしている。
