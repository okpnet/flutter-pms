# 呼称の DB 関数(適用済み)をモデル・取得元に取り込む(単位・利害関係者)

DB に `unit_save`・`stakeholder_save`(`doc/query/20261114_0002`。戻り値は行、更新は渡した項目だけ)が適用された。

## 内容
1. `melos run gql:schema` で本家スキーマを更新(追加: `UnitSave*`・`StakeholderSave*`)。
2. モデル: `system_model/gql/unit.yaml` に `UnitSavePageCall`、`shared_master_model/gql/stakeholder_page.yaml` に `StakeholderSavePageCall` と `StakeholderPageEdit`(削除用)を追加。両モデルの `build.yaml` に JSON スカラーを追加(JSON の文字列で送る)。
3. 取得元: `system`(単位)・`shared_master`(利害関係者)の取得元を、読み取り専用から書き込めるものに入れ替えた(登録・更新は関数、削除は論理削除)。更新は、読み込んだ値から変わった項目だけ送る。DB のエラーの文を `EntityValidationException`(必須・コード重複)に変換。利害関係者の配送区分は、サンプルの ID が DB に無いため読み取り専用。単位の記号は DB の採番で読み取り専用。
4. 通信テスト(PostGraphile、一般ユーザー): 単位・利害関係者の登録 → 名称だけ更新(ほかが残る)→ 空にした項目が消える → 必須・コード重複の検証エラー → 論理削除。`system` 7 件・`shared_master` 27 件通過。

## 見つかった問題
- **適用済みの関数の不具合**: 同じ値で更新すると、履歴のトリガーが「変更なし」で UPDATE を握りつぶして 0 行になり、関数が `FOUND` で行の有無を判定していたため INSERT に進み、`shared_dictionary_value_ix1` に違反する。画面が全項目を送ると必ず起きる。適用済みの DB で再現し、修正 `doc/query/20261114_0003_appellation_functions_fix.sql`(`20261114_0002` を変更した全体のファイル。変更は `ap_dictionary_set`・`ap_text_set` だけで、先に行を引いて、無ければ INSERT、有れば UPDATE)で直ることを確認した(`0002` の版で再現 → `0003` を流して成功。全ケースも通過。トランザクション内で実行して ROLLBACK)。`0002` は、適用した版のまま残してある。画面側は変わった項目だけ送るため、修正の適用前でも動く。**DB への適用は未**(`tools/docker/postgresql/issue/20261115_0001.md` の 0)。
- 部分一意索引 `mstr_stakeholder_ix_code_active` は、DB に無い(未適用)。コードの重複は、関数の検査(`APL03`)で止まる(同時登録は止まらない)。
- 検証用 DB の再構築で担当者の ID が変わり、PocketBase の `app_user_id` が古くなっていた(「担当者が見つかりません」)。`tools\init\test_admin_init.bat`・`test_user_init.bat` を再実行し、テストのトークンのキャッシュ(`%TEMP%\pms_test_jwt_*.json`)を消して解決。
