接続先は`http://192.168.1.100:5000/graphql`、接続できなければ`http://192.168.9.245:5000/graphql`(`TestServer.candidateUrls`、テストには書かない)。実行時は`.100`に接続できず、`.245`に接続した。

「+認証」は、認証基盤(Keycloak)が未導入のため、実サーバーでのログインは試せない。代わりに、トークンが`Authorization`ヘッダーで送られること、401/403が`Err(ServerError)`(ステータス付き)になること、認証エラーのあとに復帰できることを代役サーバーで確認した。

## 結果

- 通信の異常のテスト(代役サーバー): 各モデルパッケージ5件、`organization`5件、`data_test_harness`10件。すべて成功。
- 検証用サーバーでの読み取り: 105本のうち87本が成功、**18本が失敗**。失敗は1つの原因: サーバー(`.245`)のスキーマが古く、`InfoAddress.iso31662`のまま(リポジトリのモデルは`countryCode2`)。DBの変更(住所の国コードの改名、別のセッションでコミット済み)がサーバーに反映されていない。サーバー側の更新後に`melos run gql:schema`で本家スキーマを更新すれば解消する見込み。テストは意図どおり、スキーマのずれを検出している。
- サーバーを使わないテスト(`--exclude-tags server`): 全モデルパッケージと`organization`で成功。

## 見つかった問題と対応

1. `GraphQLClientProvider.query`: 通信の途中の切断(`http`の`ClientException`)で、`Err`ではなく汎用の例外が投げられていた → `Err(NetworkError)`に修正。
2. 同: HTTP 401/403が、本文にGraphQLのエラーがあると`Err(DeveloperError)`、無いと汎用の例外になっていた → 本文にかかわらず`Err(ServerError)`(ステータス付き)に修正。
3. 未対応(`pms_graphql/issue/20261028_0001.md`): 対応表に無い例外(`PartialDataException`など)が汎用の例外になる。制限時間超過が`GraphqlTimeoutException`と`Err(TimeoutError)`の両方で現れる。
4. 環境: このPCの`.schema/schema.graphql`は、別のセッションが行ったDB変更(`countryCode2`)を含まない古いもの。コミット済みの画面用スキーマ(②の出力)は新しいため、`gql:build`は通るが、`gql:prune`・`gql:check`は`.schema`が古いと失敗する。サーバーが更新されたら`melos run gql:schema`で取得し直す。
5. `packages/infra/graphql_provider_lib/`の旧ファイル(303件)が、別のセッションのコミット(44d5d6a)でGitに再び入っている。ワークスペースの対象にはならないが、旧ライブラリの削除(issue 20261027_0001)と食い違う。意図した復活か確認が必要。
