# 20261027_0003 query_builder によるサーバー側の問い合わせ・フィルタ変換 — 実施結果

指示: [issue/20261027_0003.md](../../issue/20261027_0003.md)(保留の課題のうち、適用に書かれた範囲を実施)

## 確認結果

| 項目 | 結果 |
|---|---|
| query_builder の現状 | 既存テスト38件は成功。`GraphqlVisitor`はHasura形式(`_eq`・`_and`・`where`)で、PostGraphile(connection-filter: `equalTo`・`and`・`filter`)には使えない。README未記入、`lib/src`直下に`constants/`と重複するファイルがある。ワークスペースの他の層からは`data_strategist`・`grid_extensions`・`pms_app`の依存宣言だけで、コードからの利用は無い |
| data_strategist | 検索条件の変換機能は持たない(`Expression`を渡すだけ)。変更不要。`data_strategist/issue/20261027_0001.md`に確認結果と`take: 0`の扱いを記載 |
| 変換の置き場所 | 2段に分けた。(1) `query_builder`: `Expression` → 平坦化キーのまま出す connection-filter の木(スキーマを知らない)。(2) `pms_graphql`: 平坦化キー → 入れ子の Filter(画面ごとの対応表を持つ)。`query_builder`(foundation)が`pms_graphql`(infra)に依存しない向きを守れる |
| サーバー側集計 | 本家スキーマに集計(`aggregates`)は無い(PostGraphile に集計プラグイン無し)。取れるのは`totalCount`と、DBのビュー(`v_*`)。集計はビュー側で持つ方針が妥当(件数ビュー`v_*_count`の前例どおり)。クライアントでの畳み込みは、件数が多いと取得量が増えるため避ける |

## 実施したこと

- `query_builder`: `CLAUDE.md`(規則を適用)、`PostgraphileVisitor`・`PostgraphileExpressionBuilder`・`SortPostgraphileExpressionBuilder`、テスト、`doc/contents/usage.md`、`issue/20261027_0001.md`(整理の課題)。
- `pms_graphql`: `FlatFilterConverter.convertTree`(and / or / not の木の葉を展開)とテスト。
- `data_strategist`: Issue 追加のみ。
