## 適用
スキーマ `tests` に、psql で1回ずつ流す(何度流しても同じ。`CREATE OR REPLACE`)。
```
psql -d test_avocado -f 20261114_0001_operation_functions.sql
psql -d test_avocado -f 20261114_0001_v_work_plan_registrable.sql
psql -d test_avocado -f 20261114_0002_appellation_functions.sql
```
適用したら、`melos run gql:schema` → `melos run gql`(新しい関数は `kind: function`、ビューは `kind: read` で `model_providers` に足す)。

## 検証の結果(2026-11-14、検証用サーバー。DB は変わっていない)
- 関数・ビューの作成: 成功。
- 受注明細: キャンセル(残が減る)、残を超えるキャンセル(`OPR02`)、停止(`open_quantity` が 0)、同じ停止(`OPR03`)、再開、納期・数量の変更、キャンセル数量より小さい数量(`OPR02`)、存在しない明細(`OPR01`)・担当者(`OPR00`)。

## 06 の評価(2026-11-14)への対応
`06_cteate_test.sql` に流して一般ユーザーで試した評価で、関数の中身の直しを3件受けて反映した(`20261114_0001_operation_functions.sql`)。
| # | 指摘 | 対応 | 確認 |
|---|---|---|---|
| 4 | `order_detail_change` は `delivery_date` だけを変えていた。MRP は `deadline` を先に見る(受注明細の完了期限 → 受注の完了期限 → 受注明細の出荷納期 → 受注の出荷納期)ので、納期を変えても MRP に反映されない | MRP が見る完了期限 `deadline` を変える引数 `p_new_deadline` を足した(出荷納期は `p_new_delivery_date` で別に変える)。計画変更の旧・新の日付は、MRP が今見ている期限(旧)と新しい完了期限 | 検証用 DB: 完了期限を変えると、MRP が見る期限が新しい値になった |
| 5 | `supply_register` は、返却不要(譲渡)・無償 → 有償の切り替えで `lot_id` を渡すと在庫を払い出していた(ロットが 1997 → 1996 に減った) | 在庫を動かすのは「渡す・返す場面」(`receive = false` で、`company_owns` でも、`p_complaint_id`(切り替え)でもない)だけにした。譲渡・切り替えで `lot_id` を渡したときは、在庫を動かさず、そのロットをつなぐだけ | 検証用 DB: 譲渡の支給で `lot_id` を渡しても、ロットの数量は 22 のまま、ロットはつながった |
| 6 | `inventory_request_hold` は、在庫を保管先へ移したあとも、引当予約が移動元のロットを指したままだった | `visiter_move` が返した移動先(仮止めの + の行)に、引当予約の `trans_visiter_id` を付け替える | 実行は未確認(検証用 DB の棚に場所が無く、`VIS05` になる)。コードの確認のみ |

あわせて、評価の「推奨・確認」のうち、内容が分かる2件を反映した(残りの2件は、内容が分からないため未対応)。
1. 返品区分と明細の向きの検査: 顧客からの返品(`receive = true`)に発注側の指定(`p_purchase_id`・明細の `purchase_detail_id`・`purchase_rec_id`)、仕入先・外注先への返品(`receive = false`)に受注側の指定(`p_order_id`・`order_detail_id`・`shipping_order_detail_record_id`)があると `OPR02`。実行は未確認(返品区分のマスタが空)。
1. 押さえた品の記録: `lot_hold` の計画変更の対象を、押さえた(仮止めした)移動先のロットにした(移動元のロットは数量が減るだけで、未処置一覧は「仮止めのまま残っているロット」で見つけられる)。**これは推測。評価の意図と違えば直す**。

## ER ツール(PERO)のデータへの反映(2026-11-14)
関数の出力は、SQL ではなく PERO のデータ `tools/database/ER/pms_test.pero` の `methods` から `06_cteate_test.sql` に出力される。取り込んだ関数に、次の不具合があり、`pms_test.pero` を直した(関数22本。`methods` 以外と、対象外の関数のデータは変えていない)。
| 不具合 | 原因 | 対応 |
|---|---|---|
| 操作の関数15本が、戻り値の表より前に出力され、作成に失敗する(06 で30件のエラーのうち) | 関数の `dependsOnTableIds`(関数が使う表・ビューの ID。出力の順を決める)が空だった | 本文の `tests.<名前>` から、使う表・ビューの ID(戻り値の表を含む)を求めて入れた |
| `op_add_plan_change` に `@omit` が付かず、GraphQL の mutation として公開される。一般ユーザーが、受注明細を変えずに、キャンセル数量 999 の計画変更を登録できた | 署名(`args`)が空で、`COMMENT ON FUNCTION tests.op_add_plan_change() IS '@omit'` になっていた(引数がある関数には合わない) | `args` に26個の引数の型を入れた。SQL の `COMMENT` にも署名を書いた |
| 取り込み済みの関数が、評価の前の版 | 取り込みのあとで、SQL を直した(納期の `deadline`・譲渡の在庫・予約の付け替え・返品の向き) | 現在の SQL の本文・コメント・署名で更新した(`order_detail_change`・`inventory_request_hold`・`lot_hold`・`return_register`・`supply_register`) |
- 直す前のデータの控えは、作業用の一時フォルダに置いた(Git には入れていない)。PERO で開いたままの場合は、閉じて開き直してから出力する(開いたまま保存すると、この修正が上書きされる)。
- 初期化の順は `05` → `06` → `09` → `10` → `11` → `12` → `13` → `14` → `15`(07・08 は 06 に取り込んだ。流さない)。ルートの `CLAUDE.md` に反映した。
- 新しい関数を PERO で足すときは、`args`(署名)と `dependsOnTableIds` を忘れずに入れる(空だと、出力の順と `@omit` が壊れる)。

## 試験結果(2026-11-14、新しい 06)への対応
新しい 06(PERO で出力し直したもの)はエラー 0 で、前回の指摘 6件・推奨 2件も直っていた。ロール別・操作関数の試験(一般ユーザー)も期待どおりだった。次の指摘に対応した。
| 指摘 | 対応 | 確認(検証用 DB。トランザクション内で実行して ROLLBACK) |
|---|---|---|
| 返却不要(譲渡)・無償 → 有償の切り替えは、所有がロット単位で変わる。2000個のロットに数量1の譲渡をつなぐと、2000個がまるごと自社の物になる | **関数の中でロットを分ける**ことにした。ロットの数量が支給の数量より多いときは、先に同じ棚の中で `visiter_move`(- の行と + の行)で数量分のロットを作り、そのロットをつなぐ。同じなら、そのロットをつなぐ。足りなければ `OPR02`。理由: 呼び出し側(画面)が分けるより、1トランザクションで確実に分かれる。止めるだけだと、一部だけの譲渡ができない | 22個のロットに数量1の譲渡: つながったのは、数量1の新しいロット(元のロットではない)で、元のロットは減った。ロットより多い数量は `OPR02`。保管・廃棄(場所つき)も成功 |
| 「無償 → 有償の切り替え」は、起因の異常を渡したときだけ判定される | 画面の仕様に、この場面では異常の選択を必須にすることを書いた(`CLAUDE.md`)。関数は変えない(異常がなければ「渡す場面」になる) | — |
| 発注明細は、全部キャンセル済みでも停止できる | 全部キャンセル済み(`cancel_closed`)は `OPR03` | 残をすべてキャンセル → 停止は `OPR03` |
| 受注明細の数量は、出荷済みより小さくできる | `order_detail_change` は、キャンセル数量 + 出荷済みより小さい数量を `OPR02`。発注も、キャンセル数量 + 受入済み | 数量を下げる試験は `OPR02`(出荷済みのデータは無く、キャンセル数量で確認) |
- 検証用 DB の棚には場所が無く、`visiter_move` は移動元の棚の場所を要する(`VIS05`)。試験では、トランザクション内で場所を作って棚に付けて確認した(DB は変わっていない)。
- `pms_test.pero` に反映した(`order_detail_change`・`purchase_detail_set_stop`・`purchase_detail_change`・`supply_register`。依存の ID も更新)。**PERO で `06_cteate_test.sql` を出力し直す**(コミットした 06 は、この4関数が前の版)。
