# 登録できる作業指示かの判定のビューと、操作の DB 関数

指示元: `flutter-pms/issue/20261114_0001.md`(決定仕様 137 の反映)。検証は 2026-11-14、PostgreSQL `192.168.1.101`・PostGraphile `192.168.1.100:5000` で実施。

## 1. 操作の DB 関数(必須)
SQL の案: `doc/query/20261114_0001_operation_functions.sql`(検証用 DB でトランザクション内で実行して確認済み。適用はレビューのあと)。
PostGraphile v4 は、1つのドキュメントの複数の mutation を1つのトランザクションにしない(実測。1つ目が成功し2つ目が CHECK 違反で失敗したとき、1つ目は残り、応答は `{m1: {...}, m2: null}` の部分成功)。そのため、計画変更の登録と本体の更新をクライアントの複数の mutation で行うと、片方だけが書かれる。
1. 次の操作を、1回の呼び出し = 1トランザクションの関数(`kind: function` で呼べる VOLATILE の関数。`tests` スキーマ、担当者は `visiter_staff()` と同じく JWT の `staff_id`)にする(仕様 8章 #2)。
   1. 受注明細・発注明細のキャンセル(`cancel_quantity` の加算 + 計画変更)
   1. 停止・再開(受注明細・発注明細・生産計画)
   1. 納期・数量の変更(延期・前倒し・増減)
   1. 生産計画の打ち切り(`discontinue = true` + 計画変更)
   1. 引当予約の解除・保管、キャンセル後の品物の処置(在庫にする・押さえる・引き渡す・廃棄・材料に戻す)
   1. 返品(伝票・明細・ロットのつなぎ)・支給(伝票・明細・ロットのつなぎ)・精算
1. 引数は、担当者(省略時は JWT)・理由(変更理由の ID)・申し出た相手・備考。戻り値は、作った計画変更(`trans_plan_change`)など、画面が再読込せずに表示できる行。
1. 失敗は errcode で判定できるようにする(`visiter_*` の `VIS00`〜`VIS07` と同じ形)。

## 2. 登録できる作業指示かの判定のビュー(提案)
SQL の案: `doc/query/20261114_0001_v_work_plan_registrable.sql`(同上)。
`barcode_entry` は、停止中・終了した作業指示に実績を登録させない。生産計画の停止・打ち切り(`trans_operations_plan.stop`・`discontinue`)と、直接つながる受注明細(`trans_resource_plan.trans_order_detail_id`)は画面側で読めるが、**組立品の子の生産計画は、親をたどった最上位の受注明細の停止・全部キャンセルを判定できない**(たどり方の関数 `mrp_root_order_detail` が `@omit` で公開されない)。
1. ビュー(例: `v_work_plan_registrable`)を作る: 作業指示(`trans_work_plan_id`)・`registrable`(boolean: 生産計画が停止・打ち切りでなく、最上位の受注明細が停止・全部キャンセルでない)・`stopped`・`closed`(画面が通知の文を分けるため)。
1. `COMMENT ON VIEW` に `@primaryKey` と `@foreignKey (trans_work_plan_id) references trans_work_plan` を付ける(`v_order_detail_balance` と同じ形)。
1. できたら、`barcode_entry_model` の `ScanWorkPlanPage` が、直接の判定を、このビューの列に置き換える(判定を DB に集める)。
