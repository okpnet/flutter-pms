# 20261118_0002 受注明細の計画状況のビューと、mrp_run の変更(検査してから PERO に取り込む)

依頼元: `flutter-pms` のルート(`issue/20261118_0001.md` の G14・6-1)。**方針(2026-11-18 採択): 「未計画の受注明細」はビューにする**。検査が通るまで、PERO のデータ・`06_cteate_test.sql` には入れない(通過後に取り込む)。**検査は、DB に接続できる環境で、依頼先が実施する**(依頼元の環境では、DB に接続できず、未実施)。

## 変更の内容
1.  新しいビュー `tests.v_order_detail_plan`(受注明細ごとの、直接つながる最新の資材計画)。`trans_resource_plan_id`(論理削除と、下位の部品の資材計画を除く。最新 = `register_at` の降順、同じときは ID。無ければ NULL)・`planned`(boolean。資材計画が有る)。`mrp_run` の受注の需要が、今まで直接書いていた探し方(`LEFT JOIN LATERAL`)と同じ。
1.  新しいビュー `tests.v_order_detail_planning`(受注明細の計画状況。画面・モデル用)。`v_order_detail_balance` の行(受注が論理削除でないもの)に、`trans_resource_plan_id`・`planned`・`has_demand`(数量 − キャンセル数量 + 代品ありの返品 > 0)・`stopped`・**`to_plan`(次の受注MRP が計画する = 未計画 かつ 需要が有る かつ 停止していない)**を足す。boolean の列で判定する(R1)。`@foreignKey` で、受注明細・受注・品目・資材計画へたどれる。
1.  `tests.mrp_run` の変更は 1 か所だけ: 受注の需要の `LEFT JOIN LATERAL (…資材計画の最新の 1 件…) AS rp` を、`LEFT JOIN v_order_detail_plan AS pl … LEFT JOIN trans_resource_plan AS rp ON rp.trans_resource_plan_id = pl.trans_resource_plan_id` に替える(`rp` の列(`trans_resource_plan_id`・`inventory_resavation`・`quantity`・`deadline`)は同じ。引数・戻り値・ほかの処理は変えない)。非計上・範囲指定の再帰など、ほかの資材計画の探し方(3 か所)は変えない(探し方が違う)。
1.  `to_plan` と `mrp_run` の需要の条件(`WHERE` の `quantity − cancel + replacement > 0`・`NOT (stop AND 未計画)` と、受注MRP が未計画を対象にすること)は、同じ意味を 2 か所に書く(`mrp_run` の中の条件は、ビューを使うと、ビューが `v_order_detail_balance` を二重に評価して、遅くなるため、ビューにまとめていない)。**食い違わないことを検査(T4)で確認する**。`mrp_run` の条件を変えるときは、ビューの `to_plan` も同時に直す(ビューの `COMMENT` に書いてある)。

## 他に影響しないことの調査(静的。DDL・Dart の読み取りの範囲)
1.  **ビューの使用者**: 新しいビューを使うのは、`mrp_run`(`v_order_detail_plan` だけ)と、これから作るモデル(`production_plan_model` の `OrderDetailPlanningPage`。YAML 追加済み)だけ。既存の関数・ビュー・トリガーは、新しいビューを参照しない。名前の衝突も無い(`v_order_detail_plan*` は、DDL にも、手元の本家スキーマにも無い)。
1.  **`mrp_run` の変更**: 結合の入れ替えだけで、`rp` の行(最新の資材計画)は同じ。違いが出うるのは、同じ `register_at` の資材計画が複数ある受注明細だけ(旧い探し方は不定、新しい探し方は `trans_resource_plan_id` で決める。**不定だったものを決めるだけで、旧い結果の 1 つになる**)。`mrp_run` の呼び出し元(`mrp_execute`・クライアントの `mrpRun`・`mrpExecute`)の引数・戻り値は変わらない。
1.  **性能**: `v_order_detail_plan` は、`v_order_detail_balance` を使わない(`mrp_run` が、すでに `v_order_detail_balance` を結合しているため、ビューが重ねて評価しないようにした)。追加の結合は、`trans_resource_plan` の主キーでの 1 回(索引あり)。`v_order_detail_planning`(画面用)は、`v_order_detail_balance` を使うため、一覧・件数の読み取りで、`v_order_detail_balance` と同程度の重さ(出荷・返品の集計の副問い合わせ)。検査 T5 で、旧い探し方と新しい結合の実行時間を比べる。
1.  **PostGraphile のスキーマ**: 新しい型 `VOrderDetailPlan`・`VOrderDetailPlanning`(+ 一覧・絞り込み・並び替えの型)と、`@foreignKey` による逆向きの関係の追加(`TransOrderDetail`・`TransOrder`・`MstrItem`・`TransResourcePlan` に `vOrderDetailPlan…`・`vOrderDetailPlanning…` の項目)。**既存の項目・型の変更・削除は無い**(追加だけ)ため、既存のクエリ・モデルは影響を受けない。型・フィールドが増えるため、本家スキーマのサイズが少し増える。
1.  **権限**: `09_grant_test.sql` は、スキーマの全表(ビューを含む)に付与するため、変更不要(新しいビューは、再付与のあとに、一般ユーザー・管理者とも読める。既存の DB は、ビューを作ったあとに `GRANT SELECT ON ALL TABLES IN SCHEMA tests …` を流す)。

## 検査と適用の手順(依頼先)
1.  `tools/docker/postgresql/test/20261118_0001_order_detail_planning.sql`(検査。全部 `ROLLBACK` で取り消す)を、変更前の `mrp_run` が入った検証用 DB で、`-v apply_file=20261118_0001_apply.sql` つきで実行する。内容: T0(変更前の `mrp_run` を、受注MRP・再MRP・範囲指定の再MRP で実行し、提案を残す)→ 適用(ビュー 2 つ + `mrp_run`)→ T1(ビューの行が、旧い探し方と一致)・T2(列の整合・`to_plan` の定義)・T4(`to_plan` が、`mrp_run` の需要の条件と一致)・T3(新しい `mrp_run` の結果が、変更前と一致)・T5(実行時間の目安)。
1.  全部通ったら、`20261118_0001_apply.sql` を適用する(ビュー 2 つ → `mrp_run`。`GRANT` も)。
1.  通過後、PERO のデータと `06_cteate_test.sql` に取り込む(`test/20261118_0001_incorporate_to_pero.dart`。取り込んだら、`test/` のこの 3 ファイルは削除する)。
1.  PostGraphile を再起動し、`melos run gql:schema` → `melos run gql`(G12)。`OrderDetailPlanningPage` が生成される。

## 確認してほしいこと
1.  T1〜T5 が通ること。T3 の差が出たときは、差の行(提案の種類・品目)を知らせる。
1.  T1 で、同じ `register_at` の資材計画が複数ある受注明細が見つかったか(見つかっても、新しい探し方の結果は決定的)。
