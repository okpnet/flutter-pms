# 20261116_0001 MRP の提案のビュー(`v_mrp_suggestion`)を boolean の列で返す

依頼元: `flutter-pms` のルート(`issue/20261116_0002.md` の「MRP の提案(`v_mrp_suggestion`)の boolean 化」)。

## 目的
アプリが、提案の種類(`trans_mrp_suggestion.kind`。文字列 17 種)と判断(`decision`。0/1/2/9)のコード値を持つと、解釈がアプリごとに変わる。DB のビューが boolean の列で返し、アプリはその列だけを使う(設計の共通ルール「状態・区分をコード値で持たない・判定しない」)。

## 決定したこと
1.  ビューは `kind` を出さず、対象・動きを boolean に分解して返す。ビットスイッチの整数値(boolean をまとめた整数)は持たない(廃案)。
1.  言語別の表示の文字の列は持たない。アプリは、列のコメントを見出しにして、チェック・シグナル・ステップで表示する。
1.  `decision` を分ける: 種類から決まる `requires_decision`(判断を求めるか。情報だけは false)、利用者の操作の結果の `adopted`・`rejected`(両方 false = 未判断。両方 true は CHECK で禁止)。整数の `decision` はビューの外へ出さない。

## 依頼
1.  ビュー `v_mrp_suggestion`(名前は既存の `v_mrp_pending_suggestion` などと合わせて決めてよい)を作る。`kind` から `CASE` で導く(MRP の関数・既存の行は変えない)。`symbol` 列を含める(設計の共通ルール)。
1.  列の案(種類との対応は、実際の意味に合わせて確定する):
    1.  対象: `is_purchase`・`is_production`・`is_outsource`・`is_plan`・`is_exception`・`is_supply_request`。例外の主題: `subject_equipment`・`subject_stock`・`subject_master`。
    1.  動き: `is_new`・`is_change`・`is_cancel`・`is_keep`・`is_option`。
    1.  判断: `requires_decision`・`adopted`・`rejected`。
1.  種類の分解の案(判断を求めるかは、実際の運用に合わせて確定する):

    | 種類(`kind`) | 対象 | 動き | 判断を求める |
    |---|---|---|---|
    | `PURCHASE_NEW` | 発注 | 新規 | 確認 |
    | `PURCHASE_RESCHEDULE` | 発注 | 変更(日程) | 確認 |
    | `PURCHASE_CANCEL` | 発注 | 取消 | 確認 |
    | `PRODUCTION_NEW` | 生産 | 新規 | 確認 |
    | `PRODUCTION_RESCHEDULE` | 生産 | 変更(日程) | 確認 |
    | `PRODUCTION_CANCEL` | 生産 | 取消 | 確認 |
    | `OUTSOURCE_NEW` | 外注 | 新規 | 確認 |
    | `OUTSOURCE_CANCEL` | 外注 | 取消 | 確認 |
    | `OUTSOURCE_OPTION` | 外注 | 切替の選択肢 | はい(暫定) |
    | `PLAN_NEW` | 生産計画 | 新規 | 確認 |
    | `PLAN_UPDATE` | 生産計画 | 変更 | 確認 |
    | `PLAN_KEEP` | 生産計画 | 維持 | 確認(情報の可能性) |
    | `PLAN_CANCEL` | 生産計画 | 取消 | 確認 |
    | `EXC_OVERLOAD` | 例外(設備) | — | はい(暫定) |
    | `EXC_EXCESS` | 例外(在庫) | — | 確認 |
    | `EXC_MASTER` | 例外(マスタ) | — | 確認(情報の可能性) |
    | `SUPPLY_REQUEST` | 支給依頼 | 新規 | はい(発注・生産に変換しない) |
1.  `adopted`・`rejected` の更新方法(整数の `decision` との対応)を決める。更新はミューテーションまたは関数のどちらか(MRP の確定の関数 `mrp_commit` などとの整合も確認する)。
1.  PostGraphile 用: 主キー・外部キーを `COMMENT ON VIEW` の `@primaryKey`・`@foreignKey` で付ける。
1.  DB のテスト: 「対象の列が、全ての行でちょうど 1 つ立つ」ことを検査する(新しい種類が増えても、どの列も立たない行が出ないように)。

## 確認してほしいこと
