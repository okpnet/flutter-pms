# 要望: 共有の`Provider<ILoggerProvider>`を提供する(発行元: baton_lib)

## 背景
`baton_lib`は、ロガーを`①アプリケーションが`logger_provider`のインスタンスをRiverpodに登録 -> ②ライブラリが`ILoggerProvider`としてRiverpodから受け取る`という流れで利用する。

## 問題点
- 現状`logger_provider`にはRiverpodのProviderが無く、`baton_lib`が受け取り口として固有の`commandLoggerProvider`(`Provider<ILoggerProvider>`)を暫定で定義している。
- アプリは`main.dart`で`commandLoggerProvider.overrideWithValue(logger)`と、`baton_lib`固有のProviderへ登録している。
- ほかのライブラリ(feature等)が同じロガーを受け取るには、各ライブラリが固有のProviderを作り、アプリが個別にoverrideする必要がある。「RiverpodからILoggerProviderを取得すれば解決する」という単一参照にならない。

## 代替案(推奨)
`logger_provider`に共有のProviderを1つ定義する。

```dart
/// アプリが①でoverrideし、各ライブラリが②で受け取る。
final loggerProvider = Provider<ILoggerProvider>(
  (ref) => const NoopLoggerProvider(),
);
```

- アプリ: `loggerProvider.overrideWithValue(await DefaultLoggerProvider.fromConfig(...))`(①)
- 各ライブラリ: `ref.watch(loggerProvider)`(②)
- `baton_lib`は`commandLoggerProvider`を廃止し、`logger_provider`のこのProviderへ置き換える。

## 影響・留意点
- `logger_provider`の`pubspec.yaml`へ`flutter_riverpod`(ルートのmelos管理の版、`^3.4.3`)の追加が必要。
- Providerの名前は`logger_provider`のクラス名・Flutter慣例に合わせて決めてよい(`loggerProvider`は案)。
- 変更後は`baton_lib`側で置換を行う。必要な作業はこの変更の完了通知を受けてから実施する。

## 判断(baton_lib)
- 受け取る側(`baton_lib`)は`ILoggerProvider`を必須とし、nullを許容しない。ログの取り忘れのほうがリスクが大きいため。
- 共有Providerの未登録時の挙動(現状は`NoopLoggerProvider`)は`logger_provider`側の判断とする。登録し忘れの検出が必要なら、アプリ側のテストで`loggerProvider`が登録されていることを確認する。
