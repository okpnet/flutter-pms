# 20261101_0001 JWTを使うOAuth認証ライブラリ(pbapi)

指示: [issue/20261101_0001.md](../../issue/20261101_0001.md)
サーバー: `tools/docker/pocketbase/README.md`(PocketBase v0.40.6、テスト環境 `http://192.168.1.103:8090`。`/api/health`の応答を確認)

## 実施
`packages/infra/pbapi`を追加(`packages/*/*`のため、ルートpubspecの編集は不要)。`CLAUDE.md`(Issueの規則を適用)、`doc/contents/usage.md`、`doc/contents/server_user_files.md`を追加。

| 実装する機能 | 実装 |
|---|---|
| 新規登録 | `AccountService.register`(招待コード+パスワード。登録後ログイン) |
| パスワード変更 | `AccountService.changePassword`(古いパスワードの一致で適用。新しいパスワードで入り直す) |
| パスワードを忘れた | メールあり: `requestPasswordReset`→`confirmPasswordReset`。メールなし: `requestAdminPasswordReset`(`IAdminContact`) |
| ログイン/ログアウト | `SessionService.login`(トークンを含む`AuthSession`を返す)/`logout`(破棄) |
| セッション管理 | `ensureSession`(アクションの度)、`watch`(定期) |
| ファイルアップロード/ダウンロード | `SharedFileService.upload`(IDと版を返す)/`download`(ファイルIDから) |
| 個人ファイルアップロード | `PersonalFileService`(設定のアップロード・ダウンロード・削除) |

## 判断したこと(要確認を含む)

### 1. 通信ライブラリ: 公式の`pocketbase`(0.25.3)を採用
- 提案を求められたため、代替(`http`/`dio`で自作、他のOAuth2/OIDCクライアント)と比較した。
  - 自作: JWTの保存・更新・認証ストアの連動・multipartの実装を自前で保守することになり、脆弱性を作り込むリスクが大きい。
  - 汎用のOAuth2クライアント: このサーバーは招待制のパスワード認証(PocketBaseの`authWithPassword`)で、OAuth2のフローは使っていない(READMEで対象外)。使う理由が無い。
  - 公式SDK: サーバーの作者が保守し、サーバーのバージョンに追随する。`AsyncAuthStore`でトークンの保存先を差し替えられる。
- 弱点(補った点): SDKの`ClientException`にURL(短時間用のファイルトークンを含みうる)が入る → `PbException`に変換して外へ出さない。サンプルが使う`shared_preferences`はトークンを平文で保存する → `ITokenStore`(Strategy)にして、本番は安全な保管庫で実装する方針にした。

### 2. 「Oauth認証」の表現
- 題名は「Oauth認証」だが、サーバーはJWT(PocketBaseが発行)による招待制のパスワード認証で、OAuth2は対象外(README冒頭)。題名ではなく、サーバーの仕様に合わせた。OAuth2が必要になったら、SDKの`authWithOAuth2`で追加できる(別のIssue)。

### 3. 接続先のURLは`.../api`を付けても付けなくてもよい
- Issueは`http://192.168.1.103:8090/api`だが、SDKは`/api`を自分で付け足す。`PbEndpoint`が末尾の`/api`を取り除く(付けると`/api/api`になるため)。

### 4. 平文の`http`はローカルのネットワークだけに限った
- テスト環境は`http`のため、`localhost`・`10.x`・`172.16-31.x`・`192.168.x.x`・`*.local`は許可。それ以外は`https`必須(`ArgumentError`)。本番を`http`で運用することは想定しない。

### 5. 「新規登録: ユーザーは新しい一意なIDとパスワードを決定する」
- このサーバーは招待制で、自己登録(`users`の作成)は閉じている。ユーザーIDは**管理者が招待時に決める**(READMEの3章、重複は発行時に拒否)。そのため、利用者が決められるのは招待コードとパスワードのみ。クライアントだけでは「利用者がIDを決める」は実現できない。
- **要判断**: 利用者がIDを決める登録にするには、サーバー側を変える必要がある(例: 招待コードだけで`username`を指定できるようにするフック、または自己登録を開く)。今回はサーバーの仕様(招待制)を優先して実装した。

### 6. 「パスワード忘れた(メールあり): メールへコードを送信、一致したら変更画面へ」
- PocketBaseは、再設定の**リンク(トークン)**をメールで送る。コードの一致を確認するだけのAPIは無く、確認と再設定は`confirmPasswordReset(token, 新しいパスワード)`で同時に行われる。
- そのため「コードが一致したら変更画面へ切り替え」は実現できない。画面でコードと新しいパスワードを続けて入力させ、まとめて渡す形にした。コードの確認を先に行いたい場合は、サーバーに確認用のAPIを追加する(別のIssue)。
- メールの本文にトークンをコードとして載せる設定(PocketBaseのメールテンプレート)と、SMTPの有効化(`PB_SMTP_*`)はサーバー側の作業。

### 7. 「パスワード忘れた(メールなし): 管理者へメール」
- ログイン前のユーザーが管理者へメールを送る窓口は、PocketBaseに無い。クライアントがメールを送る手段も無い(SMTPの認証情報を持たせるのは危険)。
- 連絡手段は`IAdminContact`(Strategy)として分離し、実装はアプリが差し込む。未設定のときは`notConfigured`を投げる(黙って成功にしない)。
- **要判断**: 実装案は、(a)サーバーに専用API(`POST /api/app/password-help`、管理者へメール、レート制限つき)を追加する、(b)社内のメール・チャットへ送る。(a)が安全。

### 8. 個人ファイル(設定のアップロード)は、サーバーに`user_files`が必要
- 既存の`app_files`は全ユーザーが参照できる共有で、更新・削除もできない。設定は本人だけが見え、上書きできる必要があるため、使えない。
- 本人だけが参照・更新できる`user_files`コレクションとフックを、`doc/contents/server_user_files.md`に**提案**として書いた。サーバーの`tools/docker/pocketbase`は変更していない(サーバーに適用するかは判断が必要)。適用するまで、`PersonalFileService`は実サーバーでは404(`notFound`)になる。
- `settings_keeper`(ローカル設定の保存と復元)との接続は行っていない。必要なら`SettingsStorage`の実装として、`PersonalFileService`を使うものを別のIssueで作る。

### 9. ログアウトはこの端末のトークンの破棄のみ
- PocketBaseのトークンは状態を持たないJWTで、サーバー側から失効させる標準のAPIが無い。盗まれたトークンを止めるには、管理者が該当ユーザーのパスワードを変更する(READMEの5章)。トークンの有効期間(`PB_AUTH_TOKEN_DURATION`、既定7日)が長いため、必要なら短くする。

### 10. パスワード変更後は新しいパスワードで入り直す
- パスワードを変更すると、PocketBaseは既存のトークンを失効させる。変更後に`ensureSession`が失敗しないよう、`changePassword`が新しいパスワードで自動的にログインし直し、新しい`AuthSession`を返す。

### 11. セッション確認の失敗の扱い
- `ensureSession`は、401/403/404のときだけトークンを破棄して`false`を返す。通信できないとき(`network`)は有効/無効を決めず、例外を投げる(トークンは残す)。オフラインでログアウトさせないため。`watch`は通信できなかった回を流さない。

### 12. パスワードの長さ
- クライアントで8文字以上を確認する(サーバーの既定の最小値)。サーバーの設定が変わった場合は、サーバーの応答(`fieldErrors['password']`)が正となる。

### 13. `tools/docker/pocketbase/`は今回のコミットに含めない
- ユーザーが追加した未追跡のフォルダで、`.env`(Gitの対象外)を含む。サーバー側の作業のため、このIssueの成果物とは分けた。

## 確認
- `pbapi`のテスト 30件(通信を差し替えるテスト)+ 実サーバーのテスト 2件(`server`タグ。ログイン失敗が`invalidCredentials`になること、未ログインの共有ファイル参照が拒否または空になること)が成功。
- 実サーバーでは、データを作らないテストだけを実行した。ログイン成功・登録・ファイルのアップロードは、利用者・招待・データが増えるため実行していない(通信を差し替えたテストで、要求の形とサーバーの応答の扱いを確認した)。
- `dart analyze`は、info 2件(`prefer_initializing_formals`。非公開フィールドを名前付き引数から代入する書き方で、`baton_lib`などと同じ)。
