# CLAUDE.md

## このプロジェクトについて
`jwt_verification_test` は、**テスト専用**のプロジェクトです。PocketBase(`http://192.168.1.103:8090`)が発行した JWT を、PostGraphile(`http://192.168.1.100:5000/graphql`)とモデルパッケージ(`packages/model_providers/*_model`)で検証します。ライブラリのコード(`lib/`)は持たず、他のパッケージはこれに依存しません。

```
PocketBase ──(1)JWT を発行──▶ pbapi(SessionService)──(2)Authorization: Bearer──▶ PostGraphile ──(3)ロールを切り替え──▶ PostgreSQL
                                   Riverpod が保持                                 JWT を検証                     pms_user / pms_admin
```

## 保証すること(Issue 20261103_0001)
| 保証 | テスト |
| --- | --- |
| PocketBase が JWT を返す(署名方式・aud・ロール・担当者・期限 15 分・個人情報を含まない) | `test/pocketbase_jwt_test.dart` |
| JWT は Riverpod のサービスがメモリ上で期限の手前まで保持し、ログアウト・再起動で消える。暗号化はしない(判断は実施ログ) | 同上 |
| セッションが無い(破棄・無効化・削除)と JWT は得られない。別の利用者で入り直しても前の利用者の JWT を使い回さない | 同上 |
| PostGraphile が JWT を検証する(期限切れ=401、署名・aud・アルゴリズムの不正=403、改ざん・ロールの昇格・`postgres` へのロール切り替えは不可) | `test/postgraphile_jwt_test.dart` |
| セッションが切れた状態で、**12 のモデルすべて**がデータを返さず、正しい型のエラーを返す | `test/model_session_test.dart` |
| セッションを更新しながらデータを取得できる(期限切れ → 取り直して再試行も含む) | 同上 |
| **書き込み(ミューテーション)**を JWT で行える。セッション切れ・改ざん・匿名では書き込めず、データも変わらない(登録・論理削除・復元) | `test/mutation_session_test.dart` |

エラーの型(`pms_graphql`): 期限切れ=`SessionExpiredError(expired, 401)`、不正=`SessionExpiredError(invalid, 403)`、セッションを破棄=`SessionExpiredError(missing)`(通信しない)、JWT なし(匿名)=`PermissionDeniedError`、認証サーバーに接続できないだけ=`NetworkError`。

## 実行
資格情報・鍵は実行時に `--dart-define` で渡す(コード・Git には書かない)。詳細は [doc/contents/usage.md](doc/contents/usage.md)。

## 規則(このプロジェクト固有)
1.  サーバーは検証用で、書き込み・変更は自由。ただし、テストは自分が作ったもの(`jwt.test.…` の利用者)だけを作り、最後に削除する。
1.  Docker(`tools/docker`)のファイルは、指示があるまで変更しない。必要な変更は実施ログに提案として残す。
1.  ログインは同一 IP で 1 分 10 回までの制限がある(PocketBase)。続けて実行するときは 1 分以上あける。1 回の実行で使うログインは、`pocketbase_jwt_test` が 5 回、`model_session_test` が 4 回、`mutation_session_test` が 4 回。
1.  報告・ログには、サーバーを主語にする(「PostGraphile」「PocketBase」のどちらかを明記する)。
1.  モデルを追加したら `test/support/model_probes.dart` に読み込みの問い合わせを 1 つ足す。

##  規則
1.  ディリクトリ/ファイル
    1.  生成結果のレポートは`doc/log`ディリクトリにファイル名`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  同じ年月日、同じ番号に対する追加変更は`年月日_4桁ゼロ埋の番号_add_1からの連番.md`として保存する。
    2.  生成したライブラリに関する使い方やヘルプなどの使用にかかわるレポートは`doc/contents`の保存する。
    3.  最終的にこの`CLAUDE.md`へ統合される追加、変更の指示は`issue`ディリクトリに`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  つまり`生成結果のレポート`と連動する。
        2.  `CLAUDE.md`への統合も指示に含める。統合時、削除指示が無い限り`issue`ディリクトリ`doc/log`ディリクトリの中を削除しない。`CLAUDE.md`には変更や追加、削除であることについて記録しない(生成時に`issue`ディリクトリ`doc/log`ディリクトリを参照するため)。
    4.  細分化した機能別に`lib/`以下のディリクトリを2階層を限度(`lib/xxx/xxx`)として分ける。細分化の程度は、2階層になる程度の抽象度とする。
        1.  細分化する機能が少ない(5以下)のとき、1階層で良い(`lib/xxx`)。
2.  命名規則
    1.  ファイル名、クラス名など名前付けのルールはFlutterの規則、慣例に従う。
    2.  クラス名はデザインパターンがわかる、または意味が通る英語の名詞とする。ただし、`はい/いいえ`のような`isXxxx`などの`is/as/has`の慣例を優先する。
        1.  `Command`などデザインパターンのみの名前だと誤解や衝突を招くため、機能、動きの名詞化したものと組み合わせる。
    3.  プリフィクスにライブラリ名をつけない(BatonLibXXのような)。
3.  バレルファイルを使用する
    1.  バレルファイルにまとめ、このライブラリを使用する側は1行を読み込むだけで解決できるようにする。ただし、相互に関連が無い独立した機能の場合はバレルファイルを分けて、仕様側が機能に応じて選択できるようにする(例えば、ファイル参照機能と計算機能があり、計算機能がファイル参照を行わない場合は別々にする)。ただし、ユーザーの使用体験を優先する。ライブラリ全体の機能が少ない(10以下)ときにインポートするファイルを分ける必要はない。
4.  インスタンスのJSON化
    1.  生成するこのライブラリのインターフェイス、クラスのインスタンスをJSONにコンバートできる。ただし、エラー追跡のためであり、現時点で機能を復元する目的では使用しない。
5.  ログを残す
    1.  ライブラリは実行したときのログを残す。ただし、このライブラリ側のエラーログだけを残し、実行側のアプリケーションがどの実行でエラーが発生したか調査するとき、機能毎のライブラリ側なのかを切り分け可能にするために、適切に選別する。
    2.  ロガーはRiverpodから提供され、アプリケーション全体をとおして同じ仕様のログ出力を行う。
6.  GOFデザインパターン
    1.  クラス名やファイル名にデザインパターンを含めない場合は、コメントに該当するパターン名を追加する。
    2.  必ずしもデザインパターンに割り当てる必要はない。
