# 0042 実施ログ(生成・テストの最小分割実行、ハングアップ監視ポリシー)

## 指示

> 生成およびテストは、結合を除き最小サイズに分割して順次行う。実行時はタスクのハングアップを
> 10分間隔で監視し、状態を評価する。停止状態と判断した場合は、ハングアップなど進行を阻害する
> 原因を調査し、権限の範囲で除去(タスクキルなど)し、再評価を行う。

要件0041実施中に発生した2件の実問題(build_runnerの`_writeBuildOutput`クラッシュ、
`flutter test`の90分ハング)を踏まえ、今後の`build_runner`・`flutter test`実行に
適用する標準運用として明文化されたもの。ファイルの変更を伴わない、作業方針の要件のため、
本ログのみを記録として残す。

## 適用方針(以降のbuild_runner・flutter test実行に適用)

1. **最小分割**: `build_runner build`・`flutter test`は、複数ターゲット/複数テストファイルを
   1コマンドにまとめず、画面単位・ファイル単位など最小サイズに分割して順次実行することを
   基本とする。「結合を除き」とあるとおり、`schema.graphql.dart`単体のように結合が本質的に
   不要な単位はまとめて構わないが、複数の独立した画面・テストファイルを1コマンドに
   まとめることは避ける(要件0041で、複数ターゲットの結合実行がbuild_runnerの書き込み
   クラッシュの引き金になったことを踏まえる)。
2. **10分間隔でのハングアップ監視**: バックグラウンド実行したタスクは、10分間隔で状態を
   確認する(`ScheduleWakeup`等で定期的に見に行く。タスク完了通知が来ればそれに従うが、
   通知が来ないまま10分経過した場合は能動的に状態を確認する)。
3. **停止状態の判定**: 出力が更新されない・プロセスのCPU使用時間が一定時間(目安10分)
   変化しない、といった兆候が見られた場合はハングアップと判断する
   (`Get-Process`でCPU使用時間を2回以上の時点間で比較する。要件0041で実際にこの方法で
   `flutter test`のハングを検知した)。
4. **原因調査・除去・再評価**: ハングアップと判定した場合、まず原因を調査する
   (要件0041では、放置された古いdart/dartvmプロセスが新しいコンパイルプロセスと
   干渉していたことが判明した)。権限の範囲内(タスクキル、プロセスの強制終了等)で
   原因を除去したうえで、対象のタスクを再実行し、再評価する。
