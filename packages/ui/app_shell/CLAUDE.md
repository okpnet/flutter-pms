# app_shell

アプリ全体の枠(タイトルバー・サイドバー・ハンバーガーメニュー・ログインユーザー)の見た目の部品。`packages/features/CLAUDE.md` の「アプリの枠(app_shell)とメニュー」に従う。
機能・認証の実体は知らない。表示する項目、権限の判定、ユーザー情報は、呼び出し側(`apps/pms_app`)が渡す。

## 構成
| 部品 | ファイル | 内容 |
|---|---|---|
| メニューのモデル | `lib/src/menu_model.dart` | `AppMenu`・`AppMenuGroup`・`AppMenuItem`、`AppUser`・`UserMenuAction` |
| タイトルバー | `lib/src/title_bar.dart` | `AppTitleBar`(ロゴ・タイトル・モバイルのハンバーガー・ユーザー) |
| ログインユーザー | `lib/src/user_container.dart` | `UserContainer`(顔写真・名前・役割・ユーザーメニュー) |
| サイドバー | `lib/src/side_bar.dart` | `SideBar`(通常 248、アイコンだけ 72) |
| ハンバーガー | `lib/src/hamburger_menu.dart` | `HamburgerMenu`(サイドバーと同じメニューを共有。項目を選ぶと閉じる) |
| 画面の骨組み | `lib/src/screen_scaffold.dart` | `ScreenScaffold`・`ScreenTitle`(機能の画面用。AppBar を使わない見出し + 本体。戻れるときは戻るボタン) |
| フレーム | `lib/src/main_frame.dart` | `MultiMainFrame`・`SingleMainFrame`・`SelectionFrame` |
| 文字列 | `lib/src/app_shell_labels.dart` | `AppShellLabels`(呼び出し側が言語ごとに渡す) |

## 振る舞い
1.  画面の幅は `view_responsiveness` の `MediaBreakPoint` で判定する。モバイル=ハンバーガー(サイドバーは非表示)、タブレット=アイコンだけ、PC=通常。設定(`sidebarIconOnly`)が有効のときは PC でもアイコンだけ。
2.  ユーザー(`AppUser`)が null(ログインしていない・権限が無い)のときは、サイドバーもハンバーガーもユーザーも出さない。
3.  色・サイズは `Theme`(`theme_lib`)に従う。

## 実装の指針
1.  表示する文字列は引数で受け取る(`AppShellLabels` とメニューのモデル)。この部品自身は多言語の仕組みを持たない。
2.  メニューの項目の集め方(各機能の `MenuContributor`)は `feature_shared`、グループの並び・アイコンはアプリが決める。

## 規則/仕様
1.  ディリクトリ/ファイル
    1.  生成結果のレポートは`doc/log`ディリクトリにファイル名`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  同じ年月日、同じ番号に対する追加変更は`年月日_4桁ゼロ埋の番号_add_1からの連番.md`として保存する。
    2.  画面イメージ(HTML)や使い方などは`doc/contents`に保存する。
    3.  最終的にこの`CLAUDE.md`へ統合される追加、変更の指示は`issue`ディリクトリに`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  つまり`生成結果のレポート`と連動する。
        2.  `CLAUDE.md`への統合も指示に含める。統合時、削除指示が無い限り`issue`ディリクトリ`doc/log`ディリクトリの中を削除しない。`CLAUDE.md`には変更や追加、削除であることについて記録しない(生成時に`issue`ディリクトリ`doc/log`ディリクトリを参照するため)。
2.  命名規則
    1.  ファイル名、クラス名など名前付けのルールはFlutterの規則、慣例に従う。
    2.  クラス名はデザインパターンがわかる、または意味が通る英語の名詞とする。ただし、`はい/いいえ`のような`isXxxx`などの`is/as/has`の慣例を優先する。
        1.  `Command`などデザインパターンのみの名前だと誤解や衝突を招くため、機能、動きの名詞化したものと組み合わせる。
    3.  プリフィクスにライブラリ名をつけない(BatonLibXXのような)。
3.  バレルファイルを使用する
    1.  バレルファイルにまとめ、このライブラリを使用する側は1行を読み込むだけで解決できるようにする。ただし、相互に関連が無い独立した機能の場合はバレルファイルを分けて、仕様側が機能に応じて選択できるようにする。ただし、ユーザーの使用体験を優先する。ライブラリ全体の機能が少ない(10以下)ときにインポートするファイルを分ける必要はない。
4.  インスタンスのJSON化
    1.  生成するこのライブラリのインターフェイス、クラスのインスタンスをJSONにコンバートできる。ただし、エラー追跡のためであり、現時点で機能を復元する目的では使用しない。
5.  ログを残す
    1.  ライブラリは実行したときのログを残す。ただし、このライブラリ側のエラーログだけを残し、機能毎のライブラリ側なのかを切り分け可能にするために、適切に選別する。
    2.  ロガーはRiverpodから提供され、アプリケーション全体をとおして同じ仕様のログ出力を行う。
6.  GOFデザインパターン
    1.  クラス名やファイル名にデザインパターンを含めない場合は、コメントに該当するパターン名を追加する。
    2.  必ずしもデザインパターンに割り当てる必要はない。
