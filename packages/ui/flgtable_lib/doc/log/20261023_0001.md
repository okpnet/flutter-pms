## 5. 追記: 親の付け替えによる循環(無限ループ)リスクの評価

### 5-1. リスクが起きる条件の整理
循環とは、動かす行 N を、N の子孫 D の子にしてしまうこと(N→…→D→N)。ドロップ時に「ドロップ先 D が N の子孫か」を判定できれば防げる。判定に使える情報は表示状態によって変わる。

| 状態 | D の祖先を画面が知っているか | 判定 |
|---|---|---|
| 通常(フィルタなし)の木 | 知っている。D が表示されている=D の祖先は全て展開済みで、画面上の親の連鎖(`parent`ポインタ)を持つ | 連鎖を上にたどって N に当たれば循環。費用はゼロ(深さ分)で、正確 |
| フィルタ有効(R-6 の平坦表示) | 知らない。全ヒット行がトップノード扱いで、実際の祖先関係が画面にない | 画面だけでは判定できない。リスクはここだけ |
| データ自体が既に循環している/他者が同時に付け替えた(古い表示) | 画面の連鎖は古い | 画面では検知できない。最終防衛はデータ側 |

つまり、通常の木では「ドロップ時に全ての子を展開して調べる」(指示の案1)は不要で、表示されている祖先の連鎖を見るだけでよい。コストの高い判定が必要なのはフィルタ有効時だけである。

### 5-3. 推奨する組み合わせ

1. 通常の木: A を常に実施。N 自身、N の子孫の上へのドロップは受け付けない(ホバー中も背景色を変えない)。
2. 展開時: F を実施。循環したキーの行は追加せず、`[flgtable]`接頭辞のエラーログを残す。
3. フィルタ有効時:
   1. 判定用デリゲート`TreeCycleChecker<T>`が渡されていれば、ドロップ時に1回だけ呼ぶ。`Future<bool> Function(T node, T newParent)`で、「newParent は node の子孫か」を返す。真なら拒否し、`TableLabels`の文言(「子孫の下には移動できません」)で通知する。ホバー中は判定しない(中立表示)。
   2. 渡されていなければ E: フィルタ有効中はドラッグ自体を無効にする。
4. 判定に失敗した(例外、タイムアウト)場合は安全側で拒否し、エラーログを残す。
5. 動かす位置が現在の親と同じ(結果が変わらない)ときは、イベントも通知しない。
6. 静的リスト(`items`渡し、メモリ上)向けに、`TreeCycleChecker`の既定実装(親キーの対応表をたどる)を提供する。GraphQL 等の外部読み込みはアプリが C を実装する。
7. G(データ側の検証)は、ライブラリでは保証できないので、`doc/contens`と CLAUDE.md に「付け替えの最終検証はアプリ(データ側)の責務」と記載する。

### 5-4. この方針で変わる点
- `rowKey`がツリーでは必須になる(連鎖の比較に使うため。オブジェクトの同一性ではなくキーで比較)。
- `TableLabels`に拒否時の文言を1つ追加する。
- R-6 の平坦表示では、付け替え後も、動かした行はフィルタに合致している限り一覧に残る(移動先の子数だけ更新し、移動先は展開しない)。移動先を展開すると同じ行が子としても表示されるため、重複して見える点は仕様として許容してよいか。
