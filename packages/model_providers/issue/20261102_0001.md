### アクセス管理の方針
2026年11月3日 · @Hayato Takahashi
目的と基本の考え方
権限は部署に付け、所属する担当者がそれを受け継ぐ。個人ごとの許可は、部署の権限に足すためだけに使う。
• 権限の単位はアクセスパス（画面・ユースケースごとの info_access_path）。
• 部署に付ける：部署ごとに、使えるアクセスパスと書き込みの可否を登録する。
• 所属で受け継ぐ：担当者は、有効な所属（info_assign）の部署の権限をすべて受け継ぐ。
• 個人で足す：所属部署にないアクセスパスや書き込み権限は、担当者ごとに追加する。
• 上位部署からは受け継がない：部署の権限はその部署の所属者だけに効く。

権限の決まり方
担当者が使えるアクセスパスは、「有効な所属部署のアクセスパス」と「個人の許可」を合わせたもの。どちらかで書き込み可なら、書き込める。
1. 所属部署から受け継ぐ：info_assign.enable = true の所属だけを使う。所属を無効にすると、その部署の権限は即座に外れる。
2. 部署の書き込み：部署アクセスパスの write が true なら読み書き、false なら読み取りだけ。
3. 個人の許可を足す：担当者アクセスパス許可は、登録したアクセスパスを読み取れるようにし、write が true なら書き込みも許す。
4. 合わせ方：同じアクセスパスが複数の部署・個人の許可にあれば 1 行にまとめ、書き込みはどれか一つでも可なら可（OR）。
5. 削除済みは使わない：部署・担当者・アクセスパス・各許可のうち remove = true のものは数えない。
6. 上位部署からは受け継がない：info_department_tree の親部署の権限は、子部署の所属者には効かない。

運用ルールと今後の課題
日常の権限変更は部署と所属で行い、個人の許可は例外に限る。
場面
やること
新しい画面を追加
アクセスパスを登録し、使う部署に部署アクセスパスを付ける
配属・異動
所属を追加し、元の所属は enable = false にする（履歴が残る）
部署では足りない権限
担当者アクセスパス許可を追加する
退職
担当者を remove = true にすると、すべての権限が外れる
画面の廃止
アクセスパスを remove = true にする
課題（未対応）
• 個人で権限を減らせない（対応方針あり）：個人の許可は足すだけ。特定の人から部署の権限を外すときは、その人の所属を enable = false にする。その部署の権限はまとめて外れるので、残したいアクセスパスは個人の許可で足し直す。
• DB側での強制がない：今はアプリが画面の表示と編集を切り替えるだけ。PostGraphile を直接呼ぶと、権限に関係なく読み書きできる。

### ページアクセス管理画面の追加
以下のページの仕様を`flutter-pms\packages\features`のIssueへ追加、実行する。提案はログにまとめる。また、ページに該当するview、Yaml、モデルを生成する。該当するプロジェクトが無い場合はプロジェクトを[認証](#認証)とあわせて生成する。プロジェクトを生成する場合には当該プロジェクトに`CALUDE.md`の追加、規則を追加する。このモデル生成が完了した後にIssueを実行する。
1.  ページアクセスの追加/変更/削除
    1.  ページのパスをもつ、アクセス権限。これがページ遷移有効無効が決定する。
1.  部署の有効なアクセス権管理
    1.  部署がアクセスできるページを追加/変更/削除を決定する
1.  担当者へ追加のアクセス権管理
    1.  `部署の有効なアクセス権管理`で決定した所属する部署のアクセス権を除き、個別に対応できるページの有効/無効/削除を管理
