# 棚ビジターの数量を一本化し、取り出し可否・異常の保留をDBで判定する
viewの名前は適宜読み替えしてください。schemaを更新しました。

**対象:** PMS GraphQL(PostGraphile)・画面クエリ・ScanClient
**関連ファイル:** `claude/117_ddl_change.sql` / `claude/117_visiter_ledger_views.txt` / `claude/117_08_mrp_patch.sql`、修正版 `08_mrp.sql` / `10_mrp_dummy.sql` / `11_barcode_dummy.sql`
**種別:** 設計変更(破壊的変更を含む)

---

## 1. 背景

- 異常(`trans_complaint`)が付いた製品・購入品を、棚から取り出せる一覧から外す必要があった。
- 検討の途中で、数量が4か所(棚ビジター・受入実績ビジター・作業実績ビジター・受払実績)にあることが問題の根本だと分かった。
  - 例: 受入実績10に対して、受入実績ビジターも棚ビジターも10。どの合計を正とするかが使う人によって変わる。
  - 製造への払出を作業実績ビジターのマイナス行で記録すると、材料の在庫が製品側の品目に引かれ、現在庫から落ちていた。

## 2. 決定した方針

| # | 方針 |
|---|---|
| 1 | **数量は棚ビジター(`trans_visiter.quantity`)だけが持つ。** ＋が入庫、−が出庫 |
| 2 | 受入実績ビジター・作業実績ビジターは**数量の無い中間テーブル**(つなぐだけ) |
| 3 | 受払実績(`trans_convey`)は**出来事(いつ・どこで・誰が)だけ**を記録し、数量・受入区分を持たない。棚ビジターの1行につき1件 |
| 4 | 出庫・分割は、棚ビジターに**親(`parent_trans_visiter_id`)**を付けて表す |
| 5 | 帳簿と現品が合わないときは、**棚卸しの調整行**(`adjustment = true`)を追加して合わせる |
| 6 | 異常は中間テーブル `trans_complaint_visiter` で棚ビジターにつなぎ、解除日・許可者を持つ |
| 7 | 異常が見つかった品は、**別の棚(隔離棚)に移して保留**するのが通常の運用 |
| 8 | 止める単位は**在庫(ロット)全体**。一部だけ不良でも、ロット全体を止める |
| 9 | 人が異常の登録を忘れることがあるので、**登録漏れを拾うビュー**とマスタ点検で知らせる |
| 10 | 取り出し可否の判定はDBに一本化する(`ScanClient.listVisiters` の判定を置き換えられる) |

### 用語

- **在庫(ロット):** 棚ビジターのうち `quantity > 0` かつ `adjustment` でない行。保留・異常・取り出し可否はこの単位に付く
- **今の数量:** ロットの数量 ＋ そのロットを親に持つ出庫行と棚卸し行の合計
- **分割元:** 親をたどった先のロット。品目、受入実績・作業実績とのつながり、異常は分割元から引き継ぐ

## 3. 棚ビジターの行の作り方(アプリ・ScanClientが守る決まり)

| 操作 | 作る棚ビジターの行 | つなぎ |
|---|---|---|
| 受入 | ＋(親なし)。棚があふれたら＋を2行(棚ごと) | 受入実績ビジター → 受入実績 |
| 作業完了 | ＋(親なし) | 作業実績ビジター → 作業実績 |
| 払出・出荷 | −(親 = 取り出したロット、棚 = 親と同じ) | ― |
| 製造への材料投入 | −(親 = 材料のロット) | 作業実績ビジター → 作業実績(投入先) |
| 移動・分割 | 元の棚に−(親 = 元のロット) ＋ 移動先に＋(親 = 元のロット) | ― |
| 隔離・保留 | 移動と同じ。移動先の＋の行を `release = false` にする | 異常があれば `trans_complaint_visiter` |
| 棚卸し | ＋または−(親 = そのロット、`adjustment = true`) | ― |

- どの行にも、受払実績(`trans_convey`)を1件ずつ作る(いつ・どこで・誰が)。
- 制約: 数量0の行は作れない。出庫と棚卸しの行は親が必須(`trans_visiter_CK1`)。
- 分割先に、受入実績・作業実績のつなぎを写す必要はない(親をたどって求める)。

> **TODO(提案):** 移動・分割は2行と受払実績をまとめて作るので、1つのDB関数にすると原子性と決まりの順守が保証できます。例: `visiter_move(p_src, p_container, p_qty, p_hold boolean)` / `visiter_issue(p_src, p_qty, p_work_record)`。必要なら別Issueで作ります。

## 5. GraphQLへの影響

> フィールド名は PostGraphile v4 の既定の inflector で書いています。simplify inflector を使っている場合は `allVVisiterIssuables` → `vVisiterIssuables` のように読み替えてください。

### 5-1. 破壊的変更

| 対象 | 変更内容 | 対応 |
|---|---|---|
| `TransConvey` | `quantity`, `receive` が無くなる | 受払実績の登録・表示から外す。数量は `transVisiterByTransVisiterId { quantity }` |
| `TransPurchaseRecVisiter` / `TransWorkRecordVisiter` | `quantity` が無くなる | 数量はつながっている棚ビジターから取る |
| `TransVisiter` | `parentTransVisiterId`, `adjustment` が増える。`quantity` が符号付きになる | 一覧に「今の数量」を出すなら `VVisiterLot.quantity` を使う |
| `VShelfInventoryStatus`(棚在庫状況) | 1行 = ロット。`purchaseRecQuantity` / `conveyReceiveQuantity` / `conveyIssueQuantity` / `workRecordQuantity` が無くなる | `receiptQuantity` / `issueQuantity` / `adjustmentQuantity` / `quantity`(今の数量)に置き換える |
| `VVisiterQuantityCheck` | 削除 | `VVisiterLedgerIssue` / `VVisiterOriginCheck` を使う |
| `VItemOnHand` | `heldQuantity`, `availableQuantity`, `heldVisiterCount` が増える | MRP は `availableQuantity` を使う |

### 5-2. 追加・変更したビュー(`117_visiter_ledger_views.txt`)

| ビュー | 1行 | 主な列 | 用途 |
|---|---|---|---|
| `v_visiter_lineage` | ロット × 分割元(自分を含む) | `ancestorVisiterId`, `depth` | 分割元をたどる(ほかのビューの土台) |
| `v_visiter_lot` | ロット | `receiptQuantity`, `issueQuantity`, `adjustmentQuantity`, `quantity`, `splitCount`, `openComplaintCount` | ロットの今の数量 |
| `v_visiter_issuable` | ロット | `issuable`, `blockReason`(`hold` / `complaint` / `empty`), `openComplaintCount` | **払出候補の取得**(`issuable: true` で絞る) |
| `v_visiter_hold_without_complaint` | ロット | `holdAt`, `quantity` | 仮止めなのに異常が無いロット(異常の登録を促す) |
| `v_visiter_ledger_issue` | 行の不備 | `issueKind`(`negative_balance` / `orphan_line` / `invalid_parent` / `container_mismatch` / `zero_line`) | 帳簿の不備の点検 |
| `v_visiter_origin_check` | 受入実績・作業実績 | `recordQuantity`, `visiterQuantity`, `difference` | 伝票数量と入庫の行の合計の不一致 |
| `v_complaint_target_visiter` | 異常の対象 × ロット | `targetKind`, `linked`, `visiterStatus` | **異常の登録漏れの一覧**(`linked: false`) |
| `v_complaint_target` | 異常の対象 | `missingCount`, `missingIssuableCount`, `missingEmptyCount` | 異常ごとの漏れの件数 |
| `v_mrp_visiter_item` | ロット | `itemId`, `itemCount`, `finished`, `held` | 品目の判定(MRP用) |
| `v_item_on_hand` | 品目 | `onHandQuantity`, `heldQuantity`, `availableQuantity` | 品目別の現在庫 |
| `v_shelf_inventory_status` | ロット | 上記 ＋ `consumedWorkRecordIds`(投入先の作業実績) | 棚在庫状況(87 の改訂) |
| `v_complaint_complaint_visiter_count` / `v_visiter_complaint_visiter_count` | 異常 / 棚ビジター | `enableCount` ほか | 子テーブルの件数(115) |

判定の要点:

- `issuable = release IS TRUE AND openComplaintCount = 0 AND quantity > 0`
- `openComplaintCount` には、**分割元に付いた未解除の異常も含む**。隔離前のロットに異常を付けても、分割先が自動で止まる。
- 受入異常・作業異常(`trans_complaint_purchase_rec` / `trans_complaint_work`)は自動では止めない。そこから作られたロット(分割先を含む)に異常が付いていなければ、`v_complaint_target_visiter` で漏れとして出る。

### 5-3. クエリ例

```graphql
# 払出候補 (棚・品目で絞る)
query Issuable($container: UUID!) {
  allVVisiterIssuables(condition: { transContainerId: $container, issuable: true }) {
    nodes { transVisiterId quantity
            vMrpVisiterItemByTransVisiterId { mstrItemByItemId { code } } }
  }
}

# 取り出せない理由つきの棚一覧
query Shelf($container: UUID!) {
  allVVisiterIssuables(condition: { transContainerId: $container }) {
    nodes { transVisiterId quantity issuable blockReason openComplaintCount }
  }
}

# 異常の登録漏れ (取り出せてしまうものを先に)
query ComplaintMissing {
  allVComplaintTargetVisiters(filter: { linked: { equalTo: false }, transVisiterId: { isNull: false } },
                              orderBy: VISITER_STATUS_DESC) {
    nodes { transComplaintId targetKind transVisiterId visiterQuantity visiterStatus }
  }
}

# 品目別在庫 (現在庫 / 保留 / 使える)
query OnHand { allVItemOnHands { nodes { itemId onHandQuantity heldQuantity availableQuantity } } }
```

## 6. MRP・マスタ点検(08)の変更

- `v_mrp_visiter_item` と `v_item_on_hand` は 06 側(A5ER)に移した。08 では定義しない。
- `mrp_issued`(払出済み数量)は、受払実績 → 出庫の行(−)の数量で数える。
- `mrp_run` の現在庫は `v_item_on_hand.available_quantity` を使う。保留中・未解除の異常のロットは計画に使わず、解除されれば次の再MRPで使われる。
- `mrp_commit` の「計算後の更新チェック」に `trans_complaint_visiter` を追加した。
- マスタ点検(`v_mrp_master_issue` / `mrp_check_items(NULL)`)に次の項目を追加した。

| コード | 重要度 | 内容 |
|---|---|---|
| `VISITER_HOLD_NO_COMPLAINT` | 警告 | 仮止めなのに異常が無い |
| `VISITER_NEGATIVE_BALANCE` | エラー | ロットの今の数量がマイナス(出しすぎ) |
| `VISITER_ORPHAN_LINE` | エラー | 出庫・棚卸しの行の親がロットではない |
| `VISITER_INVALID_PARENT` | エラー | 分割先の親がロットではない |
| `VISITER_CONTAINER_MISMATCH` | 警告 | 出庫行の棚が親のロットの棚と違う |
| `VISITER_ZERO_LINE` | 警告 | 数量0の行 |
| `VISITER_ORIGIN_MISMATCH` | 警告 | 受入実績・作業実績の数量と入庫の行の合計が違う |
| `VISITER_COMPLAINT_MISSING` | 取り出せる状態ならエラー、それ以外は警告 | 受入異常・作業異常の対象から作られたロットに異常が無い |

※ `mrp_check_items(品目ID)` は従来どおり棚ビジターの項目を除くので、上記は全件の点検とマスタ点検画面にだけ出る。
