## 提案(2): DB の変更

DB のテストではなく、**ビュー2本の新規と、既存ビュー1本の変更**。いずれも DB の Issue(`tools/docker/postgresql/issue/`)として、テーブルの変更は伴わない。

### A. `v_visiter_issuable`(新規ビュー): 取り出し可否

1行 = 棚ビジター(`remove` が偽)。`ScanClient.listVisiters` と同じ判定を DB に一本化する。

| 列 | 内容 |
| --- | --- |
| `trans_visiter_id` | 主キー |
| `trans_container_id`, `quantity`, `release` | 棚ビジターの値 |
| `open_complaint_count` | `trans_complaint_visiter` のうち `release_at IS NULL` かつ `remove` が偽の件数 |
| `issuable` | `release IS TRUE AND open_complaint_count = 0 AND quantity > 0` |
| `block_reason` | 取り出せない理由(`hold`=仮止め / `complaint`=未解除の異常 / `empty`=数量0) |

用途: 払出の候補の取得(`issuable` で絞る)、画面の表示、`ScanClient` の判定の置き換え(実装は `listVisiters` のままでも結果は同じ)。

### B. `v_visiter_hold_without_complaint`(新規ビュー): 点検用

仮止め(`release = false`)なのに、未解除でも解除済みでも異常が1件も登録されていない棚ビジター。「異常の登録を後から促す」一覧で、マスタ点検(`mrp_check_items`)の1項目として出す。実機の確認用データは `11_barcode_dummy.sql` の「異常の登録が無い保留」1件。

### C. `v_mrp_visiter_item`(既存ビューの変更): マイナスの行を除く

- 作業実績経由の品目決定で、`trans_work_record_visiter.quantity < 0`(払出の行)を除く。払出の行が付いても材料の棚ビジターの品目が製品側に引かれず、`v_item_on_hand` から落ちない。
- 合わせて `v_item_on_hand` から、`release` が偽、または未解除の異常がある棚ビジターを除くか(現在庫から外す)、別の列(`held_quantity`)にするかを決めてほしい。**推奨: 別の列**(在庫の実数は変わらず、使えない量が見える)。

### D. 在庫の整合の検査(`v_visiter_quantity_check`、新規ビュー)

棚ビジターの `quantity` と、行の合計(受入 + 作業実績の入庫行 − 払出行)を並べ、不一致の棚ビジターを返す。「入庫+/出庫−の合計で在庫を把握する」方針を、`quantity`(現在量)と矛盾させないための検査。マスタ点検の1項目にもする。

### 実施の順序

C → A → B → D(C が在庫の数字に効く)。決まれば、`11_barcode_dummy.sql` に払出の行(マイナス)を持つデータを足し、各ビューの読み込み(`gql/*.yaml`)と実機テストを追加する。
