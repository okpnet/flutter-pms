## 方針の評価(issue 3: 棚に対する異常処理)

提案された方針(取り出せる条件 = `release` が真、かつ中間テーブルに `release_at IS NULL` の行が無い。まず `release = false` で仮止めし、異常は後から登録する。隔離棚への移動では新しい棚ビジターに中間テーブルの行をコピーする)は適切。次の点を補足する。

1. **判定を1か所にまとめる。** 「取り出せる棚ビジター」の判定は、画面ごとに条件を書かず、DB のビュー(例: `v_visiter_issuable`、取り出し可否と理由を持つ)にする。`release` と中間テーブルの2つの情報から決まるため、書き方が揺れると払出の可否がずれる。
2. **点検用のビューも用意する。** 「`release = false` なのに未解除の異常が無い棚ビジター」(仮止めのまま異常が未登録)を返すビューを、マスタ点検(`mrp_check_items`)に加える。これで「すぐ止める」と「記録を必ず残す」が両立する。
3. **逆の状態の扱い。** `release = true` なのに未解除の異常がある場合は「取り出せない」にする(異常を優先)。異常を解除(`release_at` を設定)しても `release` は自動で真に戻らないので、解除の操作で `release` も真にするか、`release` は手動の仮止めだけに使うかを決める。推奨は後者(`release` = 手動の仮止め、異常 = 中間テーブル)で、判定はビューで両方を見る。
4. **移動時のコピーの規則。** 全数を隔離棚へ移すときは、元の棚ビジターの行は残す(履歴の追跡)。数量が0になった元の棚ビジターは、払出可否の判定の対象外(数量0)にする。一部だけ移すときは、異常数量(`quantity`)も新旧に按分して持つ。
5. **在庫の集計との関係(DB の変更が必要)。** `v_item_on_hand` は `release`・異常を見ていない。保留・異常の在庫を「現在庫」から除くか、別の列(保留在庫)にするかを決めて、ビューを変更する。

## 払出をマイナスの行で表す方針の影響調査(issue 1)

方針: 払出は `trans_work_record_visiter` に行を追加する。入庫はプラス、出庫はマイナスにして、合計で在庫量を把握する。DB の定義(`06_cteate_test.sql`・`08_mrp.sql`)を調べた結果は次のとおり。

| ビュー | 影響 |
| --- | --- |
| `v_mrp_visiter_item`(品目の決定) | **問題あり。** 作業実績経由の品目は「作業指示 → 資材計画の品目」(作る側の品目)で決める。払出の行を、材料を使う側の作業実績に付けると、材料の棚ビジターの品目が「作る製品の品目」にもなり、品目が2種類(`item_count = 2`)になる。結果、この棚ビジターは `v_item_on_hand` の現在庫に数えられなくなる |
| `v_item_on_hand`(品目別現在庫) | 数量は `trans_visiter.quantity`(棚ビジターの現在量)の合計で、行の合計ではない。行の合計を在庫とするなら、`quantity` を更新し続けるか、ビューを行の合計に変える必要がある |
| `v_shelf_inventory_status`(棚在庫状況) | `work_record_quantity` は行の合計(`SUM`)なので、マイナスが入れば相殺される。意図どおり。`convey_issue_quantity`(搬送の払出の数量)は別の列で、二重に数えない注意が要る |
| `v_*_count`(件数) | 件数は変わらない(払出の行も1件) |
| `trans_convey`(搬送) | **既に受け払いの台帳。** `receive` が真なら入庫、偽なら出庫で、数量は正の値。方針の「入庫+/出庫−」に最も近い |

提案(DB の変更。この Issue では行わない):

1. 払出の行には、材料を使う側の作業実績を付けつつ、`v_mrp_visiter_item` は **数量がマイナスの行を品目の決定から除く**(払出の行は品目の根拠にしない)。
2. 在庫量は **棚ビジターの行の合計**(受入 + 作業実績の入庫 − 出庫)として、`trans_visiter.quantity` との一致を検査するビューを用意する。一致しない棚ビジターはマスタ点検に出す。
3. 払出の行と搬送(`trans_convey`、`receive = false`)を二重に登録しない。払出は行の追加を正とし、搬送は棚の移動(コンテナ間)に使う。

この決定が済むまで、`WorkRecordVisiterPageCreate` を払出の数量マイナスで使うのは保留とする(機能側で払出を実装する前に、DB のビューの変更が必要)。

## 設備点検(issue 4)

- 対象の明細は、設備の `trans_inspect_sch`(`ScanInspectSchPage`、設備 id で絞る)→ 明細(`ScanInspectSchDetailPage`、`scheduled_start_date` が今日以前)→ 結果(`ScanInspectRecordPage`、明細 id で絞り、無い明細だけを残す)の順に、最も古い1件を選ぶ。点検項目・式は `ScanInspectionPage`・`ScanInspectionFormulaPage` で引く。
- 結果の登録は `InspectRecordPageCreate`(`result`・`result_state`・`result_value`(JSON)・実施の開始/終了)。`result_value` は式ごとの入力値の JSON。式は `formula_class`(`=,<>,>,<,>=,<=,IN,NOT IN`)と `arg_class`(JSON)で持つ。**`arg_class` の形は仮**(ダミーデータでは `{"operator":"<=","value":0.5}`)で、画面側の定義が決まったら合わせる。
- 設備 → 点検予定 → 明細の関連は外部キーが複合(履歴 id + id)のため、入れ子で読めない。そのため上のとおり複数回の照会で組み立てる(`ScanClient` へ追加する作業)。
