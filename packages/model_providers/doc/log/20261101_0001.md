# 20261101_0001 バーコード実績登録の未対応事項:決める必要のある情報の提案

対応する指示: [issue/20261101_0001.md](../../issue/20261101_0001.md)(元: `packages/features/barcode_entry/issue/20261031_0003.md`)

モデル・コードは変更していない。DB の構成(`.schema/schema.graphql`、`08_mrp.sql`)と検証用サーバーの実データを読み取りだけで調べ、決めてもらう項目と推奨案をまとめた。

## 調べた事実

- `trans_visiter`(棚ビジター)は 棚(`trans_container_id`)・`status`・`quantity` だけで、品目の列を持たない。品目は `v_mrp_visiter_item`(`08_mrp.sql`)が次の2経路からたどって決めている。
  - 受入: `trans_purchase_rec_visiter` → `trans_purchase_rec` → `trans_purchase_detail.item_id`(その発注明細に作業指示が無いとき。`finished` = 真)
  - 作業実績: `trans_work_record_visiter` → `trans_work_record` → `trans_work_plan` → 生産計画 → 資材計画の `item_id`(`finished` = その工程が最終工程のとき)
  - 品目が2種類以上、または結び付きが無い棚ビジターは、在庫(`v_item_on_hand`)に数えない。
- `trans_visiter.status` は、DB のコメントが「状態」だけで、値の定義が無い。検証用サーバーの2件は `status` が空。
- 検証用サーバーに 点検予定の明細(`trans_inspect_sch_detail`)、点検結果、点検項目マスタ、不適合(`trans_complaint`)、作業指示(`trans_work_plan`)は 0 件。設備は6件ある。
- `trans_complaint` の `titles`・`details` は文書(`shared_*`)への参照で必須、`reporter_staff_*` も必須。子の `trans_complaint_work`(作業実績)、`trans_complaint_purchase_rec`(受入)が数量を持つ。

## 決めてほしいこと

推奨案は、現在の DB の作りから矛盾が少ない順に付けた。

### 1. 棚出庫(払出)

払い出す棚ビジターを、バーコードの入力からどう決めるか。

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| **A(推奨)** | 払出のとき、読み取った棚(コンテナ)の棚ビジターのうち、`v_mrp_visiter_item` で品目が作業の材料の品目と一致するものを払い出す。複数あるときは、古い順(`update_at`)に数量が足りるまで | DB の変更が無い。在庫の判定(`v_item_on_hand`)と同じ品目の決め方 | 同じ棚に同じ品目が複数あるときの順序を決める必要がある。品目が2種類以上のビジターは対象外になる |
| B | 払出するビジターのバーコード(`trans_visiter.symbol`)を直接読む | 対象が明確 | 作業者が材料ごとにビジターのバーコードを持つ運用が必要 |

不足している情報:
- 払出の取り方は A か B か。A の場合の順序(先入れ先出しか、棚の位置順か)。
- 払い出す材料(品目と数量)の出どころ。作業指示から材料の一覧(部品表)をたどってよいか。
- 払出した結果を、棚ビジターの数量の減算(`quantity` の更新)で表すか、払出の行を追加する(`trans_work_record_visiter` の使用)か。現在の DB は後者の作りに見える。

### 2. 異常(不合格)の登録

| 案 | 内容 |
| --- | --- |
| **A(推奨)** | 当面は備考(理由)に残す。`trans_complaint` の登録は、文書・報告者・承認の流れが要るため、別の画面(品質の画面)から行う。バーコード画面は「異常あり」の印だけを残す |
| B | 登録モデルを作る(`quality_model` に `ComplaintPageCreate`、文書は表題・詳細の2件を `shared_*` に登録)。バーコード画面で表題(定型文から選択)・数量・理由を入力する |

不足している情報:
- 異常の登録を、バーコード画面で行うか、品質の画面に任せるか。
- B の場合: 表題の既定値(定型文)、報告者(`ENTRY_STAFF_ID` でよいか)、承認(`approvals`)を後で付けるか。

### 3. ビジターの状態(`status`)の値

値の意味が定義されていないので、設定できていない。決めてほしい内容は次のとおり。

- 値の一覧と意味。例: `0` 通常(使用可)、`1` 保留、`2` 不合格、`3` 払出済み。
- 不合格を状態で表すなら、異常の登録(上記2)は不要になるか。
- `v_item_on_hand` は `status` を見ていない。不合格や保留の在庫を除くなら、DB のビュー側の変更も要る。

推奨は、まず値の定義を DB の列コメントに書くこと(DB の Issue)。それまで `status` は設定しない。

### 4. 設備点検

設備の symbol から、点検予定の明細(`trans_inspect_sch_detail`)のどれに結果(`trans_inspect_record`)を付けるか。

推奨ルール:
1. 設備に結び付く点検予定(`trans_inspect_sch`)の明細のうち、`scheduled_start_date` が今日以前で、結果(`trans_inspect_record`)がまだ無いものを対象にする。
2. 複数あるときは `scheduled_start_date` が最も古いものを選ぶ(画面で他を選び直せるようにする)。
3. 対象が無いときは、登録せずに「点検予定がありません」と表示する。

不足している情報:
- 上のルールでよいか。予定外の点検(臨時点検)を登録する場合の扱い。
- 設備と点検予定の結び付き(設備→点検→予定の明細)のたどり方。検証用サーバーに点検のデータが 0 件のため、実機で確認できない。**テストデータ(点検マスタ・点検予定の明細)の追加が必要**(`10_mrp_dummy.sql` の設備6件に対して)。
- 結果の入力: `result`(合否)と `result_value`(JSON)の形式、`result_state` の値。点検項目(`checkItems`)ごとに値を入れるなら、JSON の形を決める。

決まれば `resource_model` に `kind: create`(`InspectRecordPageCreate`)を追加し、点検項目は同じ明細から読み込む。

### 5. 単位

決める事項は少ない。`all_common.yaml` の `UnitReadFields`(呼称の `labels`)を `ScanItemPage` に追加すれば、画面の「個」「本」を出せる。

不足している情報:
- 表示は 正式名(`name`)か、略称(`nickname`)か。推奨は略称があれば略称、無ければ正式名。
- 言語は `JA`(CLAUDE.md の取り決めどおり)でよいか。

承認をもらえれば、そのまま追加して生成・テストまで実行できる。
