# 20261101_0003 追加: 棚ビジターの数量一本化(DB 117)への対応

## 実施

1. 本家スキーマを再取得(`gql:schema`)。`v_visiter_lot` / `v_visiter_issuable` ほかが入った。
2. YAML を新しいスキーマに合わせた(プルーナーのエラー 0 件)。
   - 数量の削除: `PurchaseRecVisiterPageCreate.quantity`、`WorkRecordVisiterPageCreate.quantity`、`ConveyPage` / `ConveyPageEdit` / `ConveyPageCreate` の `receive`・`quantity`。
   - 棚ビジターに `adjustment`・`parent_trans_visiter_id` を追加(`VisiterPage` / `VisiterPageEdit` / `VisiterPageCreate`)。
   - `ShelfInventoryStatusPage`: 1行 = ロットの列に置き換え(`receipt_quantity` / `issue_quantity` / `adjustment_quantity` / `quantity`(今の数量)ほか)。
   - `MrpVisiterItemPage`: `release`・`open_complaint_count`・`held` を追加。`ItemOnHandPage`: `held_quantity`・`available_quantity`・`held_visiter_count` を追加。
   - 新規 `work_record_model/gql/visiter_ledger.yaml`(`VisiterIssuablePage`・`VisiterHoldWithoutComplaintPage`・`VisiterLedgerIssuePage`・`VisiterOriginCheckPage`)、`quality_model/gql/complaint_target.yaml`(`ComplaintTargetVisiterPage`・`ComplaintTargetPage`)。
3. `ScanClient`
   - `createConvey` は `receive`・`quantity` を送らない。`linkWorkRecordVisiter`・`linkPurchaseRecVisiter` も数量を送らない。入庫(`putWork` / `putPurchase` / `putItem`)は、+の棚ビジター1行 + 受払実績1件。
   - `createVisiter` に `parentVisiterId`・`adjustment`・`release` を追加。
   - 新規 `issueLot`(払出・投入: 親 = ロット、棚 = 親と同じ、-の行。投入先の作業実績があれば結び付ける)、`moveLot`(移動・分割・隔離: 元の棚に-、移動先に+。`hold: true` で+の行を `release = false`)、`adjustLot`(棚卸し: `adjustment = true`)。どの行にも受払実績を1件ずつ作る。
   - `listVisiters` は DB の `v_visiter_issuable` で判定する(`issuable`・`blockReason`・`openComplaintCount`)。`ScanVisiter` に `containerId`・`openComplaintCount`・`issuable`・`blockReason` を持たせた(`hasOpenComplaint` は残した)。
4. `page.md` に「棚ビジターの台帳」を追加(整合テスト)。`packages/model_providers/CLAUDE.md` に「棚ビジター(在庫)の決まり」を統合。`barcode_entry_model/CLAUDE.md` を更新。

## 提案・判断

1. **払出・移動を DB 関数にする(issue §3 の TODO)を推奨する。** 今は `moveLot` が最大4回の登録を順に呼ぶ。途中で失敗すると、受払実績の無い行や、-だけで+が無い行が残る(`v_visiter_ledger_issue` の `orphan_line` などで検出はできるが、人が直す)。`visiter_move(p_src, p_container, p_qty, p_hold)` / `visiter_issue(p_src, p_qty, p_work_record)` があれば、`ScanClient` は1回の呼び出しになる。関数を作る場合は PostGraphile の mutation として公開され、そのモデル化は別 Issue で行う。
2. **出しすぎの事前検査をクライアントに置かない。** `issueLot` は数量 1 以上だけを検査し、ロットの今の数量を超えるかは見ない(競合があるため、判定は DB の `negative_balance` に任せる)。出しすぎを登録時に止めたい場合は、DB 側の制約か上の関数で行うのが確実。判断を求める。
3. **`listVisiters` は2回の読み込み**(`v_visiter_issuable` と、symbol のための `trans_visiter`)。`v_visiter_issuable` に `symbol` 列があれば1回で済む。DB で追加してよいか。
4. **材料の払出(製造への投入)の自動化は未実装。** BOM から材料を求め、ロットを先入れ先出し(`update_at`)で選ぶ処理は、`ScanClient` ではなく機能(`barcode_entry`)側の仕様と合わせて決める必要がある。仕様が決まれば `issueLot` を使って組み立てる。
5. **出しすぎでマイナスになったロット**は `v_item_on_hand.onHandQuantity` に入る(issue §11)。画面の合計に使うときは `v_visiter_ledger_issue` の件数を併記するのがよい。
