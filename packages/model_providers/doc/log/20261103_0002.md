# 20261103_0002 ログ 20261103_0001 の対応(issue 20261103_0002)

## 1・4. 担当者の登録 → PocketBase の `app_user_id` への紐付けの調査
**結論: `info_staff` に列を足さなくても、`app_user_id` に `info_staff_id` を入れる形で成立する。**

| 確認した事項 | 結果 |
| --- | --- |
| `users.app_user_id` の形式 | 英数字・`_`・`-` の1〜64文字、一意(`pb_migrations/1762041600_init_schema.js`、`lib/admin.js` の `setAppUserId`)。UUID(36文字)は収まる |
| 紐付けの向き | PocketBase → App DB だけで足りる。`app_user_id` が空の間はログイン不可(authRule)。`pb_user_id` を App DB に持つのは任意(逆引き用) |
| 順序 | README のとおり「App DB に担当者を登録 → `activate`(`app_user_id` を設定)」で固定。`activate` が失敗しても何度でも呼び直せる |
| 変更 | `app_user_id` は一度決めると変更不可(別の値だと 409)。担当者の `info_staff_id` は不変なので問題ない |
| 失効 | 担当者を `remove = true` にしても PocketBase 側は自動では止まらない。`disabled`(`/admin/users/{id}/disable`)を合わせて呼ぶ運用が必要 |

**流れ(提案)**
1. 本人が申請する(`/api/app/signup`)。`signup_profiles` に本人情報が入る。
1. 管理者のアプリが `signup_profiles` を読み、`info_staff`(名称・コードなど)と `info_assign`(部署・役割の割り当て。`enable = true`)を登録する。登録で得た `info_staff_id` を控える。
1. `POST /api/app/admin/users/{pb_user_id}/activate` に `app_user_id = info_staff_id` を渡す。
1. 有効化コードを本人へ渡す。以降、JWT の `sub`・`app_user_id` が `info_staff_id` になる。

**DB 側の不一致(要対応)**: DB の関数(`07_visiter_functions.sql`、`08_mrp.sql`)は `jwt.claims.staff_id` を担当者として読む。しかし PocketBase の GraphQL 用 JWT のクレームは `sub`・`pb_user_id`・`app_user_id`・`app_role` で、`staff_id` が無い。次のどちらかが必要。
1. PocketBase の `50_graphql_token.pb.js` に `staff_id`(= `app_user_id`)のクレームを足す。
1. DB の関数が `jwt.claims.app_user_id` を読む。
→ 前者を提案する(DB の関数の変更が要らない)。`tools/docker/postgresql/issue/20261103_0001.md` を更新した。

**モデル側**: 担当者の登録・所属の登録は `organization_model`(`StaffPageEdit`・`AssignPageEdit`)を使う。登録(`kind: create`)の YAML は未作成なので、承認画面を作る時点で `StaffPageCreate`・`AssignPageCreate` を `organization_model` に足す(複数テーブルにまたがる登録は窓口で順に呼ぶ決まり)。認証用の新しいモデルパッケージは作らない。

## 3. ページ切り替え時の権限確認 — モデルの範囲(提案)
**前提(採択)**: ログインユーザーの JWT を Riverpod に保存し、ページ遷移・更新のたびに権限を確認する。

**モデルの範囲**
1. 既存の `StaffEffectiveAccessPathPage`(`info_staff_id` で絞る)で足りる。列は `usecase_path`・`can_write`・`from_department`・`from_staff`。確認に使うのは `usecase_path` と `can_write` だけ。
1. `access_control_model` に窓口 `AccessPermissionClient`(Facade)を足す。生成された型は窓口の中に隠し、平らな型 `EffectiveAccess(usecasePath, canWrite)` の一覧を返す。`ScanClient` と同じ作り。
   - `fetchByStaff(staffId)`: 担当者の実効アクセスパスをすべて取得(1回の問い合わせ。ページ数は少ない)。
1. 判定の部品(純 Dart。`foundation` または `page_mediator_extension`)に `AccessDecision`:`canView(path)`・`canWrite(path)`。パスは `usecase_path` と前方一致(`/system/unit/...` は `/system/unit` の権限)で判定する。
1. 保存と更新: ログイン直後に取得して Riverpod に保存する。JWT の期限(既定 15分)の更新と合わせて取り直す。ページ遷移ごとには通信せず保存した値で判定し、保存した値の取得から一定時間(例: 5分)を過ぎていたら取り直す。権限を変更した直後は画面から明示的に取り直せる。
1. 遷移の確認: `IPageSessionMediator` の実装に判定を差し込み、GoRouter の `redirect` から呼ぶ。権限が無いときは専用のページ(権限なし)へ。書き込み不可のときは編集の操作を無効にする(`can_write`)。
1. DB 側の強制は無い(`CLAUDE.md` の方針)。PostGraphile を直接呼べば権限に関係なく読み書きできるため、ここは画面の切り替えだけと明記する。

**確認したい点**: ① `usecase_path` と GoRouter のパスの対応(前方一致でよいか)、② 取り直しの間隔、③ 権限が無いときの遷移先。
