- 区分・利害関係者(顧客、外部)での絞り込みキーの例: `stakeholder||isCustomer`、`stakeholder||master||shippingKinds||code`。対応表は`lib/contents/shipping_order_page_filter_spec.dart`・`shipping_today_page_filter_spec.dart`。
- 出荷オーダーのDBには区分の列が無い。区分は利害関係者(`mstr_stakeholder`)の配送区分(`mstr_shipping_kind_id`)で表す。履歴(`history_mstr_stakeholder`)には呼称・配送区分の関連が無いため、元の`mstr_stakeholder`を子(`master`)にした。
- 追加した2ページには、子のレコード数(5-14節)の列を含めた(`page_views_consistency_test`の検査)。
- 生成を進めるため、全量スキーマを再取得した(`doc/log/schema_refetch_2026-10-26.md`)。再取得後のスキーマで`lib/postgraphile`の全モデルを再生成したため、既存の画面のモデルにも差分がある(生成物の内容のみ。スキーマにコメント・フィールドが増えたため)。
- 採用した`lib/graphql`: `shipping_order_page`(readのみ)、`shipping_today_page`、`work_plan_delay_page`。

## DB要(page.mdに記録した項目)と提案
集計のビューが無いため、次のビューを提案する(DBの変更は未実施)。ビューができたら、`v_*_count`と同じ形で親のページの列に追加し、再生成する。
- 売上合計(受注より): 受注(`trans_order`)の受注明細(`trans_order_detail`)の金額合計。受注日・利害関係者・区分で絞れるよう、`trans_order`のキーと合計を持つビュー(例: `v_order_sales_total`)。
- 買付合計(発注、非計上発注より): `trans_purchase_detail`と`trans_unrecognized_detail`の金額合計(例: `v_purchase_total`、`v_unrecognized_total`)。
- 納期遵守率: 出荷オーダーの予定日・工程計画の完了・発注の納期に対する実績日の比較。遵守件数と全件数(率は件数の比で計算できる)を持つビュー。
- 金額の列が受注明細・発注明細のどれかは、ビューを作るときに確認が必要(今回は未確認)。
