# このライブラリについて
## 一般
このライブラリ`baton_lib`は、パッケージGoRouterと画面ページをもつ機能毎のライブラリをコマンドでつなぎ、責務を分離します。機能が分離された別のページへの遷移や、同ページに実行させる内容、渡すオブジェクトを定義します。
このライブラリを呼び出すアプリケーション、機能毎のライブラリの間でやりとりするインスタンスは全てインターフェイスとして渡します。ただし、インスタンスを文字列化して渡すのではなく、コマンドオブジェクトとして渡します。このコマンドオブジェクトは、例えば`Commandインターフェイス`や継承した`Destinationインターフェイス(ページ遷移)`へキャストすることでアプリケーション側、または各機能毎のライブラリ側で分離します。画面遷移も「親アプリへのコマンド」の一種として扱い、入口を1つにします。

###　このライブラリの実装イメージ
以下は、このライブラリの実装、使用イメージです。実際に実装されている名前ではありません。
+   このライブラリ側の宣言イメージ
```dart
// pms_command
abstract class Command<R> { const Command(); }

/// 画面遷移も Command の一種。R は戻り値の型
abstract class Destination<R> extends Command<R> { const Destination(); }

abstract interface class CommandBus {
  Future<R> execute<R>(Command<R> command);
}

/// 横断的な処理(ログ、権限チェックなど)を差し込むためのミドルウェア
typedef Middleware = Future<Object?> Function(
    Command command, Future<Object?> Function() next);
```

+   使用側のイメージ
```dart
// feature_order(使う側):遷移もデータ操作も同じ呼び方になる
final bus = ref.read(commandBusProvider);
final id = await bus.execute(const CustomerPickerDestination()); // int? が返る
await bus.execute(ApproveOrderCommand(orderId: 10));

// app:Destination かどうかでハンドラを振り分ける
if (command is Destination) return navigator.push(registry.resolve(command));
return handlers.resolve(command).handle(command);
```

##  規則/仕様
1.  ディリクトリ/ファイル
    1.  生成結果のレポートは`doc/log`ディリクトリにファイル名`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  同じ年月日、同じ番号に対する追加変更は`年月日_4桁ゼロ埋の番号_add_1からの連番.md`として保存する。
    1.  生成したライブラリに関する使い方やヘルプなどの使用にかかわるレポートは`doc/contens`の保存する。
    1.  最終的にこの`CLAUDE.md`へ統合される追加、変更の指示は`issue`ディリクトリに`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  つまり`生成結果のレポート`と連動する。
        1.  `CLAUDE.md`への統合も指示に含める。統合時、削除指示が無い限り`issue`ディリクトリ`doc/log`ディリクトリの中を削除しない。`CLAUDE.md`には変更や追加、削除であることについて記録しない(生成時に`issue`ディリクトリ`doc/log`ディリクトリを参照するため)。
    1.  細分化した機能別に`lib/`以下のディリクトリを2階層を限度(`lib/xxx/xxx`)として分ける。細分化の程度は、2階層になる程度の抽象度とする。
        1.  細分化する機能が少ない(5以下)のとき、1階層で良い(`lib/xxx`)。
1.  命名規則
    1.  ファイル名、クラス名など名前付けのルールはFlutterの規則、慣例に従う。
    1.  クラス名はデザインパターンがわかる、または意味が通る英語の名詞とする。ただし、`はい/いいえ`のような`isXxxx`などの`is/as/has`の慣例を優先する。
        1.  `Command`などデザインパターンのみの名前だと誤解や衝突を招くため、機能、動きの名詞化したものと組み合わせる。
    1.  プリフィクスにライブラリ名をつけない(BatonLibXXのような)。
1.  バレルファイルを使用する
    1.  バレルファイルにまとめ、このライブラリを使用する側は1行を読み込むだけで解決できるようにする。ただし、相互に関連が無い独立した機能の場合はバレルファイルを分けて、仕様側が機能に応じて選択できるようにする(例えば、ファイル参照機能と計算機能があり、計算機能がファイル参照を行わない場合は別々にする)。ただし、 ユーザーの仕様体験を優先する。ライブラリ全体の機能が少ない(10以下)ときにインポートするファイルを分ける必要はない。
1.  インスタンスのJSON化
    1.  生成するこのライブラリのインターフェイス、クラスのインスタンスをJSONにコンバートできる。ただし、エラー追跡のためであり、現時点で機能を復元する目的では使用しない。
1.  ログを残す
    1.  ライブラリは実行したときのログを残す。ただし、このライブラリ側のエラーログがけを残し、実行側のアプリケーションがどの実行でエラーが発生したか調査するとき、機能毎のライブラリ側なのかを切り分け可能にするために、適切に選別する。
    1.  ロガーはRiverpodから提供され、アプリケーション全体をとおして同じ仕様のログ出力を行う。
##  使用パッケージ
使用する外部のパッケージのバージョンは、`../../flutter_app_lib`、`../../flutter_pub_lib`で同じパッケージを使用しているアプリケーション、ライブラリにあわせること。古いパッケージを使用している同ディリクトリのパッケージがある場合は、そのアプリケーションまたはライブラリの名前をログに残す。
1.  使用して良いパッケージ
    1.  Logger
    1.  BuildRunner(Dev)
    1.  Riverpod
    1.  RiverpodGenerator(Dev)
    1.  その他必要があれば提案しなければならない。
