# 20261107_0001 設定はサーバーのルートだけにし、/health と /info をライブラリが付ける(pms_app issue 20261107_0001)

## 問題
- 裏設定の `maintenanceUrl` は `http://.../health` だった。表示の情報は `/info/...` にあるため、設定と実際のアドレスが別々で、人為的な食い違いが起こりうる。
- 情報のパスにファイル名(`/info/<名前>.json`)を含むため、管理者がファイル名を間違える可能性がある。

## 対応(案1を採用し、ファイル名もなくした)
1. 設定(`maintenanceUrl`・`MAINTENANCE_URL`)は**サーバーのルートだけ**(例 `http://192.168.1.101:18480`)。`HttpMaintenanceChecker.forServer` が `/health`(`maintenanceHealthPath`)と `/info`(`maintenanceInfoPath`)を付ける。パスの共有は、サーバーとこのライブラリの定数の1か所。
1. 以前の設定(末尾が `/health`)も、末尾の `/health` と `/` を取り除いて受け付ける(`maintenanceServerRoot`)。保管庫や暗号化した設定に残る値はそのまま動く。
1. 情報のパスは `/info` だけ(ファイル名なし)。サーバー(`tools/docker/maintenance`)は `location = /info` で、実体 `data/info/maintenance.json` を読み書きする。`/info/<名前>.json` は無くなった(404)。
1. `tools/docker/maintenance/README.md` の使い方の表(`/info/<名前>.json`)を `/info` に直した。`status.json` の記述は残っていない。

## 他の案を採らなかった理由
- 情報取得パス・状態取得パスを裏設定に別々に持つ案: 設定の項目が増え、食い違いの余地が残る。パスはサーバーとライブラリの仕様なので、設定に持たせない。

## テスト
`maintenance` 16件通過(ルートだけの設定から `/health`・`/info` を組み立てる、`/health` 付き・末尾 `/` の以前の形を同じルートにする、を追加)。pms_app 31件・backstage 39件通過。
nginx の設定(`/info`)は、この環境に docker が無く、実行して確認していない(別環境で `PUT /info` → `GET /info` → `DELETE /info` を確認する)。
