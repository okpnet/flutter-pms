# maintenance

メンテナンス中のページ。サーバーからの応答がメンテナンス中のときに表示し、他のページへは一切リンクしない。`packages/features/CLAUDE.md` の[規則/仕様]を必ず適用する。
プロジェクト名は、ページの役割(メンテナンス)から `maintenance` とした。

## 画面
1.  メンテナンスページ(`MaintenanceDestination` → `/maintenance`): 文面・実施時間(開始・終了)・「再確認」だけを持つ。タイトルバー・サイドバー・メニュー・戻る操作・リンクを持たない。メンテナンス中は戻る操作(`PopScope`)も無効。
2.  ルートはアプリの枠(`ShellRoute`)の外に置く。メニューの項目は持たない。
3.  ログイン中に処理していても、ページの切り替え・更新のタイミングでメンテナンスを確認し、メンテナンス中ならメンテナンスページへ切り替える。認証ステータスの更新のタイミングで切り替えられる(下記)。

## 仕組み
| 部品 | 内容 |
|---|---|
| `IMaintenanceChecker` | サーバーの状態の確認。`HttpMaintenanceChecker` は HTTP 503 をメンテナンス中とする(`Retry-After`、本文 JSON の `message`・`startAt`・`endAt` を読む)。通信できないときは利用可能として扱い、ログに残す。既定は `AlwaysAvailableMaintenanceChecker`(テスト用) |
| `maintenanceStatusProvider` | いまの状態。`refresh()`(サーバーへ確認)と `report()`(通常の通信の応答から知らせる) |
| `maintenanceRedirect` | ルーターの `redirect` に使う判定。メンテナンス中はどのページもメンテナンスページへ向け、終わっていればメンテナンスページから戻す |
| `MaintenanceAwarePageSession` | `page_mediator_extension` のセッション確認へ、メンテナンスの確認を足す(Decorator)。ページの切り替え・更新で、認証の確認より先にメンテナンスを確認する |

アプリへの組み込み: `MaintenanceModule` を `ShellRoute` の外のルートへ追加し、ルーターの `redirect` で `maintenanceRedirect` を呼ぶ(`refreshListenable` に `maintenanceStatusProvider` を使う)。`pageSessionMediatorProvider` へ `MaintenanceAwarePageSession`(内側は認証の確認)を差し込む。`maintenanceCheckerProvider` へ `HttpMaintenanceChecker` を差し込む。

## 構成
| 種別 | ファイル | 内容 |
|---|---|---|
| 実装の入口 | `lib/maintenance.dart` | アプリだけが読み込む(モジュール・判定・状態・確認の実装) |
| 契約の入口 | `lib/maintenance_api.dart` | 遷移先の型(`MaintenanceDestination`) |
| 状態 | `lib/src/status/` | 状態・確認・Provider・リダイレクト・セッション |
| ページ | `lib/src/page/` | ページ・モジュール・遷移先・パス |
| 文字列 | `lib/src/i18n` | slang の Yaml(日本語・英語) |

##  規則
1.  ディリクトリ/ファイル
    1.  生成結果のレポートは`doc/log`ディリクトリにファイル名`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  同じ年月日、同じ番号に対する追加変更は`年月日_4桁ゼロ埋の番号_add_1からの連番.md`として保存する。
    2.  生成したライブラリに関する使い方やヘルプなどの使用にかかわるレポートは`doc/contents`の保存する。
    3.  最終的にこの`CLAUDE.md`へ統合される追加、変更の指示は`issue`ディリクトリに`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  つまり`生成結果のレポート`と連動する。
        2.  `CLAUDE.md`への統合も指示に含める。統合時、削除指示が無い限り`issue`ディリクトリ`doc/log`ディリクトリの中を削除しない。`CLAUDE.md`には変更や追加、削除であることについて記録しない(生成時に`issue`ディリクトリ`doc/log`ディリクトリを参照するため)。
    4.  細分化した機能別に`lib/`以下のディリクトリを2階層を限度(`lib/xxx/xxx`)として分ける。細分化の程度は、2階層になる程度の抽象度とする。
        1.  細分化する機能が少ない(5以下)のとき、1階層で良い(`lib/xxx`)。
2.  命名規則
    1.  ファイル名、クラス名など名前付けのルールはFlutterの規則、慣例に従う。
    2.  クラス名はデザインパターンがわかる、または意味が通る英語の名詞とする。ただし、`はい/いいえ`のような`isXxxx`などの`is/as/has`の慣例を優先する。
        1.  `Command`などデザインパターンのみの名前だと誤解や衝突を招くため、機能、動きの名詞化したものと組み合わせる。
    3.  プリフィクスにライブラリ名をつけない(BatonLibXXのような)。
3.  バレルファイルを使用する
    1.  バレルファイルにまとめ、このライブラリを使用する側は1行を読み込むだけで解決できるようにする。ただし、相互に関連が無い独立した機能の場合はバレルファイルを分けて、仕様側が機能に応じて選択できるようにする(例えば、ファイル参照機能と計算機能があり、計算機能がファイル参照を行わない場合は別々にする)。ただし、 ユーザーの仕様体験を優先する。ライブラリ全体の機能が少ない(10以下)ときにインポートするファイルを分ける必要はない。
4.  インスタンスのJSON化
    1.  生成するこのライブラリのインターフェイス、クラスのインスタンスをJSONにコンバートできる。ただし、エラー追跡のためであり、現時点で機能を復元する目的では使用しない。
5.  ログを残す
    1.  ライブラリは実行したときのログを残す。ただし、このライブラリ側のエラーログがけを残し、実行側のアプリケーションがどの実行でエラーが発生したか調査するとき、機能毎のライブラリ側なのかを切り分け可能にするために、適切に選別する。
    2. ロガーはRiverpodから提供され、アプリケーション全体をとおして同じ仕様のログ出力を行う。
6.	GOFデザインパターン
	1.	クラス名やファイル名にデザインパターンを含めない場合は、コメントに該当するパターン名を追加する。
	2.	必ずしもデザインパターンに割り当てる必要はない
