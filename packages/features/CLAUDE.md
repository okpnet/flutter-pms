
#	画面のデザイン
##　このフォルダの目的
このワークスペースで生成するアプリケーションの画面を、機能毎にプロジェクトにまとめ、その中でGoRouterのノードを含めたWidget(ページ)を生成する、ルートプロジェクトです。
様々なライブラリやパッケージを参照するため、全て一度に生成せず、少しずつまとめる必要があります。そこで、希望毎にプロジェクトを生成し、その画面デザインと当該プロジェクトの`CALUDE.md`を生成。そのプロジェクトの`doc/contents`フォルダに画面イメージをHtmlで生成します。そのHtmlを元に当該プロジェクトの`issue`フォルダへ追加、変更をまとめ、完成させる予定です。全てのプロジェクトの`CALUDE.md`は、このファイルを基準として生成します。その中で[規則/仕様](#規則/仕様)は必ず適用します。
1.  `flutter-pms\legacy\fultter_main\mock_up`にライブラリを使った配置があるので参考にする。

##  規則/仕様
1.  ディリクトリ/ファイル
    1.  生成結果のレポートは`doc/log`ディリクトリにファイル名`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  同じ年月日、同じ番号に対する追加変更は`年月日_4桁ゼロ埋の番号_add_1からの連番.md`として保存する。
    2.  生成したライブラリに関する使い方やヘルプなどの使用にかかわるレポートは`doc/contens`の保存する。
    3.  最終的にこの`CLAUDE.md`へ統合される追加、変更の指示は`issue`ディリクトリに`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  つまり`生成結果のレポート`と連動する。
        2.  `CLAUDE.md`への統合も指示に含める。統合時、削除指示が無い限り`issue`ディリクトリ`doc/log`ディリクトリの中を削除しない。`CLAUDE.md`には変更や追加、削除であることについて記録しない(生成時に`issue`ディリクトリ`doc/log`ディリクトリを参照するため)。
2.  命名規則
    1.  ファイル名、クラス名など名前付けのルールはFlutterの規則、慣例に従う。
    2.  クラス名はデザインパターンがわかる、または意味が通る英語の名詞とする。ただし、`はい/いいえ`のような`isXxxx`などの`is/as/has`の慣例を優先する。
        1.  `Command`などデザインパターンのみの名前だと誤解や衝突を招くため、機能、動きの名詞化したものと組み合わせる。
    3.  プリフィクスにライブラリ名をつけない(BatonLibXXのような)。
3.  バレルファイルを使用する
    1.  バレルファイルにまとめ、このライブラリを使用する側は1行を読み込むだけで解決できるようにする。ただし、相互に関連が無い独立した機能の場合はバレルファイルを分けて、仕様側が機能に応じて選択できるようにする(例えば、ファイル参照機能と計算機能があり、計算機能がファイル参照を行わない場合は別々にする)。ただし、ユーザーの使用体験を優先する。ライブラリ全体の機能が少ない(10以下)ときにインポートするファイルを分ける必要はない。
4.  インスタンスのJSON化
    1.  生成するこのライブラリのインターフェイス、クラスのインスタンスをJSONにコンバートできる。ただし、エラー追跡のためであり、現時点で機能を復元する目的では使用しない。
5.  ログを残す
    1.  ライブラリは実行したときのログを残す。ただし、このライブラリ側のエラーログだけを残し、実行側のアプリケーションがどの実行でエラーが発生したか調査するとき、機能毎のライブラリ側なのかを切り分け可能にするために、適切に選別する。
    2.  ロガーはRiverpodから提供され、アプリケーション全体をとおして同じ仕様のログ出力を行う。
6.  GOFデザインパターン
    1.  クラス名やファイル名にデザインパターンを含めない場合は、コメントに該当するパターン名を追加する。
    2.  必ずしもデザインパターンに割り当てる必要はない。

## 機能プロジェクト共通
1.  画面デザインは`flutter-pms\tools\open-design`のHtmlデザインを原則の基準とする。
    1.  テーブル構造、ツリー構造は`flutter-pms\packages\ui\flgtable_lib`を使用する。
    2.  列、フィールドは`model_providers の各モデルパッケージ`を参照する。
    3.  プロジェクト(機能)の区分は、Htmlのメニューを参照する。
2.  各プロジェクトに共通して次を行う。
    1.  データの取得は`riverpod`をとおして`flutter-pms\packages\foundation\data_strategist`を使用する。
    2.  プロジェクトごとに`CLAUDE.md`を生成し、このファイルの[規則/仕様](#規則/仕様)を含める。
    3.  プロジェクトの評価結果に対する提案、問題/課題は、規則に従って`doc/log`に追加する(プロジェクト毎に解決していくため)。
3.  ページ用の拡張(`packages/core/page_mediator_extension`)。ページが、データ取得(`data_strategist`)・設定の保存(`settings_keeper`)・セッション確認(認証・メンテナンス)を使うときは、実装を直接参照せず、窓口(`IPageDataMediator`・`IPageSettingsMediator`・`IPageSessionMediator`)を`PageMediatorMixin`(`ConsumerStatefulWidget`)または`WidgetRef`の拡張(`ref.pageData`など)から使う。実体はアプリが Riverpod で差し込み(`pageSessionMediatorProvider`など)、テストでは差し込まない(セッション確認は何もしない既定の実装)。
4.  ビジュアルテスト(example)
    1.  各プロジェクトは、プロジェクト内の`example`に、Windows向けのビジュアルテスト用アプリを持つ。そのプロジェクトだけを起動して画面を個別に確認できるようにする。
    2.  `example`は本番のアプリと同じ配線(GoRouter・CommandBus・ハンドラ登録)の`feature_shared`の`FeatureHost`を使い、`lib/main.dart`の`entries`に遷移先を並べる。画面を追加したら`entries`に1行足し、`test/widget_test.dart`で起動と遷移を確認する。
    3.  `example`は`flutter-pms`のworkspace対象外(ロックファイルは別。`flutter pub get`で一緒に解決される)。起動は`flutter run -d windows`。
5.  多言語(slang)
    1.  表示する文字列は、プロジェクト内の`lib/src/i18n`の言語ファイル(Yaml、`ja.i18n.yaml`が基準、`en.i18n.yaml`など)に置く。設定は`slang.yaml`(`class_name`・`enum_name`はプロジェクト固有の名前にする)。生成は`dart run slang`。生成物(`strings*.g.dart`)もコミットする。
    2.  言語の選択は`riverpod`で行う。`feature_shared`の`localeProvider`を`ref.watch`して`xxxStringsProvider`が文字列を返す。slangのFlutter連携・グローバル変数は使わない。基準言語以外は遅延読み込みのため、読み込みが終わるまでは基準言語(日本語)を返す。
    3.  エラーは文字列ではなく種類(enum・例外の型)で持ち、画面が表示時に文字列へ変換する。ログの文言は多言語の対象にしない。
    4.  画面を持つようになったプロジェクトから導入する(画面が空のプロジェクトは、画面を作るときに追加する)。
6.  IDの扱い
    1.  GraphQLのUUIDは、アプリ内では文字列(`String`)として扱う。遷移先・命令・モデル・パスのidはすべて`String`にする。
7.  削除の参照チェック
    1.  他の画面・テーブルから使用されているデータは削除できない。リポジトリの`remove`は、使用中のとき専用の例外(例: `ShippingKindInUseException`)を投げ、画面はログに残さず利用者に表示だけする。GraphQL版は、DBの外部キー違反をこの例外に変換する。
8.  共有マスタ(`shared_master`)の利用条件
    1.  利害関係者(`stakeholder`)と担当者(`contact`)は`shared_master`が持つ。顧客・外部供給者・配送サービサーは同じ利害関係者をフラグで見分けるだけで、取得元・編集画面は1つにする。顧客台帳は顧客のフラグ、外部供給者台帳は外部供給者のフラグでの絞り込み(`EntityListDestination`の`filter`)とする。
    2.  利害関係者の配送区分の選択は、同じプロジェクトの配送区分(`shipkind`)で行う。
    3.  配送区分は、トップメニューの「営業」「購買」のどちらからも選択して開く。メニューの項目は共通の画面(`shared_master`)へ遷移する。顧客台帳は「営業」、外部供給者台帳は「購買」のメニューから開く。

## 機能コード・画面コード
1.  機能(プロジェクト)と画面のコードの一覧を`doc/page_code_list.yml`に置く。機能コード1文字 + 画面コード1文字(どちらも大文字英数、36種まで)の2文字が画面のコードになる。連想できる文字を優先して割り当てる。
2.  生成は`node tools/entity_gen/page_codes.js`(リポジトリのルートで実行)。既に割り当てたコードは変えない(バーコードに印字するため)。
3.  画面の追加・削除のたびに、生成して一覧をレビューする。削除した画面は`removed: true`で残り、コードを再利用する前にレビューする。
4.  一覧は、後に、バーコードを読み込んで`Destination`へ遷移する画面(登録画面からのみ使用)に使う。その画面は未作成(ワークスペースの Issue)。バーコードで実績を登録する画面は`barcode_entry`(機能コード`E`)。

## 構成
すべての構成はモバイル、タブレット、PC（モバイルより大きいサイズ）のサイズに応じたview_responsivenessを使用する。
色、サイズなどはtheme_libを使用する。
### ライブラリ構成
+ 画面構造
	+ フレーム構造
	+ ツリー構造
	+ テーブル構造
	+ リスト構造
	+ 編集構造

#### 画面構造
すべての画面ライブラリの原点、ルート。実体を持たない抽象化されたインターフェイス。

#### フレーム構造
分割または並べた割合、順序、Zインデックスを持ち、1つまたは複数の抽象化された画面構造を子として持つ。

#### ツリー構造
grid_extenssion使用。親子構造（子のインデント処理）を持ち、ドラッグドロップで親の付け替えができる（Trueのとき）。親は子の有無の情報をもち、子があるときに展開（遅延読み込み）、縮小ができる。

#### テーブル構造
grid_extenssion使用。列（プロパティ/キー）と行をもつリスト構造で、列のソート、フィルタができる（Trueのとき）。列は値を表示/非表示ができる。列キーは`flutter-pms\packages\infra\model_providers の各モデルパッケージ\source\views`に従う。
列構造は、`flutter-pms\packages\infra\model_providers の各モデルパッケージ\lib\postgraphile`を参照し、該当するモデルクラスのプロパティ名を適用する。
編集が有効なとき、行のクリックで編集画面へ遷移する。
#### リスト構造
タイルもしくは1つのラベル（アイコンとラベルの組み合わせもありうる）をもつドラッグドロップで順を変えることができる（Trueのとき）リスト構造。1レコード/1タイルをタップ/クリックで編集構造へ遷移できる。[テーブル構造](#テーブル構造)との違いは、列を持たないことである。
編集が有効なとき、行のクリックで編集画面へ遷移する。
#### 編集構造
汎用インプット構造:通常のWidgetを使う。ライブラリとして生成しない。内部にリスト構造を持つ場合がある。
GraphQLから取得したデータのうち、イミュータブルな更新者、更新日は編集できない。

## 共通画面
### タイトルバー
1. アプリケーションのタイトルまたはイメージを表示する
2. モバイル表示のときハンバーガーメニューを表示する。表示する項目と振る舞いは[サイドバー](#サイドバー)と共有する。
	+ ログインしており、画面に対して権限が有効になっている場合のみ（ログイン、ログアウト、一部のエラー画面では表示されない）表示される

### サイドバー
1. モバイルのとき[ハンバーガーメニュー](#ハンバーガーメニュー)として表示するため、非表示にする。
2. タブレットの場合、または設定で有効の場合はアイコンのみの表示にする。
	+ ログインしており、画面に対して権限が有効になっている場合のみ（ログイン、ログアウト、一部のエラー画面では表示されない）表示される
### メインフレーム
[フレーム構造](#フレーム構造)を実装した子を持つ画面。
1. シングルメインフレーム
	+ タイトルバーとメインフレームの子を1つ持つ
2. マルチメインフレーム
	+ タイトルバー、サイドバー、メインフレームの3つの子を持つ
	+ メインフレームは画面によってさらに分割されるときがある

### 選択フレーム
[フレーム構造](#フレーム構造)を実装した子を持つ画面。タイトルバー、サイドバーを持たず、他のフレームと併用する。

## 機能別画面
### 一般
`基本的な情報`とは、名前、略称、読み、住所などの情報をもとに一意に識別できる情報。データの更新者、更新日、削除されているかの情報を含めない。
機能画面の機能単位のプロジェクトは`flutter-pms\packages\features`に保存する。
### 参照するモデル
`flutter-pms\packages\infra\model_providers の各モデルパッケージ\source\page.md`を画面の参照元とする。
以下の各画面はプロジェクトの単位として、当該情報を`CLAUDE.md`としてまとめ、実装の基準とする。
ログインしていない、画面に対して権限が有効になっていない場合、かつ通信可能でエラーでなければログイン画面に遷移する。

### Html のトップメニューに対応する機能プロジェクト
`tools/open-design` のトップメニュー(ダッシュボード → 資源 → 業務グループ → 会社情報)の単位で、`flutter-pms\packages\features` に1メニュー1プロジェクトを置く。各プロジェクトの`CLAUDE.md`に画面・参照するモデルをまとめる。

### 契約(xxx_api)の置き方
別パッケージ `xxx_api` は作らない。1機能=1パッケージとし、`lib/xxx.dart`(実装の入口。アプリだけが読み込み、公開は `XxxModule` のみ)と `lib/xxx_api.dart`(遷移先・命令の型だけ。他の機能・アプリが読み込む)の2つのバレルに分ける。他の機能は `lib/src` や `xxx.dart` を読み込まない。

### 実体の画面(entity_screens)
1.  配送区分のような専用の画面を除く、台帳(テーブル構造/ツリー構造)と編集(編集構造)の画面は、実体の定義から作る。定義は`tools/open-design`の画面定義(`domains.base.js`・`schema.gen.js`)と手書きの定義(`tools/entity_gen/handwritten.js`、会社情報・資源)から`tools/entity_gen/gen.js`が生成する。再生成はリポジトリのルートで`node tools/entity_gen/gen.js`。
2.  生成物(各プロジェクトの`lib/src/entities`・`lib/src/i18n/ja.i18n.yaml`の生成部分・`lib/src/<名前>_module.dart`・`test/<名前>_entities_test.dart`、`example`の`main.dart`、`apps/pms_app/lib/entity_menu.dart`)は直接編集しない。直したいときは生成元(Htmlの画面定義、`handwritten.js`、`gen.js`)を直して再生成する。
3.  画面の作りは`packages/ui/entity_screens`、機能への組み込みは`feature_shared`の`EntityFeatureModule`(Template Method)。各機能のモジュールは、定義・サンプル・表示名を渡すだけにする。
4.  実体のキーは全体で一意。パスは台帳`/e/<キー>`、新規`/e/<キー>/new`、編集`/e/<キー>/<id>`。遷移は`feature_shared`の`EntityListDestination`・`EntityEditDestination`で行う。
5.  項目の種類は文字・複数行・数値・日付・選択・参照・条件。条件は、演算子(`=`・`≠`・`>`・`<`・`>=`・`<=`・範囲(`between`)・二値(`yesno`))をリストから選び、値を手で入力する。値は JSON の文字列(例 `{"operator":">=","value":"10"}`、範囲は値が2つ、二値は真偽)で持つ。項目は読み取り専用にできる(`FieldDefinition.readOnly`。DB のビューの集計列など)。編集画面では表示だけ、台帳では読み取り専用の列(`flgtable_lib` の `ColumnDefinition.readOnly`)にし、入力・検証・保存の対象にしない。真偽(`FieldKind.flag`)は、チェックボックスまたはトグル(`toggle`)で入力し、値は`flagOn`(`1`)または空で持つ。台帳の列は はい/いいえ。真偽がオンのとき別の項目を無効にして値を空にする(`disables`)、別の真偽がオンでなければ必須にする(`needUnless`)、数値の下限(`ge`:以上、`gt`:より大きい)、子が存在する間は外せない(`lockedBy`。理由は項目の下に表示する)を、項目の定義に持たせる。無効になった項目は、台帳で定義した文言(`f_<キー>__off`、例:言い値（都度確認）)を出す。必須・形式・選択肢の検証は取得元(リポジトリ)が行い、エラーは種類(enum)で返して画面が文字列にする。参照の選択肢、使用中・配下がある場合の削除不可、所有する子の台帳の連動削除は登録簿(`EntityCatalog`)が行う。
6.  参照先が別の機能にあっても、機能同士はコンパイル時に依存しない。各機能が実体を登録簿へ登録し、実行時にキーで引く。専用の画面を持つ実体(配送区分)は選択肢(lookup)だけを登録する。同じ実体を別名で参照させたいとき(利害関係者を顧客・外部供給者として)は、別名の選択肢を役割で絞って登録し、元の実体(`backing`)の削除の使用中判定に含める。`example`は、参照先の機能も一緒に載せる。
7.  取得元は暫定でメモリ上のサンプル(`InMemoryEntityRepository`)。GraphQL版は`IEntityRepository`を実装して差し替える。
8.  重複不可は、実体の定義の`uniqueKeys`(項目の組)で持たせ、取得元が保存時に検証する(所有される実体は同じ親の中、それ以外は全体)。出典はDBの一意制約と画面案の「重複不可」。一意性の真実はDB側にある。定義は、画面の事前検証とメモリ上のサンプルの検証に使う。GraphQL版は、DBの一意制約違反を重複のエラー(`EntityFieldError.duplicate`)に変換する。
9.  参照項目は、リストから選ぶ方式のほかに、参照先の台帳の画面で選んで戻る方式(`FieldDefinition.picker`)を持つ。参照先が多い・検索して選びたいときに使う(例: 設備の品目は品目の台帳で選ぶ)。選択は CommandBus の`EntityPickerDestination(entityKey)`で行い、機能同士はコンパイル時に依存しない。結果は選択の結果`Selection`(`packages/core/selection_result`。実体のキー・一意な id・表示名・追加の値。JSON の`encode`/`decode`でも受け渡せる)で、取り消しは null。選択画面は新規登録のボタンを持たず、行の操作(ダブルクリック・長押し)で選んで戻る。見出しは「<名称>の選択」(モジュールの`pickTitle`で差し替え)。実体のキーのほか、別名(`EntityFeatureModule.pickAliases`)で選べる。別名は実体の台帳を役割で絞って開き、台帳の画面をそのまま使う(例: `supplier`は利害関係者のうち外部供給者の台帳で「サプライヤーの選択」、`customer`は「顧客の選択」)。名称(`name`)を持たず、この方式の参照で名称を借りる実体は、他の実体から選ぶときの表示をコード + 参照先の表示にする。
10. ツリーの台帳の親の付け替え(ドラッグ&ドロップ)は、更新と検証(循環・権限)を利用者が実装するハンドラ(`EntityFeatureModule.reparentHandler`)で行う。ハンドラが無い実体では付け替えを有効にしない。ハンドラの完了(失敗を含む)後に台帳を再読み込みして、実際のデータに合わせる。
11. 所有する子の台帳は、親の表の各行に子の表を入れた「表の中の表」で出せる(子の定義の`nest`。親の絞り込み`where`と、メニューのグループ`menuGroup`を持つ)。行ごとに開閉でき、初期状態はすべて開く。親の検索と並べ替え、子の表は`flgtable_lib`。編集モードで、親ごとの「追加」と子の行から編集への遷移ができる。画面案(`domains.js`)のタブの`nest`から生成する。
12. 他の実体から参照されている一覧(力量・資格の保持者、品目・利害関係者・設備・部署・場所・工程を参照している実体など)は、定義の`reverseLists`で持たせ、編集画面の下に読み取り専用で表示する。生成元は`tools/entity_gen/gen.js`の`REVERSE`。参照元の実体が別の機能にあっても、機能同士はコンパイル時に依存せず、実行時に登録簿から引く。
13. 項目名は`schema.graphql`のコメントを使う。コメントで裏付けられない項目名(画面案の名称を日本語として推論したもの)は、生成時に`tools/entity_gen/out/labels_inferred.md`へ一覧にし、`doc/log`に記録する(後で差し替えるため)。
14. DB のビューなど、読み取り専用の実体は、定義の`viewOnly`(画面案の実体の属性`viewOnly`)で持たせる。台帳に「新規」を出さず、編集画面に保存・削除を出さない。項目はすべて読み取り専用(`readOnly`)で、必須にしない。例: 品目の在庫(`itemonhand`)、資材所要計算の結果(`mrppending`・`mrppurchase`・`mrpissue`・`mrpcoverage`)、ビジター品目(`mrpvisiter`)。

### アプリの枠(app_shell)とメニュー
1.  タイトルバー・サイドバー・ハンバーガーメニュー・ログインユーザーは、見た目の部品として`packages/ui/app_shell`(1パッケージ)にまとめる。機能・認証の実体は知らず、表示用のモデル(`AppMenu`・`AppUser`)だけを受け取る。フレームは`MultiMainFrame`(タイトルバー + サイドバー + メイン)、`SingleMainFrame`、`SelectionFrame`。
2.  サイドバーとハンバーガーメニューは同じメニューを共有する。モバイルはハンバーガー、タブレットと設定が有効のときはアイコンだけのサイドバー、PCは通常のサイドバー。ログインしていない(ユーザーが無い)ときは、メニューもユーザーも出さない。
3.  メニューの項目は各機能が提供する(`feature_shared`の`MenuContributor`を`FeatureModule`と合わせて実装し、`MenuEntry`(グループの識別子・表示名・項目名・遷移先)を返す)。同じグループの識別子の項目は1つのグループにまとまる。グループの並びとアイコンはアプリ(`pms_app`の`shell_frame.dart`)が決める。権限の判定もアプリが行う。
4.  機能の画面は、`AppBar`を使わず、`app_shell`の`ScreenScaffold`(画面の見出し + 本体。戻れるときは戻るボタン)で作る。タイトルバーはアプリの枠(`AppTitleBar`)だけが持ち、枠の中に入れても二重にならない。`FeatureHost`の起点の一覧(example用)は例外とする。
5.  ログインユーザーの実体は`feature_shared`の`userSummaryProvider`(`UserSummaryNotifier`)で提供する。標準値はアプリが差し込む(認証(Keycloak)が無いあいだは固定の利用者)。設定画面でユーザー名・役割を設定値として与えられ、「標準に戻す」で標準値へ戻る。ログアウトでユーザーなしになり、メニューとユーザーは出さない。設定値(使用言語・サイドバーをアイコンだけにする設定・ユーザー名と役割)の保存と復元は`packages/core/settings_keeper`で行う。ライブラリは保存先を知らず、保存先(`SettingsStorage`)はアプリが`settingsStorageProvider`で決める(`pms_app`は`%APPDATA%\pms_app`のファイル)。起動時に復元してから、変更を保存し始める(`userSettingsAutoSaveProvider`、`app_core`が持つ)。ログアウト中はユーザーを保存しない。
6.  ユーザーメニューは「設定」と「ログアウト」を持つ。ログアウトはログアウト画面(`LogoutDestination`)へ遷移する。ログインは認証の導入後に追加し、それまでは仮のボタンで標準のユーザーに戻す。
7.  `app_core`は、ブート・エラー・設定(使用言語、サイドバーをアイコンだけにする設定、ログインユーザー、バージョン情報)・ログアウトを持つ。
9.  長時間の処理(例:資材所要計算)は、`feature_shared`の`busyProvider`(`BusyNotifier.run`)で包む。処理中は`BusyScope`(アプリは`MaterialApp`の`builder`に置く)が画面全体(メニュー・ハンバーガー・下部ナビを含む)の操作を無効にし、「計算中」と経過時間を出す。画面側も`PopScope`で戻る操作を止める。処理が終わる・失敗すると操作は元に戻る。
8.  アプリの枠のメニューの項目も CommandBus で開く(`feature_shared`の`TopLevelDestination`で包み、積まずに枠の中の画面を入れ替える)。`example`は CommandBus を通さずに開いてよい。

### 使用言語
1.  使用言語の既定は実行環境(OS)の言語。アプリが`localeProvider`を`SystemLocaleNotifier`へ差し替える。設定画面で「実行環境に従う」「日本語」「English」から選べる。対応していない言語は、各機能の文字列が基準言語(日本語)にする。
2.  各機能の文字列は、機能内の`lib/src/i18n`の言語ファイル(Yaml)に置く。`feature_shared`の`localeProvider`だけを共通の入口にする。

## GraphQL モデルの利用
1.  機能パッケージは、自分に対応する`packages/model_providers/<機能>_model`だけに依存する。他の機能のモデルパッケージには依存しない。
2.  機能をまたいで受け渡す(遷移先・命令・Baton経由を含む)のは ID(`String`)や基本型だけにする。生成された型(列挙型・入力型を含む)は、そのモデルパッケージと対応する機能の外に出さない。機能ごとに同名の型が生成されるため、このルールは必須とする。
3.  生成モデルは Git に入れない。モデルを使う前に`melos run gql:build`を実行する(本家スキーマは不要)。

## テスト
1.  データの取得元は`IDataRepository`(`data_strategist`)で受ける。テストの道具は`packages/infra/data_test_harness`だけを使い、`dev_dependencies`にだけ書く。接続先のURLをテストに書かない。
2.  GraphQLを使わない機能・部品の単体テストは、`RecordingDataRepository`で取得元を差し替え、GraphQLにもサーバーにも接続しない。
3.  GraphQLで取得する機能は、通信テストを書く(`test/xxx_connection_test.dart`)。
    1.  検証用サーバー(`serverTest`、読み取り専用)で、実際に取得できること。接続先は`http://192.168.1.100:5000/graphql`、接続できなければ`http://192.168.9.245:5000/graphql`。接続できなければ中止(skip)。
    2.  通信の異常は代役サーバー(`FaultyGraphqlServer`)で再現する: 遅延(呼び出し側の制限時間でタイムアウト)、応答の途中・前の切断(例外として呼び出し元へ伝わる)、認証エラー(401/403)、認証ヘッダーの送信、切断からの復帰。
    3.  生成モデルの型は、機能の外へ出さない(テストの確認もこの機能が公開する型で行う)。
4.  サーバーのデータを変更するテストは書かない(読み取り専用)。
