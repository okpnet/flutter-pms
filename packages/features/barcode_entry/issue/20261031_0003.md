# GraphQL 版の取得元の確認事項

`doc/log/20261031_0002_add_2.md` の実装で、DB の構成から決められなかった点。

1.  **棚出庫(払出)**: `trans_visiter` は棚(コンテナ)・状態・数量だけで、品目の列が無い。作業の材料を棚から払い出すには、どのビジター(ロット)から何を払い出すかの対応が要る。現状は作業実績の開始だけを登録している。→ 払出するビジターの決め方(品目との結び付けの置き場所。例: 受入ビジター `trans_purchase_rec_visiter` から品目をたどる)を決めてほしい。
2.  **不合格(異常)**: `trans_complaint_work`・`trans_complaint_purchase_rec` は親の `trans_complaint`(表題・詳細の文書、報告者)が必要。親を登録するモデル(文書の登録を含む)が無いため、備考に理由を残している。→ 異常の登録モデルを作るか、備考のままにするか。
3.  **ビジターの状態(`status`)**: 合格・不合格などの値の意味が不明のため、設定していない。→ 値の定義を決めてほしい(不合格を状態で表すなら、異常の登録は不要になる)。
4.  **設備点検**: 点検の結果(`trans_inspect_record`)は点検予定の明細(`trans_inspect_sch_detail`)に結び付く。設備の symbol から、どの予定の明細を対象にするか(今日以前で未実施の最も古いもの、など)を決めてほしい。決まれば `resource_model` に `kind: create` を追加する。点検項目(`checkItems`)も同じ明細から取る。
5.  **単位**: 品目の単位(`mstr_item` → 単位)を `ScanItemPage` に追加すれば、画面の「個」「本」を出せる。軽い読み込みのまま追加する。
6.  **作業者・場所の履歴ID**: 入庫(`trans_convey`)は `staff_history_id`・`location_history_id` を送っていない。DB のトリガーが補うか、検証用サーバーで確認できない(書き込みのため)。補われない場合は、最新の履歴IDを読み込んで送る。
7.  **作業指示のテストデータ**: 検証用サーバーに作業指示(`trans_work_plan`)の symbol が無く、照会の実機確認ができていない。
8.  **認証**: 登録者の作業者ID(`ENTRY_STAFF_ID`)は起動時の設定。認証(PocketBase)の導入後は、ログインユーザーから与える。
