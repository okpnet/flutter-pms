# GraphQL 版の取得元(IScanGateway)に必要なモデル

`doc/log/20261031_0002_add_1.md` の確認結果に基づく。実装はこの Issue の判断のあとに行う。

## 1. 不足しているもの
1.  `tools/gql_yaml2graphql` に登録(`kind: create`。`createXxx` の mutation)の生成がない。次の登録が必要。
    | 用途 | テーブル | 備考 |
    |---|---|---|
    | 作業実績 | `trans_work_record` | 数量・開始/終了・作業者・設備。不合格の記録の置き場所は未確認 |
    | 作業実績と棚在庫の結び付き | `trans_work_record_visiter` | 完了数量のビジターとの関連 |
    | 購入品受入 | `trans_purchase_rec`、`trans_purchase_rec_visiter` | 受入数量・ビジターとの関連 |
    | 棚への入庫/払出 | `trans_visiter`(数量・状態・棚)、`trans_convey`(`receive` = 入庫/払出、`convey_at`、数量) | 払出が棚出庫処理、入庫が入庫処理 |
    | 設備点検 | 点検整備の実施の登録(`resource_model` の点検整備) | 項目ごとの結果の列を確認 |
2.  `barcode_entry_model`(新設)が必要。機能は自分のモデルパッケージだけに依存する規則のため、既存の `work_record_model` などを直接読まない。作業指示・棚・発注明細・品目・設備を symbol で引く読み込みと、上の登録を YAML で持たせる。
3.  不合格(理由・数量)の置き場所。`trans_work_record` と `trans_purchase_rec` に該当列があるか未確認。無ければ DB の追加か、`remarks` への記録か。

## 2. 判断してほしいこと
1.  `tools/gql_yaml2graphql` に `kind: create` を追加してよいか(推奨。更新と同じ列の定義を使える)。
2.  `barcode_entry_model` を新設してよいか。
3.  登録は複数のテーブルにまたがる(例: 入庫 = 作業実績 + 作業実績ビジター + 移動)。DB の関数(`tests` スキーマのような)で1回の呼び出しにするか、クライアントで順に呼ぶか。途中で失敗したときの整合を考えると、DB の関数を推奨。
4.  検証用サーバーは読み取り専用のため、登録の通信テストは書けない。読み取り(symbol の照会)と代役サーバーでの通信異常だけをテストする。

## 3. 作業の順序案
1. 2-1 と 2-2 の判断 → 2. `gql_yaml2graphql` に create → 3. `barcode_entry_model` の YAML・生成 → 4. `GraphqlScanGateway`(`IScanGateway` の実装)→ 5. `entry_app` / `pms_app` で `scanGatewayProvider` を差し込む。
