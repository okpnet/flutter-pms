# 20261104_0004 ユーザー情報の表示・アプリケーションの裏設定の調査

指示: `issue/20261104_0004.md`(適用できるかの調査。実行するかは調査の結果から評価する)。調査のみ。ファイルは変更していない。

## 1. ユーザー情報の表示のプロジェクトはあるか
専用のプロジェクトは無い。部品は3か所に分かれている。
| 場所 | 持っているもの | 足りないもの |
|---|---|---|
| `packages/ui/app_shell` | `UserContainer`(顔写真・名前・役割・ユーザーメニュー)、`AppUser(name, role, photo: ImageProvider?)`。写真が無いときは名前の頭文字 | 写真を取得して渡す部分 |
| `packages/core/feature_shared` | `userSummaryProvider`(`UserSummary(name, role)`)。ログインで `auth_files` が名前を設定する | 写真の情報 |
| `apps/pms_app` の `AppMainFrame` | `AppUser(name:, role:)` を作る | `photo` を渡していない(いつも頭文字) |
| `packages/features/app_core` | 設定画面でユーザー名・役割を設定値として編集 | 写真の変更 |
画面案(`tools/open-design`)には「自分のイメージ」がある(`app.js` の設定画面、`pms_design.md` の「自分のイメージ」)。ファイルを選ぶ(PNG・JPEG・GIF・WebP、2MBまで)→ アプリバー・ダッシュボードの顔写真が変わる → 「初期のイメージに戻す」。初期のイメージは `tools/open-design/avatar.svg`。標準設定(ユーザーが変更できない)は画面案に無い。

## 2. 指示の適用の評価
| 指示 | 評価 | 内容 |
|---|---|---|
| 専用プロジェクトの生成 | 適用できる | 候補は `user_profile`。表示の部品は `app_shell` にあり、取得・変更・設定を `user_profile` が持つ。`CLAUDE.md`・規則は `auth_files` と同じ形で作れる |
| 標準はユーザーが画像を変更できない | 適用できる | 設定(裏設定)の値で切り替える。`isChangeUserImage`(既定 false) |
| 起動時のプロパティ `isChangeUserImage` でユーザーも変更可 | 適用できる | `--dart-define` か裏設定の値で渡す。裏設定の値と起動時の値の優先順位を決める必要がある |
| 管理者が PocketBase のユーザーのファイルとして画像を追加 | 条件付き | 下の「サーバーの制約」 |
| 画像が無いときは既定のデザイン | 適用できる | `avatar.svg` を既定の画像として使う(アセットに追加) |

## 3. サーバー・ライブラリの制約(Issue)
1. `pbapi` の `AuthSession` には `avatar` のファイル名が無い。ユーザー本人の画像は、`users` コレクションの `avatar` 項目(PocketBase 標準のファイル項目)にある。取得するには `users` のレコードを取り直し、ファイルの URL(file token が必要な場合あり)から取得する処理が必要。**`auth_files`/`pbapi` の問い合わせに画像を含める追加が必要。**
2. `AccountService.updateProfile(avatarBytes:)` は本人の画像を変更できる。サーバーの `users.updateRule` は `id = @request.auth.id` で、本人だけが `avatar` を変更できる。**管理者が他人の画像を API から変更することはできない**(superuser の管理画面のみ)。
3. 個人ファイル(`PersonalFileService`、`user_files`)は本人だけが作成・参照できる(`createRule`: `owner = @request.auth.id`)。管理者が他人名義で作ることはできない。また `user_files` コレクションは、現在のサーバーの `pb_migrations` に無い(`pbapi/doc/contents/server_user_files.md` の提案のみ)。
4. 共有ファイル(`app_files`)は全員が参照でき、管理者だけの書き込み制限も無い。ユーザーの写真には使えない。
5. 解決の提案(サーバー側、どれか1つ):
   - A(推奨): `users.updateRule` に管理者の例外を足す(`id = @request.auth.id || ADMIN`、ただし `role`・`app_user_id` などの禁止項目は維持)。標準の `avatar` 項目をそのまま使え、本人にも表示が簡単。
   - B: 管理者専用 API(`POST /api/app/admin/users/{id}/avatar`)をフックで追加する。ルールを広げない。
   - C: `user_files` を用意し、`key: avatar` のファイルを管理者も作れるようにルールを広げる。
6. **ログに残す課題**: 上の 1〜3 は `pbapi`/サーバーの変更を伴うため、実装前に方針の決定が必要。

## 4. アプリケーションの裏設定の評価
| 指示 | 評価 | 内容 |
|---|---|---|
| ログインページから特定の条件で裏設定ページへ移れる | 適用できる | 候補: 特定のユーザーID+パスワード、または「ユーザーIDが空+特定のパスワード+ログインボタンを5秒長押し」。`auth_files` のログインページに入口の判定を差し込む(判定は `auth_files` から呼ぶ契約の型にする) |
| 裏設定ページから他のページへ移動できない | 適用できる | 枠の外のページとして、戻る操作・リンクを持たない(`maintenance` と同じ作り)。出るには「終了」の操作でログインへ |
| アプリの振る舞いを変更する | 適用できる | 初期の項目の候補: ユーザー画像の変更可否(`isChangeUserImage`)。ほかは調査して提案する |
| 平文でなく暗号化して保存。アプリが削除されるまで永続 | 適用できる | `auth_files` が既に `flutter_secure_storage`(OS の保管庫)を使っている(`SecureTokenStore`)。裏設定も同じ保管庫に入れる(JSON)。外部ライブラリの追加は不要 |
| 開発側は JSON または Yaml で変更できる? | 条件付き | アセットに既定値の JSON を置き、保管庫に値があればそれを優先する(開発側は既定値を編集)。実行中の値を Yaml/JSON ファイルから取り込む画面(インポート)も作れるが、平文のファイルが残らないよう取り込み後に削除するか決める |
| 条件(ID・パスワード)の持ち方 | 要決定 | ソースに書くと平文で漏れる。ハッシュ(例: PBKDF2/Argon2)+ソルトをアセットの設定に置き、入力と照合する案(照合値だけがアプリに入る)が妥当 |

### 裏設定の項目の提案(調査結果)
1. ユーザー画像: ユーザーによる変更の可否(`isChangeUserImage`、既定 false)。
2. 接続先: GraphQL の URL、PocketBase の URL(いまは `--dart-define`)。
3. 機能の表示: メンテナンスの確認先 URL、検証用・本番の切替。
4. ログの出力レベル。
5. サイドバーの既定(アイコンのみ)や使用言語の既定の固定。
(1 以外は提案。必要なものだけ採用する。)

## 5. 評価と次の手順の提案
- 全体として実行できる。ただし、画像の管理者追加(§3)は、サーバー側の変更方針(A/B/C)が決まってから。
- 先に進められる順: ① `user_profile` の生成(`CLAUDE.md`・既定の画像・`isChangeUserImage`・自分のイメージの画面、本人変更は `updateProfile`)→ ② 裏設定(暗号化の保管庫+入口+ページ)→ ③ 管理者の画像追加(サーバーの方針決定後)。
- 決めてほしいこと: (a) プロジェクト名 `user_profile` でよいか、(b) 画像の管理者追加はサーバー案 A/B/C のどれか、(c) 裏設定の入口の条件(ID+パスワード / 長押し)と、照合値をハッシュで持つ方針、(d) 裏設定の項目(§4 の提案から採用するもの)。
