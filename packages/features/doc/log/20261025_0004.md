1. **顧客台帳を sales へ統合**: `customer` と `customer_api` を `sales` に統合し、両パッケージを削除した。実装は `sales/lib/src/customer/`。`SalesModule` が区分のモジュール(現状は顧客)を束ねる(Composite)。履歴・過去のログは `sales/doc/log/20261025_0002_customer.md` に移した。

4. **api の分割をやめた**: 下記の方針とし、`apps/pms_app`・`WORKSPACE.md`・ルートと features の `CLAUDE.md` を合わせた。

## xxx_api の評価と代替案
- **別パッケージ `xxx_api` の利点**: pubspec に依存が出るため「実装に依存しない」を機械的に守れる。実装を変えても api に依存する側は再ビルド・再解決されにくい。
- **このプロジェクトでの問題**: 機能が11以上あり、`xxx_api` を全部作るとパッケージが倍(20超)になる。ほとんどの機能は他の機能に契約を公開する必要がない。契約が実際に使われるのは当面 `sales` の顧客(選択・名前の取得)ぐらいで、他に対して空のパッケージを維持するコストが見合わない。
- **採用した代替案**: 1機能=1パッケージのまま、2つのバレルに分ける。`lib/xxx.dart`(実装の入口。アプリだけが読み込み、`XxxModule` のみ公開)と `lib/xxx_api.dart`(遷移先・命令の型だけ。他の機能・アプリが読み込む)。バレル規則(仕様側が機能に応じて選べる)にも合う。
- **弱点と対策**: 守る仕組みが規約になる(pubspec では防げない)。`lib/src` と `xxx.dart` を他の機能が読み込まない、をレビューと lint で確認する。必要になれば、`import_lint` 系のルールや analysis の `depend_on_referenced_packages` 以外の import 制限を追加する。契約が増えて独立させたくなった時点で、`xxx_api` パッケージへ切り出せる(型の移動と import の置換のみ)。
- 別案(不採用): 契約の型を `feature_shared` に集約する。機能が増えるたびに共通パッケージが膨らみ、機能の独立性が下がるため。
