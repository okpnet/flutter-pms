## A. 設定の永続化の提案(Mediator)
ライブラリは保存先を知らず、保存と復元を依頼する窓口だけを持つ。実体(保存先)はアプリが差し込む。
1.  `feature_shared` に `IUserSettingsStore`(`load()`・`save(UserSettings)`)と `UserSettings`(使用言語、サイドバーをアイコンだけ、ユーザー名・役割)を置く。既定の実装は何も保存しない。`userSettingsStoreProvider` をアプリが override する(宣言はライブラリ、実体はアプリ)。
2.  `localeProvider`・`sidebarIconOnlyProvider`・`userSummaryProvider` の変更を窓口([UserSettingsMediator])が受け、`save` を呼ぶ。起動時は `main.dart` で `load()` の結果を各 Provider の初期値として渡す。利用者ごとの保存先(ファイル、`shared_preferences`、GraphQL のユーザー設定)はアプリが選ぶ。
3.  設定画面(app_core)は、保存の有無を知らずに今までどおり Provider を変更するだけにする。
承認いただければ、`feature_shared` に窓口と既定実装、アプリに暫定のファイル保存(Windows)を実装する。

## B. 画面の細部と親の付け替え
`flgtable_lib` の更新後に、検索・列の表示/非表示を `entity_screens` に適用する。親の付け替えは、`entity_screens` はドラッグ&ドロップを受けて、付け替え先を渡すハンドラ(コールバック)を呼ぶだけにし、実際の更新と検証(循環・権限)は利用者(機能側)が実装する。ハンドラが無いときは付け替えを有効にしない。

## D. 重複チェックと JavaScript
- 重複の真実は DB 側(一意制約)にある。JavaScript(`tools/entity_gen/gen.js`)は実行時には関係せず、画面の定義(Dart)を作るときに `UNIQUE` の表を `uniqueKeys` として書き出すだけ。
- 定義の `uniqueKeys` は、メモリ上のサンプルの取得元と画面の事前検証に使う。GraphQL 版では DB の違反を重複のエラー(`EntityFieldError.duplicate`)に変換するだけでよく、定義の `uniqueKeys` は不要になっても構わない。この扱いを `features/CLAUDE.md` の実体の画面 8 に明記した。
- 将来 DB の制約(`06_cteate_test.sql` や `schema.graphql`)から機械的に取れるなら、`UNIQUE` の手書きの表をやめ、制約から読む形にできる。

## E. 配送サービサー(`is_logistics`)
- Html には、配送サービサーの台帳・メニューは含まれない。画面案(`tools/open-design`)では、顧客・外部供給者の項目の1つ(`is_logistics`、「配送サービサー」、はい/いいえ)としてだけ存在する。
- 計画(外部供給者の一部)と一致するため、台帳は作らない。利害関係者の編集画面の項目として、すでに入力できる。
- 残る課題の「配送サービサーの台帳」は取り下げる。担当者のサンプルは、Html に行が無いため空のまま。
