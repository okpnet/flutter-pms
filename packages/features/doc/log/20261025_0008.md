### 1. 共通のシェル部品
- **app_shell**: `MultiMainFrame`(モバイル=ハンバーガー、タブレット/設定=アイコンだけ、PC=通常)、`SingleMainFrame`、`SelectionFrame`。メニューは `AppMenu`(上部の項目 + グループ)で、サイドバーとハンバーガーが共有。ユーザーが無い(ログインしていない)ときはメニューもユーザーも出さない。
- **メニューの提供**: 各機能が `MenuContributor` で `MenuEntry` を返す。同じグループの識別子の項目は1つにまとまる。`shared_master` の配送区分は「営業」「購買」の両方に項目を出す(0005 の課題6の解決)。グループの並び・アイコンは `apps/pms_app/lib/shell_frame.dart`。
- **app_core**: ブート(`/boot`)、エラー(`/error`)、設定(`/settings`)。文字列はアプリの枠(アプリ名・メニューの説明)も含む。
- **レビューしてほしい点**:
  1. 画面の枠の中に、各機能の画面が `Scaffold`/`AppBar` つきでそのまま入るため、タイトルバーが二重になる(枠のバー + 画面のバー)。機能の画面の AppBar を枠の中では出さない、または戻る操作を枠に寄せる案がある。
  2. ログインユーザーは暫定で固定(鈴木 一郎)。認証(Keycloak)の導入までの仮置き。
  3. 設定(言語・アイコンだけ)は保存しない(起動のたびに既定へ戻る)。
  4. ユーザーメニューは「設定」のみ(ログアウトは認証の導入後)。
  5. メニュー項目は `context.go` で開く(枠の中を入れ替える)。CommandBus を通さない遷移になる。

### 3. GraphQL 版(方針の記入が無いため、判明していることを記録)
- 配送区分: `ShippingKindReadFields`/`EditFields` を使う `ShippingKindPage`/`ShippingKindPageEdit` 相当のページ定義を `views` に足し、`gen_view_graphql`(build_runner)で生成する必要がある。生成物ができたら `GraphQLShippingKindRepository` を実装する。
- 共通: `FilterCondition`/`SortCondition` → `Expression` の変換の置き場所、クライアント(エンドポイント・認証・言語ID)の Provider が未定義。

### 4. 利害関係者(顧客・外部供給者)の再提案
- **現在との相違**: `sales` の顧客(専用の画面、メモリ上の3件)と `purchasing` のサプライヤー(生成した実体、別の12件)は、別々のデータになっている。実際は同じ `mstr_stakeholder` を、フラグで顧客・外部供給者・配送サービサーに分けて見るだけ。
- **提案**: 利害関係者(`stakeholder`)と担当者(`contact`)を共有マスタ(`shared_master`)に置く。
  1. 取得元は1つ(`IStakeholderRepository`)。顧客台帳は `is_customer` の絞り込み、外部供給者台帳は `is_supplier` の絞り込み。1人が顧客と外部供給者の両方になれる。
  2. 編集画面(`StakeholderEditFields`)と担当者の子の台帳は1つ。配送区分の選択は同じパッケージ内の `ShippingKindPickerDestination` で行える(0005 の課題5が解決する)。
  3. 契約(`shared_master_api.dart`)に `StakeholderListDestination(role)`・`StakeholderPickerDestination(role)` などを置く。`sales_api.dart` の顧客の型は、移行期間は残して置き換える。
  4. メニューは、営業=顧客台帳、購買=外部供給者台帳、ともに共有マスタの画面を開く。受注・発注などの参照先の選択肢(lookup)は、同じ取得元から役割で絞って登録する。
- 影響: `sales` の `lib/src/customer/` を `shared_master` へ移す。`purchasing` の `supplier`・`suppcontact`(生成)は、生成の対象から外す。移行の規模は中(テスト・example・CLAUDE.md の更新を含む)。承認があれば着手する。
