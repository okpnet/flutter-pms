### 2. 共通のシェル部品を、プロジェクト(パッケージ)にするかの評価と提案
対象: サイドメニュー(サイドバー)、タイトルバー、ハンバーガーメニュー、ログインユーザーコンテナ。

**評価**
- 4つとも、機能の画面ではなく、アプリ全体の枠(メインフレーム)の部品である。サイドバーとハンバーガーは「同じ項目・同じ振る舞いを共有する」(CLAUDE.md の共通画面の仕様)ため、一緒に変える。タイトルバーはハンバーガーの開閉口を持ち、ログインユーザーコンテナはタイトルバーとサイドバーの両方に現れる。変更が連動するので、4つをバラバラのパッケージにする価値は低い。
- 層の規則(`apps` → `features` → `core` → `ui`/`infra` → `foundation`)からは、機能(メニューの項目、ユーザー情報の中身)を知らない見た目の部品は `ui` 層に置くのが妥当。項目の組み立てと権限の判定はアプリ(`pms_app`)側の責務。
- 現状は `pms_app` のホームだけで、メニューの項目を持つ機能(`FeatureModule`)側の口が無い。

**提案(未実施。決定が必要)**
1. **`packages/ui/app_shell` を1つ作る**(4つを1パッケージにまとめる)。
   - 中身: `AppTitleBar`、`SideBar`(モバイル=非表示、タブレット=アイコンのみ、PC=通常。`view_responsiveness` に従う)、`HamburgerMenu`(サイドバーと同じメニューモデルを共有)、`UserContainer`(顔写真・名前・所属と、設定・ログアウトのユーザーメニュー)、メインフレーム(シングル/マルチ)、選択フレーム。
   - 入力は表示用のモデル(`MenuModel`・`UserSummary`)だけにして、機能・認証の実体を知らない。色・サイズは `theme_lib`。
2. **メニュー項目は各機能が提供する**。`FeatureModule` に「メニュー項目(グループ・ラベル・アイコン・遷移先)」を足す案。アプリが項目を集め、Html の並び(ダッシュボード → 資源 → 業務グループ → 会社情報)に整える。これで「配送区分は営業と購買のどちらからも開く」(0005 の課題6)も、`shared_master` が両グループの項目を宣言することで解決できる。
3. **ログインユーザーの実体は `app_core`(AppCore の機能プロジェクト)に置く**。ブート・ログイン・ログアウト・エラー・設定の画面と、ログイン状態の Provider。`app_shell` の `UserContainer` へは `UserSummary` を渡すだけにする(`ui` 層が認証に依存しない)。
4. `FeatureHost`(example 用)は、`app_shell` ができたら同じ枠を使うよう差し替えられる。
- 代替案(不採用): 4つを `pms_app` の中に置く。小さく始められるが、example(機能の単体確認)で同じ枠を再利用できない。

## 20261025_0005.md の提案・課題の解決
1. **UUID を文字列で扱う**(採択)。全体への影響を評価し、`String` を採用した。
   - 理由: GraphQL の UUID は生成コードで文字列。GoRouter のパスのパラメータも文字列。`baton_lib` の命令・遷移先は JSON 化する(エラー追跡)ため文字列が扱いやすい。`int` のままだと、変換と不整合の元になる。
   - 影響: `shared_master`・`sales` の遷移先・命令・モデル・パス・リポジトリ・テスト・`pms_app` の表示を `String` に変更した。新規採番は `uuid`(`^4.6.0`)の v4。サンプルの id は固定の UUID 文字列。
2. **GraphQL で取得する**(採択)。**未実施**。理由:
   - `graphql_provider_lib` に配送区分の画面定義(`ShippingKindPage` 相当)が無い。`source/page.md` に項目(`ShippingKindReadFields`)はあるが、`views/sales/shipping_kind.yaml` に `kind: read` の画面としての定義が無く、`lib/postgraphile` に生成物が無い。先に graphql_provider_lib 側で画面定義を追加し、`build_runner` で生成する必要がある(別プロジェクトの作業)。
   - 通信は `gqlib` の `GraphQLClientProvider` を使う。クライアントの Provider(エンドポイント・認証ヘッダー・言語ID)は未定義。認証(Keycloak)は未導入。
   - 手順案: ① `ShippingKindPage`/`ShippingKindPageEdit` を yaml に追加して生成 → ② `GraphQLShippingKindRepository implements IShippingKindRepository` を `shared_master` に追加(`find` でサーバー側のフィルタ・ソート・ページング、名称辞書の値を平らにする)→ ③ アプリが `shippingKindRepositoryProvider` を差し替える。顧客(`CustomerPage`)は生成物が既にあるので、同じ手順で先に進められる。
   - `FilterCondition`/`SortCondition`(`flgtable_lib`)から `Expression`(`query_builder`)への変換が必要。変換の置き場所を決める必要がある(提案: `data_strategist` 側か、機能ごとのリポジトリ)。
3. 列ラベルは仮(採択)。言語ファイルに置いた。`schema.graphql` にコメントが付いたら置き換える。
4. 削除時の参照チェック(採択)。`IShippingKindRepository.remove` は使用中のとき `ShippingKindInUseException` を投げ、画面は「使用中のため削除できません」を表示する(ログには残さない)。`InMemoryShippingKindRepository` は `isInUse` を差し込める。実際の判定は、GraphQL 版で外部キー違反をこの例外に変換して行う。
5. 顧客の編集と配送区分の選択の接続(採択)。`packages/features/CLAUDE.md` と `sales/CLAUDE.md` に条件として追加した。
6. 配送区分の開き方(採択)。トップメニューの「営業」「購買」から選択して開く。`packages/features/CLAUDE.md` と `shared_master/CLAUDE.md` に条件として追加した。メニュー自体は上記の提案(`app_shell` とメニュー項目の提供)の決定後に実装する。
7. slang による多言語化(採択)。`sales` と `shared_master` に導入した。
   - 言語ファイルは Yaml(`lib/src/i18n/ja.i18n.yaml` が基準、`en.i18n.yaml`)。設定は各プロジェクトの `slang.yaml`(`class_name` は `SalesStrings`・`SharedMasterStrings`)。生成は `dart run slang`。
   - 言語は Riverpod で注入する。`feature_shared` に `localeProvider`(既定は日本語)を追加し、`salesStringsProvider`・`sharedMasterStringsProvider` が従う。slang の Flutter 連携とグローバル変数は使わない。
   - 基準言語以外は slang が遅延読み込みで生成する。読み込みが終わるまでは日本語を返し、終わったら差し替える。
   - エラーは種類(enum・例外の型)で持ち、画面が表示時に文字列へ変換する。ログの文言は対象外。
   - ワークスペースのルート `pubspec.yaml` の `melos > bootstrap > dependencies` に `slang: ^4.19.2` を追加した(`uuid` は既存)。
   - 残る11プロジェクトは画面を作るときに導入する(`CLAUDE.md` に記載)。
