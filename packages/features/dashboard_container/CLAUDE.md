# dashboard_container

ダッシュボードに表示するための件数のコンテナ(ウィジェット)。レコード数の合計を、幅(Full・1/2・1/4)に応じた数だけ表示する。`packages/features/CLAUDE.md` の[規則/仕様]を必ず適用する。
プロジェクト名は、ダッシュボードに置くコンテナであることから `dashboard_container` とした。ダッシュボードのページ(`app_core`)は、この領域(`DashboardContainerArea`)を置く。

## 仕様
1.  大きさは Full・1/2・1/4(`CountContainerSize`)。1つのコンテナに並べる件数の項目(タイル)は、Full が3つ、1/2 が2つ、1/4 が1つまで表示する(並べた項目の先頭から)。
2.  項目1つにつき、フィルタグループ(区分、利害関係者(顧客・外部)など)を1つ対にする(`CountTileSpec.groupKey`)。選んだ項目(`optionKey`、null は「すべて」)の件数を表示する。選択は項目のメニューから変える。
3.  配置(コンテナの並び・大きさ・項目・選んだフィルタ)は設定として保存し(`page_mediator_extension` の設定の窓口、`settings_keeper`)、ダッシュボードを表示するタイミング(`DashboardContainerArea` の表示時)で設定から読み込む。保存する形は `DashboardContainerSettings`(JSON)。保存先はアプリが決める。
4.  領域の幅に応じて並べる。Full は全幅、1/2 は 1/2、1/4 は 1/4(隙間を除く)。狭い画面(既定は幅 600 未満)では、どのコンテナも全幅にする(項目の数は大きさのとおり)。
5.  件数の元(`ICountSource`)は、機能・アプリが提供して `countSourcesProvider` へ差し込む。`RepositoryCountSource` は、件数を返す取得元(`IDataRepository<int>`、GraphQL の `totalCount`)から `page_mediator_extension` のデータ取得で数える。元が登録されていない項目は「未設定」と表示する。
6.  配置の編集は `DashboardContainerEditor`(コンテナ・項目の追加・削除、コンテナの並び替え・大きさ、項目の元とフィルタグループ)で行い、変更はすぐに設定として保存する(`dashboardContainersProvider` の `addContainer`・`removeContainer`・`moveContainer`・`setSize`・`setTiles`)。1つのコンテナに並べられる項目は 3つまで。大きさの上限を超える項目は「表示しない」と注記する。ダッシュボードのページ(`app_core`)が、領域と編集を切り替えて置く。

## 構成
| 種別 | ファイル | 内容 |
|---|---|---|
| 実装の入口 | `lib/dashboard_container.dart` | 契約の入口を公開する |
| 契約の入口 | `lib/dashboard_container_api.dart` | 件数の元・フィルタグループ・配置の型と、ダッシュボードに置く部品(領域・編集)・配置の状態。このプロジェクトは部品を提供するため、部品も契約に含める(`app_core` などは、こちらだけを読み込む) |
| 型 | `lib/src/model/` | 配置(`CountContainerSpec` など)・件数の元 |
| 設定 | `lib/src/settings/` | 保存する形・持ち主・状態(Provider) |
| 画面 | `lib/src/view/` | 領域・コンテナ・項目 |
| 文字列 | `lib/src/i18n` | slang の Yaml(日本語・英語) |

##  規則
1.  ディリクトリ/ファイル
    1.  生成結果のレポートは`doc/log`ディリクトリにファイル名`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  同じ年月日、同じ番号に対する追加変更は`年月日_4桁ゼロ埋の番号_add_1からの連番.md`として保存する。
    2.  生成したライブラリに関する使い方やヘルプなどの使用にかかわるレポートは`doc/contents`の保存する。
    3.  最終的にこの`CLAUDE.md`へ統合される追加、変更の指示は`issue`ディリクトリに`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  つまり`生成結果のレポート`と連動する。
        2.  `CLAUDE.md`への統合も指示に含める。統合時、削除指示が無い限り`issue`ディリクトリ`doc/log`ディリクトリの中を削除しない。`CLAUDE.md`には変更や追加、削除であることについて記録しない(生成時に`issue`ディリクトリ`doc/log`ディリクトリを参照するため)。
    4.  細分化した機能別に`lib/`以下のディリクトリを2階層を限度(`lib/xxx/xxx`)として分ける。細分化の程度は、2階層になる程度の抽象度とする。
        1.  細分化する機能が少ない(5以下)のとき、1階層で良い(`lib/xxx`)。
2.  命名規則
    1.  ファイル名、クラス名など名前付けのルールはFlutterの規則、慣例に従う。
    2.  クラス名はデザインパターンがわかる、または意味が通る英語の名詞とする。ただし、`はい/いいえ`のような`isXxxx`などの`is/as/has`の慣例を優先する。
        1.  `Command`などデザインパターンのみの名前だと誤解や衝突を招くため、機能、動きの名詞化したものと組み合わせる。
    3.  プリフィクスにライブラリ名をつけない(BatonLibXXのような)。
3.  バレルファイルを使用する
    1.  バレルファイルにまとめ、このライブラリを使用する側は1行を読み込むだけで解決できるようにする。ただし、相互に関連が無い独立した機能の場合はバレルファイルを分けて、仕様側が機能に応じて選択できるようにする(例えば、ファイル参照機能と計算機能があり、計算機能がファイル参照を行わない場合は別々にする)。ただし、 ユーザーの仕様体験を優先する。ライブラリ全体の機能が少ない(10以下)ときにインポートするファイルを分ける必要はない。
4.  インスタンスのJSON化
    1.  生成するこのライブラリのインターフェイス、クラスのインスタンスをJSONにコンバートできる。ただし、エラー追跡のためであり、現時点で機能を復元する目的では使用しない。
5.  ログを残す
    1.  ライブラリは実行したときのログを残す。ただし、このライブラリ側のエラーログがけを残し、実行側のアプリケーションがどの実行でエラーが発生したか調査するとき、機能毎のライブラリ側なのかを切り分け可能にするために、適切に選別する。
    2. ロガーはRiverpodから提供され、アプリケーション全体をとおして同じ仕様のログ出力を行う。
6.	GOFデザインパターン
	1.	クラス名やファイル名にデザインパターンを含めない場合は、コメントに該当するパターン名を追加する。
	2.	必ずしもデザインパターンに割り当てる必要はない
