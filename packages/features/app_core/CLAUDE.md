# app_core

アプリの基盤(ブート・エラー・設定・ログアウト)の実装。`packages/features/CLAUDE.md` の[規則/仕様]を必ず適用する。
画面の枠(タイトルバー・サイドバー・ハンバーガー・ログインユーザー)の見た目は `packages/ui/app_shell` が持ち、このプロジェクトはその文字列(アプリ名・メニューの説明・設定)と、基盤の画面を持つ。

## 画面(Html のメニュー・features/CLAUDE.md の AppCore)
1.  ブート画面(シングルメインフレーム): 読み込み中の表示。`/boot`
2.  エラー画面(シングルメインフレーム): アプリケーションエラーの表示。`ErrorDestination({message})` → `/error`
3.  設定(マルチメインフレーム): 使用言語(実行環境に従う/日本語/English)、サイドバーをアイコンだけにする設定、ログインユーザー(ユーザー名・役割を設定値として与える。標準値へ戻せる)、バージョン情報(`--dart-define=APP_VERSION=x.y.z`)。`SettingsDestination` → `/settings`。使用者全体ではなく、使用ユーザーにだけ影響する設定
4.  ログアウト画面(シングルメインフレーム): `LogoutDestination` → `/logout`。ユーザーメニューの「ログアウト」で開く。認証の導入までは、仮のボタンで標準のユーザーに戻す
5.  ログイン画面: 認証(Keycloak)の導入後に追加する(未実装)。ログイン状態は `userSummaryProvider`(`feature_shared`)で提供する

## 構成
| 種別 | ファイル | 内容 |
|---|---|---|
| 実装の入口 | `lib/app_core.dart` | 公開は `AppCoreModule` と、アプリが使う文字列(`appCoreStringsProvider`) |
| 契約の入口 | `lib/app_core_api.dart` | 遷移先の型(`SettingsDestination`・`LogoutDestination`・`ErrorDestination`) |
| モジュール | `lib/src/app_core_module.dart` | ルートと遷移先の変換 |
| 画面 | `lib/src/pages/app_core_pages.dart` | ブート・エラー・ログアウト・設定 |
| 文字列 | `lib/src/i18n` | slang の Yaml(日本語・英語) |

## 実装の指針
1.  設定の変更は `feature_shared` の Provider(`localeProvider`・`sidebarIconOnlyProvider`)へ反映する。保存と復元は`feature_shared`の`UserSettingsOriginator`(`settings_keeper`のメメント)が行い、保存先はアプリが決める。
2.  使用言語の既定は実行環境(OS)の言語(アプリが `SystemLocaleNotifier` を差し込む)。
3.  ログは `logger_provider` の `loggerProvider` を `ref` から直接取得し、この機能が発生元のエラーだけを出す。

## example と多言語
1.  ビジュアルテスト用の `example` は、画面を増やすときに追加する(現状は `test/` の `FeatureHost` を使ったテストで確認している)。
2.  文字列は `lib/src/i18n` の言語ファイル(Yaml)に置き、`slang.yaml` の `class_name: AppCoreStrings` で生成する(`dart run slang`)。

## 規則/仕様
1.  ディリクトリ/ファイル
    1.  生成結果のレポートは`doc/log`ディリクトリにファイル名`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  同じ年月日、同じ番号に対する追加変更は`年月日_4桁ゼロ埋の番号_add_1からの連番.md`として保存する。
    2.  画面イメージ(HTML)や使い方などは`doc/contents`に保存する。
    3.  最終的にこの`CLAUDE.md`へ統合される追加、変更の指示は`issue`ディリクトリに`年月日_4桁ゼロ埋の番号.md`として保存する。
        1.  つまり`生成結果のレポート`と連動する。
        2.  `CLAUDE.md`への統合も指示に含める。統合時、削除指示が無い限り`issue`ディリクトリ`doc/log`ディリクトリの中を削除しない。`CLAUDE.md`には変更や追加、削除であることについて記録しない(生成時に`issue`ディリクトリ`doc/log`ディリクトリを参照するため)。
2.  命名規則
    1.  ファイル名、クラス名など名前付けのルールはFlutterの規則、慣例に従う。
    2.  クラス名はデザインパターンがわかる、または意味が通る英語の名詞とする。ただし、`はい/いいえ`のような`isXxxx`などの`is/as/has`の慣例を優先する。
        1.  `Command`などデザインパターンのみの名前だと誤解や衝突を招くため、機能、動きの名詞化したものと組み合わせる。
    3.  プリフィクスにライブラリ名をつけない(BatonLibXXのような)。
3.  バレルファイルを使用する
    1.  バレルファイルにまとめ、このライブラリを使用する側は1行を読み込むだけで解決できるようにする。ただし、相互に関連が無い独立した機能の場合はバレルファイルを分けて、仕様側が機能に応じて選択できるようにする。ただし、ユーザーの使用体験を優先する。ライブラリ全体の機能が少ない(10以下)ときにインポートするファイルを分ける必要はない。
4.  インスタンスのJSON化
    1.  生成するこのライブラリのインターフェイス、クラスのインスタンスをJSONにコンバートできる。ただし、エラー追跡のためであり、現時点で機能を復元する目的では使用しない。
5.  ログを残す
    1.  ライブラリは実行したときのログを残す。ただし、このライブラリ側のエラーログだけを残し、機能毎のライブラリ側なのかを切り分け可能にするために、適切に選別する。
    2.  ロガーはRiverpodから提供され、アプリケーション全体をとおして同じ仕様のログ出力を行う。
6.  GOFデザインパターン
    1.  クラス名やファイル名にデザインパターンを含めない場合は、コメントに該当するパターン名を追加する。
    2.  必ずしもデザインパターンに割り当てる必要はない。
