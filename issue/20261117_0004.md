# 20261117_0004 共有ファイルの保存の流れ(DB の ID を先に得て、PocketBase へバイナリと一緒に渡す)

## 仕様(利用者の確認どおり)
1.  `trans_file` を先に INSERT し、DB が採番した `trans_file_id` を得る。
1.  その ID を PocketBase の `app_files.app_file_id` にして、ファイルのバイナリと同時に渡す(アップロード)。
1.  DB の主キーは、全表のトリガー(`trg_01_updatetimes_<表>`)が INSERT のたびに採番し、クライアントが渡した値は無視される(DB の仕様。CLAUDE.md の「登録・更新の方式」に追記)。そのため、順番は「DB → PocketBase」になる。

## 再調査の結果: PocketBase 側の列の追加は要らない
1.  `app_files` には、もともと `app_file_id`(text・必須・最大 64 文字・`^[A-Za-z0-9_-]+$`。「App DB 側のファイル管理 ID。同じ ID で複数の版を持てる」)がある(`tools/docker/pocketbase/pocketbase/pb_migrations/1762041600_init_schema.js`)。
1.  UUID(36 文字・ハイフン入り)は、この条件に入る。`pbapi` の `SharedFileService` の ID の検査(`^[A-Za-z0-9_-]{1,64}$`)も同じで、UUID を渡せることをテストで確認した(`pbapi_test.dart`)。
1.  フックは `uploaded_by`・`revision`・`original_name`・`size_bytes` を自動で入れる。`trans_file_id` に当たる情報は `app_file_id` で持てるので、列の追加・サーバーの変更は無し。
1.  実サーバー(PocketBase)への実際のアップロードの確認は、管理者(superuser)の資格情報が要る結合テスト(`pocketbase_integration_test.dart`。後始末の削除が superuser だけのため)で、今回は実施していない。

## 実装(前の暫定案は取り下げ)
前回の暫定(`trans_file.binary_data` に PocketBase の ID を入れる)は、取り下げた。`binary_data` は空文字のまま使わない。
1.  選ぶ: `IEntityFileTransfer.pick()`。保存先へは上げず、窓口がバイナリを預かり、仮の ID(`pending:…`。`EntityFile.isPending`)を返す。
1.  保存(取得元。基準の実装は `quality` の `ComplaintFileRepository`): ① `trans_file` の行を作って ID を得る → ② `IEntityFileTransfer.upload(picked, trans_file_id)` で、その ID を `app_file_id` にして PocketBase へ上げる(`pms_app` の `PocketBaseEntityFileTransfer`) → ③ `trans_complaint_file` でつなぐ。
1.  ② が失敗したら(PocketBase のアップロードの失敗を捕まえたとき)、① の行を論理削除して失敗にする(つながない)。③ が失敗したときも、① の行を論理削除する。PocketBase に上がったファイルだけは、利用者の権限では削除できない(`app_files` の更新・削除は superuser だけ)ため、参照されないまま残る。
1.  読む・ダウンロード: 画面の値(`EntityFile.id`)は `trans_file_id`(= `app_file_id`)で、そのままダウンロードする。差し替えは、新しい行・ファイルを作って付け替える(PocketBase は上書きしない)。
1.  テスト: `quality` の `complaint_file_test.dart`(実サーバーの DB で、保存の順・DB の ID で上がること・差し替え・取り消し・上げる失敗の取り消し。保存先は代役)。

## 捕まえられない場合の代案
アプリの強制終了・通信の断などで、① のあと(② の失敗・③ の失敗の取り消しの前)に処理が止まると、論理削除できない。その場合に残るもの: ① の行(有効のまま。どこからも参照されない)、PocketBase のファイル(上がっていれば)。
1.  代案 A: 参照されない `trans_file` の行(どの `trans_*_file`・`mstr_*` からも `trans_file_id` で参照されず、一定時間より古い)を探して論理削除する掃除(管理者の操作またはサーバー側の定期ジョブ。DB の関数 1 本)。
1.  代案 B: PocketBase のファイルの掃除は、管理者が `app_file_id` が DB に無い(または論理削除済みの)ファイルを一覧して削除する(superuser の操作。PocketBase のフックでも可能)。
推奨: 当面は何もしない(残るのは少量)。件数が増えたら A・B を足す。

## 調査: ロールバックで解決できるか(「トランザクション開始 → ID 取得 → アップロード → 失敗 → ロールバック」)
結論: **この構成では、その流れは再現できない**(DB と PocketBase が別のシステムで、アプリは HTTP でしか触れないため)。確認した事実:
1.  PostGraphile v4 は、1 回の HTTP 要求(= 1 つの GraphQL ドキュメント)を 1 つのトランザクションにする。要求をまたいで開いたままにはできない(「ID 取得」と「アップロードの結果」は別の要求になり、間でトランザクションは終わっている)。同じ要求の中の入れ子の登録は 1 トランザクション(実測済み)だが、その中で PocketBase へ上げることはできない。
1.  DB 側から PocketBase を呼べば、1 つのトランザクションにできる(アップロードが失敗したら、関数が例外を投げて自動でロールバック)。しかし、テスト環境の PostgreSQL 15(標準イメージ)には、HTTP を呼ぶ拡張(`http`・`pg_net`)も、手続き言語(`plpython3u` など)も入っていない(入っているのは `plpgsql`・`pgcrypto` だけ。`dblink`・`postgres_fdw`・`file_fdw` は入れられるが、HTTP は呼べない)。入れるにはイメージの作り直しが要る。さらに、バイナリを GraphQL → DB 経由で渡すことになり(`binary_data` に base64)、アップロード中ずっと DB のトランザクションと接続を持つ(大きなファイルで長くなる)。方針(バイナリは PocketBase にだけ置く)にも合わない。
1.  2 相コミット(`PREPARE TRANSACTION`)は、`max_prepared_transactions = 0`(無効)で、PostGraphile からも使えない。PocketBase 側も参加できない。

### 代案(強さの順)
| 案 | 内容 | 残るもの | 費用 |
|---|---|---|---|
| 現状(補償) | 失敗を捕まえて `trans_file` を論理削除 | 強制終了などで捕まえられないとき、DB に参照されない行 | 実装済み |
| A | 参照されない `trans_file` を後から掃除(DB の関数 1 本) | 上と同じ(一定時間後に消える) | 小 |
| E | PocketBase にサーバー側の経路(フックの自前の API)を置き、PocketBase が PostGraphile を呼んで行を作り、失敗したら同じ経路の中で取り消す。クライアントが途中で止まっても、サーバーが最後まで行う | サーバーの停止のときだけ | 中(PocketBase のフック・JWT の受け渡し) |
| F | 順序を入れ替える: 先に PocketBase へ上げ(`app_file_id` はクライアントが作った UUID)、そのあと DB へ `trans_file` + つなぎを 1 回の入れ子の登録(1 トランザクション)で登録する。DB は全部成功か全部ロールバック | PocketBase に参照されないファイル(DB には何も残らない。`app_file_id` で突き合わせて掃除できる) | 中(`trans_file` のトリガーが渡された主キーを使う必要がある=全表の方針の例外。または `app_files` に DB の ID を後から結びつける列を足す) |
推奨: 当面は現状 + A。DB に孤児を残したくないなら F(PocketBase の孤児は、DB の行が無いので無害で、増えても参照されない)。E は、強制終了への耐性が要るときの選択。F は、利用者の指定(「trans_file を先に INSERT」)と順序が変わるため、採択の判断を求める。
