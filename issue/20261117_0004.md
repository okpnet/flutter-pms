# 20261117_0004 DB の主キーはトリガーが採番する(共有ファイルの ID の決め方)

## 事実(実測)
1.  全 262 表の `trg_01_updatetimes_<表>` が、INSERT のたびに `NEW.<主キー> := gen_random_uuid()` で主キーを上書きする。クライアントが `create…` の入力に主キー(例: `transFileId`)を渡しても、無視される(実測: `createTransFile` に渡した ID と、返った ID が違う)。
1.  このため、CLAUDE.md にあった「ID はクライアントで作れる(主キーは uuid)」は誤りで、「登録の応答で返った ID を使う」に直した。
1.  共有ファイルは、画面がファイルを選んだ時点で、新しい UUID を作り、その UUID を PocketBase のファイル ID(`appFileId`)にして上げる(`entity_screens` の `FieldKind.file`・`IEntityFileTransfer`)。DB の `trans_file_id` を PocketBase の ID にする設計(`20261117_0003.md` の 1 の前提)は、このままではできない。

## 実施した暫定の対応(DB の変更なし)
`trans_file.binary_data`(text・NOT NULL。使われていない列)に、PocketBase のファイル ID を入れる。`trans_file_id` は DB が採番した値のまま、`trans_complaint_file` などの FK はこの値を使う。画面の値(`EntityFile.id`)は PocketBase の ID(= `binary_data`)で、ダウンロードはこの ID で行う。基準の実装: `quality` の `ComplaintFileRepository`(通信テスト `complaint_file_test.dart`。登録 → 一覧 → 差し替え → 取り消し)。

## 判断が要る点(提案)
| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A(暫定。実施済み) | `binary_data` に PocketBase の ID を入れる | DB の変更なし。画面の流れは変わらない | 列名と中身が合わない(列のコメントで補う) |
| B | `trans_file` のトリガーだけ、渡された主キーを使う(`COALESCE(NEW.trans_file_id, gen_random_uuid())`) | 画面の UUID = DB の ID = PocketBase の ID で一貫する | 全表で上書きする方針の例外になる。PERO のデータ・06 の変更が要る |
| C | 列 `binary_data` を `app_file_id`(PocketBase のファイル ID)に改名する | 意味が合う | 既存のモデル(`FilePage` など)の再生成が要る |
| D | 先に `trans_file` の行を作って DB の ID を得てから、その ID で PocketBase に上げる | トリガーの方針のまま | 画面の流れが変わる(選んだ時点で DB に行ができる。キャンセルで孤児の行が残る) |

推奨: 短期は A のまま。続けるなら C(列の意味を合わせる)。B は、全表の方針を変えるため、採択の判断を求める。

## 影響範囲
1.  `trans_file` を持つ他の表(`trans_inspect_imp_file`・`trans_complaint_file` ほか。ファイルを持つ機能の取得元)は、同じ方法で取得元を作る(`ComplaintFileRepository` を基準にする)。
1.  `info_staff_icon`・設備タグ(`mstr_equipment_tag`)の `trans_file_id` も同じ。
