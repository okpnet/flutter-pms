# 20261125_0005 文書管理の簡素化(文書レベルの要否・調査と計画)

目的: 文書のメニューを、Wiki のように、1 つの画面から分岐する形に簡素化する。利用者の認識(2.1〜2.5)と、今の実装・DB を突き合わせた調査。実装は、方針の確認後。

## 1. 文書レベル(`mstr_document_tier`)は必要か
**調査の結果: 画面としては不要。DB では必須の参照だけが残っている。**
1.  DB(`06_cteate_test.sql`)で使われているのは、`mstr_document.mstr_document_tier_id`(NOT NULL の外部キー)と、件数のビュー `v_document_tier_document_count` だけ。**関数・トリガー・ビューは、階層番号(`tier_number`)・管理番号識別子(`identifier`)・限定名詞(`attributive_noun`)を使っていない**(承認・公開・スタンプの判定も使わない)。
1.  アプリ: `manual` の `GraphqlManualRepository._rootTierId` が、ルートの文書を作るときに、階層番号が最小の文書レベルを選んで入れるだけ(利用者は選ばない。マスタが空だと作れず `rootTierMissing`)。管理番号は利用者が決める(識別子から作らない)。
1.  画面案の意図(`domains.base.js`): 文書を「木」にして、品質マニュアル(レベル 1)→ 検査規程(レベル 2)→ 受入検査手順(レベル 3)のように、**文書が親子になる ISO の文書体系**を表すための段。ところが、いまの `manual` は「親の無い文書だけ」をルートとして出し、親のある文書は出さない。**Wiki(ルート → ページの木)では、段は木の深さで表せるため、別のマスタは冗長**。
1.  判定: 文書レベルは、利用者が選ぶ・見る必要のない項目。残す価値があるのは、管理番号の接頭(`identifier`。M・P・F)を提案するくらい。
1.  **提案**: ① メニューの「文書レベル」を外す(台帳の画面・ルートは残し、管理者の設定の入口に置く)。② ルートの作成は、いまのとおり階層番号が最小のレベルを自動で使う(選ばせない)。マスタが空でも作れるように、初期データに標準の 3 つ(`07_dummy.sql` 済み。本番の初期データにも入れる)。③ DB の NOT NULL をなくすかは、PERO の変更(`mstr_document_tier_id` を NULL 可にする)として別に判断(いまは、標準の 1 つを自動で入れて困らないため、急がない)。④ 「文書レベル」の名称は、設定の入口での呼び名として残す(先に実施した名称の変更はそのまま)。

## 2. 認識(2.1〜2.5)と今の実装の対応
| # | 認識 | 今の実装 | ずれ・必要な対応 |
|---|---|---|---|
| 2.1 | 文書は台帳表示 | メニューは「マニュアル」(ルートごとに 1 項目)。文書の台帳(`doc`)・コンテンツ(`doccontent`)はメニューから外してある(リンク・承認の対象としてだけ残る) | **文書の台帳が入口に無い**。ルートごとの項目が増えると、メニューが増える。→ 「文書」の 1 項目に、台帳(管理番号・名称・版・状態(公開 / 承認待ち)・更新日)を出す |
| 2.2 | 台帳から選ぶ。承認があるものは閲覧、承認がないものは閲覧できないが編集はできる | 公開の判定は DB のビュー `v_document_publication`・`v_document_content`(`readable`: 公開済み、または承認の段の該当者、または管理者)。承認待ちの文書は、読める人にだけ中身を返し、「承認待ち」の帯を出す。編集は管理者だけ | ① 「承認がないものは閲覧できない」は、いまの `readable` と**同じ向き**(公開前は一般の利用者に見せない)。② 「編集はできる」= **編集者は承認待ち(下書き)の文書を、閲覧画面ではなく編集の画面で開ける**。いまは、編集者でも承認待ちを開くと「承認待ち」の帯つきの閲覧になる。→ 編集者には、編集の状態(`edit=1`)で開く(閲覧は公開のあと) |
| 2.3 | 編集できるのは権限がある人のみ | 管理者だけ(`manualIsAdminProvider`) | **編集の権限を、アクセス権へ移す**: アクセスパス(`/manual`)の許可の書き込み(`write`。部署・担当者のアクセス権。`20261125_0003` の 6 の「アクセス権設定」で設定)を、編集の権限とする。管理者は常に編集できる。取得元の `isAdmin` の検査は、「編集の権限があるか」に変える(`ManualError.notAdmin` → `notEditor`)。DB は、文書の表への書き込みを守らない(D-1 の RLS は保留)ため、画面と取得元の検査だけになる |
| 2.4 | 閲覧の画面はマニュアルを参照 | `manual` の閲覧(`ManualViewPage`。目次・検索・本文・PDF・承認スタンプ) | ずれなし。台帳(2.1)から、ここへ分岐する(`/manual?id=<文書の ID>`) |
| 2.5 | 編集が終わった文書は、承認の申請ができる(通知のみ)。New? | **登録が申請**: 文書の登録(BEFORE INSERT のトリガー `trg_01_approval_request_*` → `approval_start`)で、承認の実行と段ごとの承認前を作り、**最初の段の該当者へ通知する**(登録した時点で申請になる)。編集中(下書き)の状態が無い | **ずれ**。登録した瞬間に通知が飛ぶため、「編集が終わってから申請」にならない。→ 下の 3 の案 |

## 3. 申請(2.5)の案(DB の変更。決定後に PERO へ)
1.  **案 A(推奨・小さい変更)**: 承認の実行(承認前の行)は、いまどおり文書の登録で作る(公開の判定は変えない。承認前が残る間は `pending`)。**通知だけを申請の操作に移す**: 登録のトリガーからは通知を出さず、DB 関数 `document_request_approval(p_document_id)`(VOLATILE。1 トランザクション。冪等: すでに通知した段には出さない。担当者は引数、省略時は JWT の `staff_id`)が、最初の順位の段の該当者へ `approval_notify` で通知する。画面は、編集の画面(または台帳)の「承認を申請」ボタン。承認の順序・一括承認・承認一覧は、いまのまま(`approval`)。再申請(版が変わった後)も同じ関数。
1.  案 B: 下書きの boolean(`draft`)を文書に足し、申請で false にする。公開の判定・承認の開始も申請のときに行う(登録 → 申請の 2 段)。変更が大きい(R1 は満たす)。
1.  案 C: 申請の操作を作らず、いまのまま(登録 = 申請)。編集が終わる前に通知が飛ぶ。
1.  申請の記録: 「いつ・誰が申請したか」は、通知(`trans_announcement`。区分 `approval`・対象は承認前)に残る。別の列は足さない(追記のみの原則)。
1.  「通知のみ」の意味(確認したい): 申請 = 承認する人への通知だけ(承認自体は、承認の画面で、承認する人が行う)でよいか。

## 4. 簡素化した画面の形(提案)
1.  メニュー: 運用と改善 → **文書**(1 項目)。ルートごとの「マニュアル」の項目は、台帳に集める。台帳の「新規」で文書(ルート)を作る(管理番号を入れる。文書レベルは自動)。
1.  **台帳**(文書): 管理番号・名称・版・状態(公開 / 承認待ち。文字はビュー `v_document_publication` の値)・更新日。承認待ちは、読めない人には出さない(`readable`)。行を押すと、閲覧(公開済み)または編集(編集者が承認待ちを開くとき)へ。
1.  **文書の画面**(`manual` の `ManualViewPage`): 閲覧・編集・履歴・PDF・承認スタンプ・「承認を申請」(編集者のみ)を、同じ画面から分岐する(Wiki と同じ)。
1.  文書階層・レポート・承認スタンプと PDF の設定は、管理者の設定へ(文書のメニューには出さない。文書レベルの台帳もここ)。

## 5. 実施の順(確認後)
1.  `manual`: 台帳の入口(メニューの 1 項目化。台帳 → 閲覧 / 編集の分岐。編集者は承認待ちを編集で開く)。テスト: `manual`・example。
1.  編集の権限をアクセス権へ(`/manual` の書き込み。取得元の `isAdmin` の検査を置き換え。`pms_app` の `manualOverrides`)。テスト: `manual`(編集者・閲覧者・管理者)・`access_control`。
1.  承認の申請: DB 関数 `document_request_approval`(PERO → `06` → DB に適用 → `gql:schema` → `document_approval_model` に `~PageCall` → 画面の「承認を申請」)。SQL テスト。登録のトリガーの通知の移動(`trg_05_approval_request`)。
1.  メニュー整理: 文書レベル・レポート・設定を管理者の設定へ。`quality_document`・`document_settings` のメニュー。画面案(`tools/open-design`)のメニューも同じに直す。
1.  順 3 の「アクセス権設定」(`20261125_0003` の 6)・順 8(example の文書と承認)と一緒に進めると、example で確認できる(編集の権限・承認待ち・申請の通知)。

## 6. 決めてほしい点
1.  文書レベル: 画面(メニュー)から外し、設定の入口へ移す案でよいか(DB の参照は残す)。
1.  承認の申請: 案 A(通知を申請の操作に移す)でよいか。「通知のみ」の意味は上のとおりでよいか。
1.  編集の権限: アクセス権の書き込み(`/manual`)で決めてよいか(管理者は常に可)。
1.  承認待ち(下書き)の文書: 編集者には編集の状態で開く、一般の利用者には出さない(`readable` のとおり)でよいか。
