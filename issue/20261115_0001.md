# 20261115_0001 登録・更新の方式(関数とミューテーションの使い分け)

指示(2026-11-15)。ルートの `CLAUDE.md` の「登録・更新の方式」に統合する。

## 指示
1.  共通のもの(呼称・文章・ラベルなど、複数の表にまたがる部品)は、DB 関数にする。
1.  マスタ・Info・trans は、極力ミューテーション(PostGraphile の自動 CRUD の create・update)で対応する。マスタごと・テーブルごとの保存関数は作らない。
1.  ただし、2 を実行したときに複数の表にまたがり、影響が大きいもの(例: MRP、棚移動)は、関数にする。

## 理由
- Info・マスタは、同時に変更される可能性が低く、影響が限定的。
- trans は、棚移動が同時に起こる可能性が高く、MRP でも参照・変更される。変更されると金銭に直結する。
- 関数が増えすぎると、DB の保守性が下がる。

## 実施の記録
1.  `doc/query/20261115_0001_common_functions.sql`(共通関数 `shared_appellation_save`・`shared_text_save`・`trans_label_save`・`trans_text_save`)と、`20261115_0002_code_unique_indexes.sql`(コードの部分一意索引)を作った(案。未適用)。検証用 DB で、トランザクション内で実行して ROLLBACK し、46 ケースを確認した。実サーバーの PostGraphile で、ミューテーションの「渡した列だけ更新」「null で消える」「論理削除」も確認した。
1.  マスタごとの保存関数(`unit_save`・`stakeholder_save`。適用済み)と、作りかけの 13 本は、方針に合わないため取り下げる。`unit_save`・`stakeholder_save` は、共通関数とミューテーションへの移行後に、DB から外す依頼を出す。
1.  詳細(DB への依頼、マスタごとのミューテーションの作り方、取得元の取り込み手順、未決)は `tools/docker/postgresql/issue/20261115_0001.md`。

## DB に適用するもの(関数・索引の一覧。役割と機能)
適用の順に並べる。SQL は `doc/query/`。検証用 DB で、トランザクション内で実行して ROLLBACK した(補助と共通関数・索引 = 46 ケース、補助の修正 = 同じ値の更新が通ること)。**DB・Docker は、指示があるまで変更しない**(適用はデータベース側の作業)。

### A. 補助の関数(`20261114_0003_appellation_functions_fix.sql`。GraphQL に出さない = `@omit`。共通関数の内部で使う)
| 関数 | 役割 | 機能(入力 → 出力。エラー) |
|---|---|---|
| `ap_staff(p_staff_id)` | 更新者の解決 | 担当者の ID(省略時は JWT の `jwt.claims.staff_id`)→ 担当者の ID と、最新の履歴の ID(`history_info_staff` の `revision` が最大)。担当者がいなければ `APL00` |
| `ap_language(p_code)` | 言語の解決 | 言語コード(大文字小文字を区別しない)→ `shared_language_code_id`。無ければ `APL00` |
| `ap_dictionary_set(辞書 ID, 値(JSON), 更新者)` | 辞書(言語別の値)の保存 | 辞書(`shared_dictionary`)を作る(ID が NULL のとき)。言語別の値(`shared_dictionary_value`)を、先に行を引いて、無ければ追加・有れば更新する(同じ値の更新が一意制約違反にならない)。空文字で値が空になる → 辞書の ID |
| `ap_text_set(文章 ID, 値(JSON), 更新者)` | 文章(`shared_text`)の保存 | 言語別の値に、先頭の文(80 字)と文字数も持たせる。更新は辞書と同じ → 文章の ID |
| `ap_appellation_set(呼称 ID, 名称・読み・略称(JSON), 更新者)` | 呼称の保存 | 呼称(`shared_appellations`)と、名称・読み・略称の辞書を作る・値を入れ替える。名称の ja は、新規で必須、更新でも空にできない(`APL02`)。読み・略称は、値を渡したときだけ辞書を作る → 呼称の ID |

### B. 共通関数(`20261115_0001_common_functions.sql`。GraphQL の mutation に出る。マスタ・Info・trans の呼称・文章・ラベルを持つ列で使う)
| 関数 | 役割 | 機能(入力 → 出力。エラー) | 呼ぶ側 |
|---|---|---|---|
| `shared_appellation_save(p_appellation_id, p_name, p_pronunciation, p_nickname, p_staff_id)` | 呼称(名称・読み・略称)の登録・更新 | 言語別の値(JSON。例 `{"ja": "…"}`)を、渡した言語の値だけ入れ替える。`p_appellation_id` が NULL なら新規 → 呼称の行。返った ID を、本体の create の `names` に渡す。`APL00`(担当者・言語)・`APL01`(呼称がない)・`APL02`(名称の ja が必須・空にできない) | マスタ・Info の `names`(単位・利害関係者・品目・職員・事業所・部署・工程など)、住所の `address1`・`address2`・`building` |
| `shared_text_save(p_text_id, p_values, p_staff_id)` | 文章(詳細など)の登録・更新 | 言語別の値を入れ替え、先頭の文・文字数も持たせる → 文章の行。返った ID を本体の `details` に渡す。`APL00`・`APL01` | マスタの `details` |
| `trans_label_save(p_label_id, p_values, p_staff_id)` | trans のラベル(題名・名称)の登録・更新 | 言語別の値を入れ替える(`trans_label` + `trans_label_value`)→ ラベルの行。返った ID を本体の題名・名称の列に渡す。`APL00`・`APL01` | 苦情・監査・リスクの題名、コンテナ・成績書の名称 |
| `trans_text_save(p_text_id, p_values, p_staff_id)` | trans の文章(詳細)の登録・更新 | 言語別の値を入れ替え、先頭の文・文字数も持たせる(`trans_text` + `trans_text_value`)→ 文章の行。`APL00`・`APL01` | 苦情・監査・リスクの詳細 |

### C. 索引(`20261115_0002_code_unique_indexes.sql`。DDL。マスタごとの関数の検査の代わりに、DB の制約で重複を止める)
| 索引 | 表(条件) | 役割 / 機能 |
|---|---|---|
| `mstr_stakeholder_ix_code_active` | `mstr_stakeholder(code)`(`remove = false`) | 利害関係者のコードの重複を止める |
| `mstr_capability_ix_code_active` | `mstr_capability(code)`(`remove = false`) | 力量のコードの重複を止める |
| `mstr_license_ix_code_active` | `mstr_license(code)`(`remove = false` かつ NULL でない) | 資格のコードの重複を止める |
| `mstr_location_ix_code_active` | `mstr_location(code)`(同上) | 場所のコードの重複を止める |
| `info_staff_ix_code_active` | `info_staff(code)`(同上) | 作業者のコード(画面の「番号」)の重複を止める |
| `info_office_ix_code_active` | `info_office(code)`(`remove = false`) | 事業所のコードの重複を止める |
| `info_department_ix_code_active` | `info_department(code)`(`remove = false`) | 部署のコードの重複を止める |
- 共通の機能: 削除済み(`remove = true`)のコードは再利用できる。関数を通さない登録・同時登録でも重複が `23505`(`duplicate key value violates unique constraint "<索引名>"`)で止まる。クライアントは、索引の名前(`_ix_code_active`)で、画面の検証エラー(重複)に変換する。適用前に、重複が無いことを確認する。名前は `<表>_ix_code_active` にそろえる(足すときも同じ)。

### D. 外すもの(移行後)・作らないもの
- 外す: `unit_save`・`stakeholder_save`(適用済み。マスタごとの保存関数のため、方針に合わない)。共通関数とミューテーションへの移行(`tools/docker/postgresql/issue/20261115_0001.md` の 3)が済んでから、外す依頼を出す。
- 作らない: マスタ・Info・trans ごとの保存関数、更新者を埋めるトリガー(更新者は、ログイン中の担当者を、クライアントが状態から渡す。下の「更新者」)。

## 更新者(`update_user_id`・`update_user_history_id`)
- ログイン中のユーザーの ID を保持している状態管理は、`pbapi` の `SessionService.current`(`AuthSession.appUserId` = アプリの DB の担当者の ID)。アプリが `auditUserProvider`(`pms_app` の `graphql_overrides.dart`)で、`pms_graphql` の `AuditUserResolver`(担当者の ID から、最新の履歴の ID を引いて使い回す)を組み立て、取得元の `auditUser` に渡す。DB のトリガーで埋める方式は採らない(`tools/docker/postgresql/issue/20261115_0001.md` の 0 の 6 は決着)。
- ミューテーション: 生成器に、定義の `withUpdater: true` を足した。付けると、Edit・Remove の引数に更新者(任意)が入る(Create は、列に書けば入る)。営業・購買・生産計画の Edit に付けた。
- 実サーバーで確認: 更新者を渡さない取得元で登録した行は更新者が空、渡す取得元の更新・登録・論理削除で、JWT の担当者と最新の履歴の ID が記録される。
- 残り: 読み取り専用の機能を、ミューテーションに入れ替えるときも、同じ `auditUser` を渡す。
