# 20261027_0001 GraphQLモデル生成を「画面(機能)単位」に分割する

- 作成日: 2026-10-27
- 対象リポジトリ: flutter-pms(pub workspace + melos)
- 種別: 設計変更 / リファクタリング
- 完了条件: 下記タスクがすべて完了し、本Issue末尾の「CLAUDE.md 追記内容」がワークスペースの CLAUDE.md に反映されていること

---

## 1. 背景

- 現状は GraphQL サーバー(PostGraphile)1つからスキーマを取得し、`graphql_provider` という1つのライブラリで build_runner によりモデルを一括生成している。
- 画面単位で責務を分ける、あるいは画面を拡張として扱う場合に、全画面がこの1ライブラリに依存するため、保守性が大きく下がる。
- 本家 `schema.graphql` は 10MB を超えており、Git で共有できない(現在は必要なときに必要な部分だけを取り出して使っている)。
- PostGraphile 側はカスタマイズしない方針(独自プラグインなし)のため、スキーマの縮小はクライアント側で行う必要がある。

## 2. 決定事項

1. **モデルは画面(機能)単位で生成する。** クエリ(`.graphql`)・画面用スキーマ・生成モデルを、機能ごとのモデルパッケージに置く。
2. **モデル生成は既存のジェネレーター(graphql_codegen)を使う。** ジェネレーター本体は自作しない。
3. **自作するのは「スキーマ抜き出しツール」だけ。** 本家スキーマと機能の `.graphql` を入力にして、使っているフィールド・引数・入力型・列挙型・スカラーだけを含む画面用 `schema.graphql` を書き出す。型単位ではなく**フィールド単位**で削る。
4. **抜き出しツールの入力は YAML ではなく `.graphql` にする。** YAML→GraphQL ツール(既存)とは役割を分け、手書きの `.graphql` にも対応できるようにする。
5. **本家スキーマに対する検証は抜き出しツールで行う。** 存在しない列や関連を指定した場合は、この段階でエラーにする。
6. **機能をまたいで受け渡すのは ID や基本型だけにする。** 生成された型(列挙型・入力型を含む)は、そのモデルパッケージと対応する機能の外に出さない。機能ごとに同名の型が生成されるため、このルールは必須とする。
7. **スカラーの変換処理と GraphQL クライアントのラッパーは infra 層で共有する。** スキーマ本体は共有しない。
8. **モデルパッケージは `packages/model_providers/` 配下に置く。** `packages/features/` はすでに画面機能として存在するため使わない。
9. **現行の一括生成ライブラリ `graphql_provider` は、移行完了後に削除する。**

## 3. 処理の流れ

```
packages/model_providers/<機能>_model/
  gql/*.yaml                        ← 人が書く(元データ)
     │ ① YAML → GraphQL ツール(既存: tools/gql_yaml2graphql)
     ▼
  lib/src/graphql/*.graphql         ← クエリ/ミューテーション
     │ ② スキーマ抜き出しツール(新規: tools/gql_schema_pruner)
     │    + .schema/schema.graphql(本家・Git管理外)
     ▼
  lib/src/graphql/schema.graphql    ← 画面用スキーマ(Git管理)
     │ ③ graphql_codegen(build_runner)
     ▼
  lib/src/graphql/*.graphql.dart    ← モデル
```

- 実行時や他のパッケージから使われるときに必要なのは ③ のモデルだけ。
- ただし、本家スキーマがない環境でも単体で再生成できるように、①② の成果物もモデルパッケージ内に残す。

依存の向き:

```
features/<機能>  →  model_providers/<機能>_model  →  infra/pms_graphql
tools/*          (どこからも依存されない。開発時のみ使う)
```

- 原則として、機能パッケージ1つにモデルパッケージ1つを対応させる。
- 機能パッケージは、自分に対応するモデルパッケージ以外のモデルパッケージに依存しない。

## 5. melos スクリプト(ルートの pubspec.yaml)

```yaml
melos:
  scripts:
    gql:schema:
      description: 本家スキーマを .schema/ に取得(DB変更時のみ)
      run: dart run tools/gql_schema_pruner/bin/fetch_schema.dart --endpoint http://localhost:5000/graphql --out .schema/schema.graphql

    gql:yaml:
      description: ① 全モデルパッケージの gql/*.yaml → lib/src/graphql/*.graphql
      run: dart run tools/gql_yaml2graphql/bin/gql_yaml2graphql.dart --root packages/model_providers

    gql:prune:
      description: ② 本家スキーマから画面用 schema.graphql を抜き出す(検証も兼ねる)
      run: dart run tools/gql_schema_pruner/bin/gql_schema_pruner.dart --schema .schema/schema.graphql --root packages/model_providers

    gql:check:
      description: ② の差分チェック(書き出さずに、差分があれば失敗する。CI用)
      run: dart run tools/gql_schema_pruner/bin/gql_schema_pruner.dart --schema .schema/schema.graphql --root packages/model_providers --check

    gql:build:
      description: ③ モデル生成
      exec: dart run build_runner build -d
      packageFilters:
        dirExists: gql

    gql:
      description: ①→②→③ をまとめて実行
      run: melos run gql:yaml && melos run gql:prune && melos run gql:build
```

- pub workspace では package_config がルートで1つにまとまるため、ルートから `dart run tools/.../bin/xxx.dart` を実行すればツールを依存に追加しなくても動く。
- PostGraphile v4 の場合は、起動オプション `--export-schema-graphql .schema/schema.graphql` で本家スキーマを直接書き出せる。この場合 `fetch_schema.dart` は不要。エンドポイントのポートは実際の環境に合わせる。

## 7. Git に入れるもの

| 対象 | Git |
|---|---|
| `gql/*.yaml` | 入れる |
| `lib/src/graphql/*.graphql`(①) | YAMLツールが本家スキーマを参照しているなら入れる |
| `lib/src/graphql/schema.graphql`(②) | **必ず入れる** |
| `*.graphql.dart`(③) | チームの方針次第(入れれば利用側で build_runner が不要) |
| `.schema/schema.graphql` | 入れない(`.gitignore`) |

```markdown
## GraphQL モデル生成ルール

### 方針
- GraphQL のモデルは画面(機能)単位で生成する。全画面のモデルを1つのライブラリで生成しない(旧 graphql_provider は廃止済み)。
- モデルパッケージは `packages/model_providers/<機能>_model/` に置く。`packages/features/` は画面機能であり、モデルは置かない。
- 機能パッケージは、自分に対応するモデルパッケージだけに依存する。
- 機能をまたいで受け渡すのは ID や基本型だけにする。生成された型(列挙型・入力型を含む)を機能の外に出さない。
- スカラーの変換処理と GraphQL クライアントは `packages/infra/pms_graphql` を使う。スキーマ本体は共有しない。
- PostGraphile 側はカスタマイズしない。スキーマの縮小はクライアント側の抜き出しツールで行う。
- モデル生成は graphql_codegen を使う。ジェネレーター本体は自作しない。

### 生成の流れ
1. `gql/*.yaml` を編集する(人が書くのはここだけ)
2. `melos run gql` を実行する
   - ① gql:yaml  … YAML → `lib/src/graphql/*.graphql`
   - ② gql:prune … 本家スキーマ(`.schema/schema.graphql`)から画面用 `lib/src/graphql/schema.graphql` を抜き出す。同時に検証も行う
   - ③ gql:build … build_runner でモデルを生成する
- DB を変更したときは、先に `melos run gql:schema` で本家スキーマを更新してから `melos run gql` を実行する。② で失敗した機能、または schema.graphql に差分が出た機能が影響範囲となる。

### 禁止事項
- `.schema/schema.graphql`(本家、10MB超)を Git に入れない。
- 画面用の `schema.graphql` を手で編集しない(必ず抜き出しツールで再生成する)。
- `*.graphql.dart` を手で編集しない。
- 新しく一括生成用のモデルライブラリを作らない。
```
