# 20261122_0001 承認パターンの台帳(GraphQL 版)と承認の段のドラッグ並べ替え

## 指示
1.  承認パターンの台帳を GraphQL で作る(`organization`。これまでメモリ上のサンプル)。
1.  `tools/open-design` の会社情報の承認パターンの画面のレビュー結果: 承認パターンの編集テーブル(承認の段の表)は、ドラッグ&ドロップで並べ替えられるようにする(ライブラリは `flgtable_lib` を使う)。
1.  テスト通過後、すべてコミット・プッシュする。

## 決定・方針
1.  承認パターン(`mstr_approval_pattern`)の台帳は、実体の画面(`entity_screens`)の実体 `approvalpattern` の取得元(`ApprovalPatternRepository`。`IEntityRepository`)を GraphQL 版にして差し替える。名称・読み・略称は共通関数 `shared_appellation_save`(言語 `ja`)で作り、返った ID を本体の create の `names` に渡す。削除は `remove = true`。
1.  承認の段は、承認パターンの編集の画面(専用の画面)で出す: 段 = 承認パターン明細(`mstr_approval_pattern_detail`)+ 承認(`mstr_approval`: 部署・役職・順位)。表は `flgtable_lib`(`TableConfig.dragEnabled`)で、行をドラッグして順位(`mstr_approval.priority`)を付け替える。ドロップのあとに 1 から振り直し、変わった段だけを更新する。段の追加・削除もこの画面で行う(削除は論理削除)。
1.  承認の順序は DB の順位(`priority`)で、同じ順位は並行(CLAUDE.md「段の順序・通知・一括承認」)。並べ替えの画面は、1 行 = 1 つの順位として振り直す(並行の段は、この画面では 1 段ずつ別の順位になる)。
1.  画面案の「承認できる人」(段ごとの担当者)・「承認の範囲」の段階・配下を含むか は、DB に表・列が無いため作らない(DB を優先)。実体 `approver` は専用の画面に置き換わるため、実体の定義から外す。`approvalscope`・`accesspathapproval` は従来のまま(サンプル)。
1.  書き込みの更新者は、ログイン中の担当者(`AuditUserSource`)。

## 実施結果(2026-11-22)
1.  承認パターンの台帳: `ApprovalPatternRepository`(GraphQL 版)・モデル `approval_pattern.yaml`。承認の段の専用の画面 `ApprovalStepsPage`(`flgtable_lib` の `dragEnabled` で行をドラッグして並べ替え。順位を振り直し、変わった段だけ保存)。実体 `approver` は廃止(生成元 `handwritten.js`・`gen.js` を直し、生成物は該当箇所だけ手で合わせた。`gen.js` の再生成は他の機能の生成物まで差分が出る(生成元とコミット済みの内容がずれている)ため、全体の再生成はしていない)。
1.  テスト: 画面(並べ替え・追加・変更・削除・失敗時の巻き戻し)と GraphQL 版(代役の通信路)は通過。**実サーバーの通信テスト(`approval_pattern_server_test.dart`)は、資格情報の環境変数を渡す実行が自動モードで拒否されたため、未実行**(接続はできるが、資格情報なしでは権限エラー)。資格情報つきで `flutter test test/approval_pattern_server_test.dart` を実行する。

##  品質管理の監査
1.  trans_auditのサロゲートキー集合trans_audit_details(監査実施詳細)は、history_mstr_audit_stdのキー、trans_label(監査名)のキー、trans_audit_teamのキー、予定日時(datetime)、終了予定日時(datetime)実施日時(date)、終了日時(datetime)、監査結論のtrans_textのキーを持つ。
1.  trans_audit_detailsのキーを持つtrans_audit_detail_check_items(監査実施詳細項目)は、history_mstr_audit_std_checkitemのキー、formula_classの式に対する値(JSONB)、所見のtrans_textのキー、所見のtrans_textのキー
1.  trans_complaintのサロゲートキーのtrans_audit_complaintは、trans_audit_detail_check_itemsのキーを持つ

イメージ
1.  trans_audit_details<-trans_audit(文書ベースで監査の計画と実施を記録)
    1.  trans_audit_detail_check_items(計画と実施の文書に紐付く基準と事実)
        1.  trans_audit_complaint(事実に異常・不適合の時の是正処置要求のための異常)
## 品質管理の監査: 評価と実施結果(2026-11-22)
評価: DB に実装できる。構造は適切(監査 = 計画の文書、監査実施詳細 = 計画と実施の行、項目 = 基準(監査標準項目)と事実、異常 = 是正処置要求のつなぎ)。既存の監査(`trans_audit`・`trans_audit_team`・`trans_auditor`・`trans_audit_member`)と、監査標準(`mstr_audit_std`・項目。履歴つき)はそのまま使い、3 表を足した。
1.  `trans_audit_details`(監査実施詳細): `trans_audit_id`(親。指示に無いが必須)・監査標準(履歴 ID + ID の組。R4)・`names`(監査名。`trans_label`)・`trans_audit_team_id`・`scheduled_at`(予定日時)・`expected_end_at`(終了予定日時)・`performed_date`(実施日。date)・`ended_at`(終了日時)・`conclusion`(監査結論。`trans_text`)。チームは、その監査のものだけ(`trans_audit_team` に (チーム, 監査) の一意 `trans_audit_team_ix2` を足し、複合の外部キーで守る)。CHECK: 終了予定 ≥ 予定、終了日時 ≥ 実施日。
1.  `trans_audit_detail_check_items`(監査実施詳細項目): `trans_audit_details_id`・監査標準項目(履歴 ID + ID の組)・`formula_value`(jsonb。式 `formula_class` に対する値)・`findings`(所見。`trans_text`)。項目は、詳細の監査標準に属すものだけ(トリガー `trg_03_audit_check_item_std`。errcode `AUD01`)。同じ詳細に同じ項目は 1 件(部分一意索引 `trans_audit_detail_check_items_ix_active`。削除済みは再登録できる)。
1.  `trans_audit_complaint`(監査の異常): `trans_complaint_id` + `trans_audit_detail_check_items_id`。同じ組は 1 件(`trans_audit_complaint_ix_active`)。1 つの項目に複数の異常、1 つの異常を複数の項目につなげられる。
1.  指示の確認が要る点: 項目の「所見の `trans_text` のキー」が 2 つ書かれていたため、1 つ(`findings`)にした(2 つ目が別の意味(例: 是正の要否の理由)なら、列を足す)。不適合かどうかの boolean 列は、異常とつながっているかで分かるため持たない(R1)。
1.  実装: `tools/database/ER/pms_test.pero`(3 表・関係・トリガー・チームの一意・図「品質(テーブル)」へ配置・部分一意索引は `endQuery`)と `06_cteate_test.sql`(PERO の出力と同じ書式で手で反映)。権限は 09 の `ALL TABLES` への付与で足りる(再構築のあと有効)。
1.  SQL のテスト: `tools/docker/postgresql/test/20261122_0001_audit_details.sql`(A1〜A10)。DDL(`..._ddl.sql`)を同じトランザクションで流し、最後に ROLLBACK する形で、実 DB で全件成功(DB は変更していない)。
