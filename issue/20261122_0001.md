# 20261122_0001 承認パターンの台帳(GraphQL 版)と承認の段のドラッグ並べ替え

## 指示
1.  承認パターンの台帳を GraphQL で作る(`organization`。これまでメモリ上のサンプル)。
1.  `tools/open-design` の会社情報の承認パターンの画面のレビュー結果: 承認パターンの編集テーブル(承認の段の表)は、ドラッグ&ドロップで並べ替えられるようにする(ライブラリは `flgtable_lib` を使う)。
1.  テスト通過後、すべてコミット・プッシュする。

## 決定・方針
1.  承認パターン(`mstr_approval_pattern`)の台帳は、実体の画面(`entity_screens`)の実体 `approvalpattern` の取得元(`ApprovalPatternRepository`。`IEntityRepository`)を GraphQL 版にして差し替える。名称・読み・略称は共通関数 `shared_appellation_save`(言語 `ja`)で作り、返った ID を本体の create の `names` に渡す。削除は `remove = true`。
1.  承認の段は、承認パターンの編集の画面(専用の画面)で出す: 段 = 承認パターン明細(`mstr_approval_pattern_detail`)+ 承認(`mstr_approval`: 部署・役職・順位)。表は `flgtable_lib`(`TableConfig.dragEnabled`)で、行をドラッグして順位(`mstr_approval.priority`)を付け替える。ドロップのあとに 1 から振り直し、変わった段だけを更新する。段の追加・削除もこの画面で行う(削除は論理削除)。
1.  承認の順序は DB の順位(`priority`)で、同じ順位は並行(CLAUDE.md「段の順序・通知・一括承認」)。並べ替えの画面は、1 行 = 1 つの順位として振り直す(並行の段は、この画面では 1 段ずつ別の順位になる)。
1.  画面案の「承認できる人」(段ごとの担当者)・「承認の範囲」の段階・配下を含むか は、DB に表・列が無いため作らない(DB を優先)。実体 `approver` は専用の画面に置き換わるため、実体の定義から外す。`approvalscope`・`accesspathapproval` は従来のまま(サンプル)。
1.  書き込みの更新者は、ログイン中の担当者(`AuditUserSource`)。

## 監査の実施: モデル・画面の方針と、DB への提案(2026-11-22)
追加の指示: (1) 階層は画面案(`tools/open-design`。監査計画の台帳だけで、実施の画面は無い)と異なり、監査 → 監査実施詳細 → 項目 → 異常。(2) 項目(チェック項目)を作る側(監査標準・計画の台帳。従来のまま)と、実際に監査する側の画面を分ける。監査する側は、検索しなくても、自分のチームに割り当てられたものだけが見え、実施中に「項目(コメント)」と「異常」の 2 画面を行き来できる。(3) チームの担当者へ、予定日をもとに通知する。

### モデル(`quality_model/gql/audit_execution.yaml`。生成済み)
`AuditDetailPage`(+`Edit`・`Create`・`Remove`)・`AuditItemPage`(+`Edit`・`Create`・`Remove`。基準の名称・型・式・つないだ異常を含む)・`AuditComplaintLinkPage*`・`AuditTextSavePageCall`・`AuditLabelSavePageCall`。「自分の監査」は `AuditDetailPage` の `$filter`(`transAuditTeamByTransAuditTeamIdAndTransAuditId.transAuditorsByTransAuditTeamId.some.staffId = 自分`)で絞る。基準の名称は、履歴の表に呼称への外部キーが無いため、現行のマスタから読む。

### 提案するビュー(読み取りの判定・文字はビューで 1 か所。R1・R2)
1.  `v_audit_assignment`(1 行 = 監査実施詳細 × チームの監査員): `staff_id`(監査員)・`trans_audit_details_id`・`trans_audit_id`・`trans_audit_team_id`・予定日時・終了予定日時・実施日・終了日時・**状態の boolean**(`is_planned`=未着手・`is_in_progress`=実施日あり・終了日時なし・`is_done`=終了日時あり・`is_overdue`=予定を過ぎて未着手)・`item_count`・`answered_count`(値または所見が入っている項目)・`complaint_count`・状態の文字 `status_label_ja/en`。画面は `staff_id = 自分` で絞るだけ(並びは `is_in_progress` → 予定日)。
1.  `v_audit_item`(1 行 = 監査実施詳細項目): 項目 + 基準(監査標準項目の履歴: 型・式・引数)+ `answered`(boolean)+ `complaint_count`。画面でネストして組み立てない。
1.  `audit_notice(p_days_before integer DEFAULT 3)`(STABLE の関数。PostGraphile では query): 呼び出した人(JWT の `staff_id`)がチームの監査員で、未終了で、予定日が `p_days_before` 日以内(または過ぎた)の監査実施詳細を返す。列は `trans_audit_details_id`・`scheduled_at`・`days_until`・`is_overdue`。**通知は行を作らず、予定日から導く**(予定日を変えれば自動で変わる。重複しない。スケジューラが要らない)。ダッシュボードの通知は、この結果を既存の通知(`trans_announcement`)と並べて出す。
    - 代案(既読・メール送信が要るとき): `trans_announcement` に `trans_audit_details_id` を足し、関数 `audit_notify_due(p_days_before)` が行を作る(冪等。部分一意索引で (担当者, 監査実施詳細, 予定日) の重複を防ぐ)。定期実行は DB 単体ではできない(`pg_cron` が無い)ため、アプリのログイン時、または外部のスケジューラが呼ぶ。まず上の導く方式を推奨する。

### 提案する関数(方針: 複数の表にまたがる・同時実行や是正の起点になるものだけ。1 回の呼び出し = 1 トランザクション)
1.  `audit_detail_prepare(p_audit_details_id)`: 監査標準の項目(その時点の履歴)を、まだ無いものだけ項目として作る(冪等)。複数行の登録のため関数にする。errcode: `AUD00` 担当者 / `AUD02` 対象が無い。
1.  `audit_detail_start(p_audit_details_id)`: 実施の開始。チームの監査員だけ(`AUD03`)。実施日を今日にし(すでにあれば変えない)、項目を用意する(`audit_detail_prepare`)。
1.  `audit_detail_finish(p_audit_details_id, p_conclusion jsonb, p_force boolean DEFAULT false)`: 実施の終了。未入力の項目があれば `AUD04`(`p_force` で押し切れる)。終了日時と結論(`trans_text_save` と同じ言語別の JSON)を入れる。
1.  `audit_complaint_register(p_item_id, p_titles jsonb, p_details jsonb, p_occurred_at timestamp DEFAULT now(), p_staff_id uuid DEFAULT NULL)`: 不適合の項目から、異常(ラベル・文章・`trans_complaint`。報告者 = 担当者。承認パターンがあれば申請になる)を作り、`trans_audit_complaint` でつなぐ。戻り値はつなぎの行。複数の表への登録で、是正処置の起点のため関数にする。
1.  項目の入力(値・所見・コメント)は、関数にせず、ミューテーション(`AuditItemPageEdit`)+ 共通関数(`trans_text_save`)で行う(1 表の更新。マスタ・trans の方針)。書き込める人(チームの監査員だけ)は、行の権限(RLS)の段階で守る(次の段階の判断)。それまでは、画面のアクセス権と、`audit_detail_start`・`audit_complaint_register` の検査で守る。

### 実施の画面(`quality` 機能。この Issue の実装対象)
1.  「自分の監査」(`/quality/my-audits`): 自分のチームに割り当てられた監査実施詳細だけを、検索なしで、実施中 → 予定日の順に並べる。予定日が近い・過ぎたものは印を付ける。開く = 監査の実施の画面。
1.  監査の実施(`/quality/audit-run?id=…`): 下のナビで **「項目」と「異常」の 2 画面**を行き来する(どちらも表示したままの状態を保つ)。項目の画面は、基準の名称・値・所見(コメント)を入力する。異常の画面は、不適合の項目に異常を入力し、つないだ異常の一覧を見る。項目の「異常を入力」から異常の画面へ、異常の画面の「項目へ戻る」から項目の画面へ、その項目を選んだまま移る。
1.  取得元は `IAuditRunGateway`(メモリ上 + GraphQL 版)。ビュー・関数が DB に入るまで、GraphQL 版は、表のモデルで読める分(自分の監査・項目・値と所見の更新)だけを実装し、項目の用意・開始・終了・異常の登録は、関数の導入後に GraphQL 版を実装する(メモリ上の版で画面は動く)。
1.  未実装の前提: 監査の計画(`trans_audit`・チーム・監査員・監査実施詳細)の登録は、まだアプリから行えない(台帳は読み取り専用)。計画の側の登録(監査標準の項目を作る側を含む)は、別の作業。
