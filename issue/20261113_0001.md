#   受注キャンセルの反映と、`features`・`model_providers` のレビュー、残りの Issue のまとめ

`issue/20261111_0002.md`(受注・発注まわりの先構築)の続き。2026-11-13 に、PostGraphile のスキーマを再取得し、`packages/model_providers`・`packages/features` をレビューした結果と、残っている Issue をまとめた。実施の記録は `doc/log/20261113_0001.md`。

実行の前提: PostgreSQL(`192.168.1.101`)と PostGraphile(`192.168.1.100:5000`)・PocketBase(`192.168.1.103:8090`)が稼働していること。サーバーを使うテストは、一般ユーザーの資格情報を渡して実行する(`packages/infra/data_test_harness/CLAUDE.md`)。

## 0. 先に確認すること

### 0-1. 「受注キャンセル」の DB の追加が、見当たらない(要確認)
スキーマの再取得で、受注キャンセルに当たる新しい DB の追加は見つからなかった。確認した範囲は次のとおり。
1. 本家スキーマ: 型 20818 → 20828。差分は**主キー制約名の変更だけ**(`…_pkc` → `…_pk`。ネストした mutation の入力型の名前 `…PkcConnect` → `…PkConnect` など)。受注キャンセルに関する型・列・関数は増えていない。
1. PostgreSQL: 関数・ビュー 582 件が、スクリプト(`06_cteate_test.sql`・`12`・`13`)の定義と一致する。受注まわりは `trans_order_detail.cancel_quantity`・`stop`・`customer_property`、ビュー `v_order_detail_balance`(`cancel_closed`)、`trans_plan_change`・`trans_order_detail_settlement` までで、**受注キャンセルの操作(DB の関数)は無い**。`trans_plan_change` は 0 件。
1. 作業ツリーの DB スクリプトは、未コミットの変更がある(`06_cteate_test.sql` が関数を取り込んで再出力され、`07_visiter_functions.sql`・`08_mrp.sql` が削除されている)。これらの内容は、すでに DB に入っているものと一致する。

→ 確認してほしい: ①「受注キャンセル」とは、すでに反映した `cancel_quantity`・`v_order_detail_balance` のことか。②別のもの(例: キャンセルの操作の関数 `v_cancel_open_item`・`v_plan_change`、受注キャンセルの画面用ビュー)なら、まだ DB に反映されていない(または、スクリプトの未コミットの変更を DB に流す前)。反映後に `melos run gql:schema` から再実行する。

### 0-2. 主キー制約名の変更(`pkc` → `pk`)の影響(確認済み)
1. `melos run gql` は成功。全モデルの `schema.graphql` は、同数の行の置換(`Pkc`→`Pk`)だけが差分で、使っている型・列は変わらない。
1. コード・YAML に `Pkc` の参照は無い。モデル 15 パッケージ・機能 10 パッケージのテスト(サーバーを使うテストを含む)は全て通る。
1. 新しいパッケージ(`supply_model`・`plan_change_model`・`return_model`)の `build_runner` が、古いキャッシュで `Null check operator used on a null value` になった。`packages/model_providers/<パッケージ>/.dart_tool/build` と `build/` を消して、`flutter pub get` のあとに再実行すると通る。新しいモデルパッケージを足したときの手順として、`packages/model_providers/CLAUDE.md` に書く(3章 #8)。

### 2-2. 高: R2(`barcode_entry` の登録の可否に、キャンセル・停止を反映する)
