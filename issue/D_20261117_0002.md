# 20261117_0002 pms_app の評価(pms_app_example)で見つかった点

評価の結果の一覧は `apps/pms_app_example/doc/contents/evaluation.md`。テストは `apps/pms_app_example/test/`(19 件。再現できる)。**Windows の目視は未実施**。以下は、判断・対応が要るもの(優先度の順)。終わっていない作業は、`issue/C_20261117_0003.md` へ移した。

## 1. 高
1.  **許可の無いページを、URL・コマンドで直接開ける(評価 7)**。メニューだけが許可で絞られ、ルーターに許可の確認が無い。一般ユーザーで `/e/item`・管理者専用の `/auth/admin/signups` が開く(画面のデータは、GraphQL・PocketBase 側の権限で守られるが、画面は開く)。
    - 案: `pms_app` の `rootRouter` の `redirect` に、`menuAccessProvider` と同じ判定(`MenuAccess.allows(path)`)を足し、許可の無いパスはエラー(権限なし)の画面へ向ける。管理者専用のパスは、`role = admin` で判定する。メニューと同じ判定を使い、重ねて持たない。判定中(取得前)の扱いと、取得できないとき(`MenuAccess.none`)の表示を決める。

1.  **ログイン後に「戻る」でログイン画面へ戻れる。ログイン済みでもログインのパスが開く(評価 3)**。ログイン後のダッシュボードへの遷移が `push`(`DashboardDestination` は `TopLevelDestination` ではない)で、ログイン画面が積まれたまま残る。
    - 案: ログイン成功のあとは `TopLevelDestination(DashboardDestination())`(積まずに入れ替える)で進める(`auth_files` の `login_page.dart`)。さらに、ログイン済みのときにログイン・登録・再設定のパスを開いたら、ダッシュボードへ向ける(`authRedirect` の逆の判定)。

### 1. 高への対応
1.  案を採択します。ただし、直接URLでの移動のみ`許可の無いパスはエラー(権限なし)の画面へ向ける`として、クリックやリンクで移動するものは、遷移前にブロックし、とどまるようにする。画面にはイメージ`apps\icon\access-denied.svg`を使用してください(pngに変換しても良い)。

1.  案を採択します。

## 2. 中
1.  **入口が無いページ(評価 11)**: 共有ファイル(`/auth/files`)・管理者の画面(`/auth/admin/signups`・`/auth/admin/resets`)は、メニューにも、ユーザーメニューにも、どこにも入口が無い(`auth_files` は `MenuContributor` を実装せず、遷移先を呼ぶ画面も無い)。
    - 案: 共有ファイルをメニュー(例: 「ファイル」)に、管理者の画面を管理者だけのメニューに出す(`MenuContributor`)。必要ない画面なら削除の対象にする。`/profile/display`・`/e/stakeholder` も入口の有無を確認する。
1.  **ログインユーザーの表示(評価 2)**: ログインで `UserSummary(name: ユーザーID)` だけを設定する。氏名(PocketBase の `name`)・役割(`role`)を入れない。枠のユーザー表示は、役割が空になる。`AuthSession` に `name` を足して渡す(`pbapi`)。
1.  **読み込み中の円が部品になっていない(評価 10)**: `CircularProgressIndicator` を 17 のファイルで直接使う。保守で見た目を変えるとき、17 か所を直す。
    - 案: `app_shell`(または `theme_lib`)に「読み込み中の表示」の部品(`LoadingIndicator`。大きさ・文言・全面を覆うかを引数にし、色・太さはテーマから取る)を 1 つ置き、`BusyOverlay`・`BootSplash`・`OverlayIndicator`(pms_app)・各画面をそれに置き換える。`pms_app` の `OverlayIndicator`(Cupertino)と `BootSplash`(Material)の二重も解消する。
1.  **英語の言語ファイルが無い(評価 6)**: 14 機能(`access_control`・`barcode_entry`・`item`・`organization`・`plan_change`・`production_process`・`purchasing`・`quality`・`quality_common`・`quality_document`・`resource`・`sales`・`system`・`work_record`)に `en.i18n.yaml` が無い。英語の環境では日本語のまま。方針(多言語の対象)を決める。
1.  **直書きの日本語(評価 6)**: `grid_extensions` の「もっと読み込む」(`tree_mixin.dart`)を、引数または slang にする。`feature_shared` の `feature_host` の「まだ画面がありません」は example 用(対象外にしてよい)。

### 2. 中への対応
1.  管理者画面(アプリの根幹の設定)は、特定のIDとパスワードから遷移でき、戻るボタンだけを持ち、そのページ以外アクセスできない仕様です。また、共有ファイルは購買の証明書や点検の証明書のレコードに関連付けされています。それらのモデルにファイルIDがない場合は追加し、画面ではダウンロードボタンが機能するようにしてください。つまり、pocketbaseへのファイルアップロードは、常にDBのファイルテーブルとセットになります。

1.  サイドメニューのユーザーはユーザーパネルの中表示で名前と部署、モバイル画面のユーザーパネル小はアイコンのみとなっています。設定画面ではユーザーパネルの大表示になって、名前と部署を表示する仕様でした。案を出した理由をお知らせください。

1.   機能として含まれていると言える、かつ、保守性の観点から良いといえるのであれば案`app_shell`に含めることを採択します。ただ、モバイルアプリでライブラリを使用することを考えると、保守性の観点から別のライブラリ`Loadux_lib`とし、使用するときは`theme_lib`を依存注入してテーマをパッチする方が良いと考えます。両方の視点、第三の視点からも検討した結果をお知らせください。

1.  全て対象です。

1.  採択します。slangを適用してください。「まだ画面~」は対象外として良いです。

### 共有ファイルの調査(`trans_file`。表はファイル名のクリックでダウンロード、編集はアップロード)
結論: **実装できる**。DB だけで完結する方式と、PocketBase と対にする方式の 2 つがあり、どちらの部品も同じ形で足せる。
1.  **残っている部品(使える)**:
    1.  DB: `trans_file`(`trans_file_id`・`binary_data` text・`name`・`media_type`・`symbol`)。参照する表は 16(`trans_certificate`・`trans_complaint_file`・`trans_inspect_imp_file`・`mstr_document`・`mstr_document_content`・`mstr_document_tier`・`mstr_equipment_tag`・`mstr_report`・`info_staff_icon`+各 `history_*`)。
    1.  モデル: `resource_model` の `FilePage`(読み取り)・`FilePageEdit`(登録・更新。`binary_data`・`name`・`media_type`)が、すでにある。
    1.  ファイルの選択・保存: `auth_files` の `IFilePickerGateway`・`IFileSaverGateway`(OS のダイアログ。テストでは差し替え可)。
    1.  PocketBase: `pbapi` の `SharedFileService`(アップロード・ダウンロード・版)。
    1.  行の操作: `entity_screens` の `RowAction`(別の実体の新規登録を開くボタン)。
1.  **足りないもの**:
    1.  `entity_screens` に項目の種類 `FieldKind.file`(表: ファイル名をリンクとして出し、クリックでダウンロード。編集: 選んでアップロード、ファイル名と種類を表示)と、ファイルの出し入れの窓口 `IFileTransfer`(`upload(bytes, name, mediaType) → trans_file_id`・`download(trans_file_id) → bytes・name`)。機能同士は依存しないため、窓口の型は `feature_shared`(または `entity_screens`)に置き、実体はアプリが差し込む。
    1.  各機能(`resource`・`quality`・`quality_document`・`work_record`・`purchasing`・`organization`)の取得元が、`trans_file_id` の項目を持つ。機能は自分のモデルだけに依存するため、`FilePage` のようなファイルのモデルを、各機能のモデルへ足す(YAML を足して `melos run gql`。**本家スキーマの再取得 = DB への接続が要る**)。
    1.  `gen.js` と画面案(`domains.js`)に、ファイルの項目(`kind: file`)の定義。
1.  **方式 A(DB だけ)**: 登録は `trans_file` の行を作り(`binary_data` に Base64 の文字列、`name`・`media_type`)、返った ID を各表の `trans_file_id` に入れる。ダウンロードは `trans_file` を読んで Base64 を戻し、`IFileSaverGateway` で保存。PocketBase は使わない。長所: 1 つの仕組みで、整合が取れる。短所: 大きなファイルは、GraphQL の応答と DB の `text` が重くなる(サイズの上限を決める)。
1.  **方式 B(PocketBase と対)**: ファイルの実体は PocketBase(`app_files`。版つき)に置き、`trans_file` には名前・種類と、PocketBase のファイル ID(`binary_data` を使うか、列を足すか)を入れる。アップロードは PocketBase → `trans_file` の順(失敗時に実体だけが残る可能性。別の後始末が要る)。長所: 大きなファイルに向く・版が残る。短所: 2 つの保存先の整合が要る。
1.  **着手の順(提案)**: (1) `IFileTransfer` と `FieldKind.file` を `entity_screens` に作り、メモリ上の実装で、台帳(クリックでダウンロード)・編集(アップロード)の画面とテスト、(2) `resource` の点検ファイル(`inspectionfile`。いま `f_fname`・`f_ftype`・`f_regdate` を持つ。`FilePage` のモデルがすでにある)で、DB に接続して確認(方式 A)、(3) ほかの表へ広げる。(1) は DB が無くてもできる。
1.  **決定(2026-11-17)**: 実体は PocketBase にだけ置き、DB は ID だけを持つ(方式 B の簡略版)。最初の対象は点検ファイル(下の「共有ファイルの実施」)。

### 共有ファイルの実施(2026-11-17。決定: 実体は PocketBase にだけ置き、DB は ID だけを持つ。最初は点検ファイル)
決定を反映して実装した(方式 B の簡略版)。**ファイルの ID は、DB の `trans_file_id`(UUID)と PocketBase の `appFileId` を同じ値にする**(DB に PocketBase の ID を別に持たない。`trans_file.binary_data` は NOT NULL のため、行を作るときは空文字を入れる)。
1.  **実施(DB が無くてもできる範囲。テスト済み)**:
    1.  `entity_screens`: `FieldKind.file`・`EntityFile`(値の JSON)・`IEntityFileTransfer`(出し入れの窓口)。台帳はファイル名のリンク(押すとダウンロード。失敗は通知)、編集はアップロード(差し替え)。`EntityScope.fileTransfer`。
    1.  `feature_shared`: `entityFileTransferProvider`(既定は未提供 = 使うと失敗の通知)。`pms_app`: `PocketBaseEntityFileTransfer`(`pbapi` の `SharedFileService`・`auth_files` のファイル選択/保存の窓口・UUID)。
    1.  ファイルの項目を持たせた実体(サンプルの取得元で動作): `resource` の点検ファイル(`inspectionfile`。ファイル名・種類の 2 項目をファイル 1 項目に置き換え)、`quality` の異常報告ファイル(`compfile`)、`work_record` の成績書(`certificate`)、`quality_document` の文書階層(`doctier`)・文書(`doc`)・文書コンテンツ(`doccontent`)・レポート(`report`)。生成元(`tools/entity_gen/gen.js` の `FIELD_ADDITIONS`・`KIND`、`tools/open-design/domains.base.js`)にも反映した(Node が無いため、生成物は手で合わせた。次に `node tools/entity_gen/gen.js` を流すとき、差が出ないかを確認する)。
    1.  テスト: `entity_screens/test/file_field_test.dart`(6 件)、`pms_app_example`(仮想の PocketBase に上がる・ID は UUID・名前を押すとダウンロード・接続断で項目にエラー)。
