**実行の前提**: `postgresql` と `PostGraphile` の再構築が完了した別の環境で実行する。この Issue は「再構築前にできること」と「再構築後にしかできないこと」を分けて、実行順に並べてある。

## 0. 先に確認すること(再構築の完了条件)

## 2. 追加が必要な項目(パッケージごと)

### 2-1. `production_plan_model` / `production_plan`

調べた箇所: `gql/mrp.yaml`(`MrpSuggestionPage`・`MrpPendingSuggestionPage`・`MrpPeggingPage` ほか)、`gql/plan.yaml`、`features/production_plan/lib/src/mrp/mrp_models.dart`。

1.  **`SUPPLY_REQUEST` の扱い(影響度 高・破壊的)**
    1.  `MrpSuggestionKind` は文字列のコードの enum(16種類)で、`ofCode` は未知のコードで `null` を返す。`SUPPLY_REQUEST` が来ると、その行が消える・表示されないおそれがある。
    1.  対策: ① enum に追加する(最小の対応)。② 表示・判断の分岐は、コードではなく DB のビューの boolean(例: 要判断かどうか。`trans_mrp_suggestion` の「要判断」の列。`SUPPLY_REQUEST` は要判断で登録されている)で行う。0-3 の1に沿って、提案の種類のコードで分岐する今の作りは、別の Issue で boolean への置き換えを検討する(今回は `SUPPLY_REQUEST` の追加だけを必須とする)。
    1.  `MrpPendingSuggestionPage`(`v_mrp_pending_suggestion`)の絞り込みの対応表(`*_filter_spec.dart`)に、種類の絞り込みの選択肢があるため、`SUPPLY_REQUEST` を足す。
1.  **供給区分 6(顧客の支給予定)**: `MrpPeggingPage` は `supply_kind` を読む(`mrp.yaml` 330行目)。区分 6 のとき `trans_supply_detail_id` を読み、支給明細へ遷移できるようにする。`trans_mrp_pegging.trans_supply_detail_id` を YAML に追加する。
1.  **取消の意味(影響度 高)**: 確定後の「発注の取消」は数量を書き換えなくなり、`cancel_quantity` と計画変更が残る。生産の取消は、着手済みは `discontinue`、未着手は削除(`remove`)。`MrpOperationsPlanFields`・`MrpPurchaseDetailFields`(参照用の読み込み)に `cancel_quantity`・`stop`・`discontinue` を足す。「提案前」と「確定後」の数量の見え方が違うため、確定後の表示は残(ビュー)を使う。
1.  **生産計画(`OperationsPlanPage`)**: `stop`・`discontinue` の列を足す。停止・打ち切りの操作は計画変更の登録を伴うため、DB の関数(`change_request.md` 7章 #2)ができるまで画面の操作は作らず、表示だけを先に作る。
1.  **計画変更の履歴・未反映の一覧**: `trans_plan_change` と `v_plan_change_unreflected` の読み込みを新しいモデル(2-6)で持ち、MRP の画面から「この MRP で反映された計画変更」を引く(`reflected_trans_mrp_run_id`)。
1.  `MrpRunPage` に、確定時に反映した計画変更の件数を出す(任意)。

### 2-2. `sales_model` / `sales`

調べた箇所: `gql/order.yaml`(`OrderDetailPage`・`OrderDetailPageEdit`)、`gql/shipping_order.yaml`、`gql/sales_record.yaml`、`gql/shipping_order_status.yaml`。

1.  `OrderDetailPage` の読み込みに `cancel_quantity`・`stop`・`customer_property` を足す。`OrderDetailPageEdit`(書き込み)にも足す。ただしキャンセル・停止・納期変更は計画変更の登録を伴うため、**画面の編集項目にはせず**、操作として別に作る(DB の関数ができるまで読み取り専用の表示)。
1.  残の表示は `v_order_detail_balance`(`open_quantity`・`cancel_closed`・精算額の合計)を読む新しい読み込み `OrderDetailBalancePage` を作る。今の受注明細の画面は数量・納期だけを出しており、残を自前で計算してはいない(調べた範囲では計算は見つからない)。したがって**既存の画面の置き換えは小さい**が、「残」を出す画面を足すときはビューの列を使う。
1.  `customer_property`(顧客所有)は boolean の表示。コード値では判定しない。
1.  **受注金額・売上(影響度 低・今は変更なし)**: `v_sales_record`・`v_shipping_order_status` に精算額が入るのは DB 側の未対応(7章 #5)。DB 側ができるまで、`sales_model` の YAML は変えない。できたら、列を足して `melos run gql` を実行する。
1.  新規の読み込み: `trans_order_detail_settlement`(精算の一覧・登録。精算区分 `delivery` の boolean で表示を分ける)、`mstr_settlement_kind`。
1.  受注から支給予定を登録する操作(`trans_supply`・`trans_supply_detail` の create)は、2-5 のモデルを使う。`sales` は `xxx_api.dart` の契約か ID だけで支給の画面へ遷移し、生成された型を機能の外へ出さない。

### 2-3. `purchasing_model` / `purchasing`

調べた箇所: `gql/purchase.yaml`(`PurchaseDetailPage`・`PurchaseDetailPageEdit`・`PurchaseRecPage`・`PurchaseRec*` の create)、`features/purchasing/lib/src/entities/purchasing_definitions.dart` と `ja.i18n.yaml`(`f_material_supply`・`f_paid_supply`)。

1.  `PurchaseDetailPage` に `cancel_quantity`・`stop` を足す。残は `v_purchase_detail_balance`(`cancel_closed` を含む)の読み込み `PurchaseDetailBalancePage` を新しく作る。
1.  **外注発注明細の `material_supply`・`paid_supply`** は「発注したときの支給の条件」として残るため、**削除せず、ラベルを「発注時の支給条件」へ直す**(`f_material_supply`・`f_paid_supply`)。実際の受け渡し・切り替えは支給(2-5)で見るため、発注明細の画面から支給へ遷移できるようにする(発注明細ID で絞る)。
1.  **0円発注で顧客支給を扱っている箇所**: 調べた範囲(`purchasing_definitions.dart`・`purchasing_seeds.dart`・`purchasing_model/gql/*.yaml`・`barcode_entry`)では、**0円発注を顧客支給として扱うコードは見つからなかった**。画面が持つ前提・文言(`f_paid_supply` ほか)の見直しだけでよい。ただし、**既存のデータ**(0円で発注されたもの)があれば、DB 側のデータの移行が要る(支給へ移す)。移行の要否は利用者が確認する。
1.  発注数量を書き換えてキャンセルしている箇所は、**画面側には見つからなかった**(書き換えは MRP の確定 = DB 関数側にあり、08 で `cancel_quantity` に変更済み)。ただし `PurchaseDetailPageEdit` は `quantity` を編集できるため、キャンセルの目的で数量を減らす使い方が残る。**対策**: 画面の数量の項目の補助文に「キャンセルは `cancel_quantity`(操作)で行う」を足す。数量の変更は計画変更(`old_quantity`→`new_quantity`)を伴うため、操作として別にする(DB の関数待ち)。
1.  返品(仕入先・外注先への返品。`receive = false`)の登録は、2-6 の返品のモデルを使う。バーコード実績登録(`PurchaseRec*` の create)は変更しない。

1.  `v_mrp_visiter_item`・`v_visiter_item`・`v_visiter_origin_check` は品目の経路が変わる(支給ビジター・返品ビジターの経由)。**列の追加がなければ YAML の変更は不要**。再生成して差分を確認し、`schema.graphql` に差分が出たら列を足す。

### 2-5. 支給(新規)

新しいモデルパッケージ `supply_model` と、機能パッケージ `supply` を提案する(下の3章の判断 #1)。

1.  読み込み: `trans_supply`・`trans_supply_detail`・`trans_supply_visiter`・`v_supply_detail_balance`・`trans_complaint_supply`。
1.  登録・更新: 支給(場面ごとの値は `change_request.md` の 2-4)、支給明細(予定)、支給ビジターのつなぎ、支給異常。
1.  **場面ごとの組み合わせ(receive・counterpart_owns・company_owns)を、アプリの定数にしない**。両方 true の不可は DB の制約(12)で保たれているため、画面は場面の選択から boolean の組を作る。表示は `v_supply_detail_balance` の `paid_supply`・`paid_by_switch` の boolean で決める。
1.  顧客支給の受け入れ(仮止め → 検品 → 解除)は `visiter_move`・`visiter_issue` の関数(`work_record_model`)と、棚ビジター・支給ビジターの作成を1つの操作にまとめる必要がある。DB の関数(`change_request.md` 7章 #2)ができるまで、画面からの一括登録は作らない(分けて呼ぶと途中で失敗したときに不整合になる)。

### 2-6. 計画変更・返品・精算(新規)

1.  `plan_change_model`(提案)に `trans_plan_change`・`mstr_change_reason`・`v_plan_change_unreflected`・`v_plan_change`(DB 側で作成後)を置く。画面は「計画変更の履歴」(対象ごと・起点ごと)と「MRP 未反映の一覧」。

1.  **登録は DB の関数ができてから**。計画変更は「起点の変更(例: 受注の `cancel_quantity`)と処置を1つのトランザクションで書く」ことが前提で、画面から別々のミューテーションで書くと、起点だけが書かれて計画変更が欠ける。

## 4. 実行の順(再構築の完了後)

先に、**生成が通ること**を確かめてから、**既存の意味の変更**を直し、**新しい画面**は最後にする。

1.  0章の確認(特に 0-2 の `@omit`、0-4 の `gql:schema`)。
1.  `melos run gql`(① → ② → ③)。② で失敗した機能と、`schema.graphql` に差分が出た機能を、影響範囲として記録する(`doc/log` へ)。
1.  `melos run analyze` と `melos run test` を実行し、通ることを確認する(この時点では既存の機能は変わっていないはず)。
1.  **破壊的なもの(高)を先に直す**: 2-1 の `SUPPLY_REQUEST` と取消の意味 → 2-3・2-2 の残・数量の表示 → 2-4 の在庫。それぞれにテストを足す(未知のコードを渡して行が消えないこと、`cancel_quantity` を持つ行の表示)。
1.  足すだけのもの(中): 各モデルの列の追加(2-1〜2-3)、`trans_visiter_owner` の読み取り専用モデル(2-4)、異常の対象(2-7)。
1.  新規のモデルとサーバーの読み取りテスト: `supply_model`・`plan_change_model`・`return_model`(`test/server_read_test.dart` の形式で既存と同じ)。
1.  画面(読み取り中心): 社外の所有物、計画変更の履歴・未反映、支給の予定と残、MRP の `SUPPLY_REQUEST`。
1.  **登録・操作の画面は、DB の関数(`change_request.md` 7章 #2)ができてから**(アクセス権は決定済み)。この Issue の対象外とし、決まったら別の Issue にする。
1.  各画面の画面仕様を `screen_spec_<画面名>.md` として、対応する機能パッケージの `doc/contents` に追加する(`change_request.md` 6章の(C))。
1.  終了後、実施した結果を `doc/log` に、完了した各パッケージの `issue` に `D_`(一部だけなら `C_`)を付ける。

## 5. 受け入れ基準(`change_request.md` 6章)

1.  状態・区分をコード値で判定していない(新しく追加するコードでは enum を作らない)。
