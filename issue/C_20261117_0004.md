# 20261117_0004 共有ファイルの保存の流れ(F 案: 先に PocketBase へ上げ、DB は 1 トランザクション)

## 決定(F 案。利用者の採択)
1.  先にファイルのバイナリを PocketBase へ上げる(`app_file_id` は窓口が作った UUID)。PocketBase へのアクセスは 1 回(アップロードだけ)。
1.  その UUID を `trans_file_id` にして、DB へ `trans_file` の行と、それを持つ行(つなぎ・アイコン・タグ・点検ファイル)を **1 回の入れ子の登録(1 トランザクション)**で登録する。DB は全部成功か全部ロールバックで、DB に参照されない行が残らない。
1.  DB の変更: `trans_file` のトリガー(`trg_01_updatetimes_trans_file`)だけ、INSERT で渡された主キーをそのまま使う(ほかの全表は、DB が採番して渡された値を無視する)。PERO のデータ・`06_cteate_test.sql` に反映済み。**既存の DB には、`06` のこの関数(`CREATE OR REPLACE FUNCTION tests.trg_01_updatetimes_trans_file`)を流す**(テスト環境には適用済み)。
1.  入れ子の向き: 子から親へ作る入れ子(`transFileToTransFileId: {create: …}`)の入力には主キーが無い(採番される)ため、親(`trans_file`)から子へ作る向き(`<子の型>sUsingTransFileId: {create: […]}`)にした。`pms_graphql` の `SharedFileLink` が文を組み立てる(生成器が入れ子の登録に対応していないため)。
1.  失敗したとき: PocketBase へ上げるのに失敗 → DB に何もしない。DB の登録に失敗 → ロールバックされ、PocketBase に参照されないファイルだけが残る(利用者の権限では削除できない。`app_file_id` で DB と突き合わせて、管理者が掃除する)。

## 調査: ロールバックで解決できるか(「トランザクション開始 → ID 取得 → アップロード → 失敗 → ロールバック」)
結論: **この構成では、その流れは再現できない**(DB と PocketBase が別のシステムで、アプリは HTTP でしか触れないため)。確認した事実:
1.  PostGraphile v4 は、1 回の HTTP 要求(= 1 つの GraphQL ドキュメント)を 1 つのトランザクションにする。要求をまたいで開いたままにはできない(「ID 取得」と「アップロードの結果」は別の要求になり、間でトランザクションは終わっている)。同じ要求の中の入れ子の登録は 1 トランザクション(実測済み)だが、その中で PocketBase へ上げることはできない。
1.  DB 側から PocketBase を呼べば、1 つのトランザクションにできる(アップロードが失敗したら、関数が例外を投げて自動でロールバック)。しかし、テスト環境の PostgreSQL 15(標準イメージ)には、HTTP を呼ぶ拡張(`http`・`pg_net`)も、手続き言語(`plpython3u` など)も入っていない(入っているのは `plpgsql`・`pgcrypto` だけ。`dblink`・`postgres_fdw`・`file_fdw` は入れられるが、HTTP は呼べない)。入れるにはイメージの作り直しが要る。さらに、バイナリを GraphQL → DB 経由で渡すことになり(`binary_data` に base64)、アップロード中ずっと DB のトランザクションと接続を持つ(大きなファイルで長くなる)。方針(バイナリは PocketBase にだけ置く)にも合わない。
1.  2 相コミット(`PREPARE TRANSACTION`)は、`max_prepared_transactions = 0`(無効)で、PostGraphile からも使えない。PocketBase 側も参加できない。

### 代案(強さの順)
| 案 | 内容 | 残るもの | 費用 |
|---|---|---|---|
| 現状(補償) | 失敗を捕まえて `trans_file` を論理削除 | 強制終了などで捕まえられないとき、DB に参照されない行 | 実装済み |
| A | 参照されない `trans_file` を後から掃除(DB の関数 1 本) | 上と同じ(一定時間後に消える) | 小 |
| E | PocketBase にサーバー側の経路(フックの自前の API)を置き、PocketBase が PostGraphile を呼んで行を作り、失敗したら同じ経路の中で取り消す。クライアントが途中で止まっても、サーバーが最後まで行う | サーバーの停止のときだけ | 中(PocketBase のフック・JWT の受け渡し) |
| F | 順序を入れ替える: 先に PocketBase へ上げ(`app_file_id` はクライアントが作った UUID)、そのあと DB へ `trans_file` + つなぎを 1 回の入れ子の登録(1 トランザクション)で登録する。DB は全部成功か全部ロールバック | PocketBase に参照されないファイル(DB には何も残らない。`app_file_id` で突き合わせて掃除できる) | 中(`trans_file` のトリガーが渡された主キーを使う必要がある=全表の方針の例外。または `app_files` に DB の ID を後から結びつける列を足す) |
推奨: 当面は現状 + A。DB に孤児を残したくないなら F(PocketBase の孤児は、DB の行が無いので無害で、増えても参照されない)。E は、強制終了への耐性が要るときの選択。F は、利用者の指定(「trans_file を先に INSERT」)と順序が変わるため、採択の判断を求める。
