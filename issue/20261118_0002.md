# 20261118_0002 「会社情報」のレビュー(`tools/open-design` の画面案と `pms_app_example` の比較)

依頼: `issue/app_checks.csv`(利用者の確認)の重複を整理するため、まず「会社情報」(会社情報・事業所・部署・承認パターン)を、画面案に合わせる。全体の評価は、このあとに続ける。
方法: 画面案(`tools/open-design/index.html`)を Edge のヘッドレスで、`pms_app_example` の実際の画面を `test/_shots_test.dart`(実物の `pms_app` を、仮想のサーバーで動かし、画像にする)で、同じ大きさ(1400 × 1100)の画像にして比べた。画像は `apps/pms_app_example/doc/contents/review_company/`(`design_*.png` = 画面案、`flutter_*.png` = 実物)。画像の右上の赤い斜めの帯は、デバッグ表示(確認の道具の都合。指摘ではない)。**Windows の実機の見た目は未確認**(画像は、テストの描画で、字形は NotoSansJP)。

## 1. 結論
画面案と実物は、**部品の見た目の違いではなく、情報の設計(画面の構成)が違う**。実物は、DB の表をそのまま並べた台帳(表 + 編集の入力欄)で、画面案は「会社情報」を 1 つの入口(概要の画面)にして、そこから各画面へたどる構成になっている。見た目の手直しでは、揃わない。次の 5 つの原因に分けると、`app_checks.csv` の重複(同じ指摘の繰り返し)は、すべて収まる。

## 2. 画面ごとの差(画像で確認)
### 2-1. 会社情報(`design_company.png` / `flutter_company.png`)
- 画面案: 会社の概要(会社名を大きく・読み・略称・代表者名(役職つき)・ホームページ(リンク)・本社所在地)+「編集」、サマリ(従業員数の内訳バー(社員・パート・派遣)・外部委託業者数・顧客数)、事業所のタイル(種別のチップ・所在地・在籍人数・「詳細」)、部署の構成、提供サービス・製品。
- 実物: 会社 1 件の行の表。列は、会社名・読み・略称・代表者名・ホームページ・国・郵便番号…(横にはみ出す)。概要・サマリ・タイル・部署の構成・提供は無い。「提供」「役職」の台帳は、別の入口。
- 差: 構成そのものが違う(R1)。サマリの元データ(従業員数の内訳・外部委託業者数・顧客数)は、実物の取得元にまだ無い(従業員数の件数は、ダッシュボードの `StaffCountMetricSource` にある)。

### 2-2. 会社情報の編集(`design_company_edit.png` / `flutter_company_edit.png`)
- 画面案: 項目は、会社名*・読み・略称・代表者名*・代表者の役職*(アプリ独自)・ホームページ・メインサイト(本社)所在地*(1 つの複数行)・備考。下に「提供の一覧」「役職の一覧」を同じ画面に置く。
- 実物: DB の列そのまま(国・郵便番号・住所 1・住所 2・建物・電話番号・FAX を別々の欄)で、必須の項目(会社名・代表者名)以外が多い。提供・役職・割当は別の台帳(入口が別)で、同じ画面に無い。
- 差: R4。項目の組み(DB の列 vs 画面案の項目)と、子の一覧の置き場所(同じ画面 vs 別の入口)が違う。

### 2-3. 事業所(`design_sites.png`・`design_sites_edit.png` / `flutter_site.png`・`flutter_site_edit.png`)
- 画面案: 一覧は、検索の枠(事業所コード・名称・読み・所在地を検索、種別のチップ、表示する列)+ 表(事業所コード・名称(太字・固定)・読み・種別(チップ)・所在地(1 つ)・在籍人数)。編集は、閲覧の表のまま「編集」を押して、名称のリンクと「事業所を追加」が出る(閲覧と編集の 2 つのモード)。
- 実物: 表だけ(コード・名称・読み・略称・国・郵便番号・住所 1 …。横にはみ出す)。「+」で新規、行で編集の別の画面。種別・在籍人数・更新者・更新日の列は無い(種別は DB に無く、画面案は「アプリ独自」)。
- 差: R3・R4。画面案の「種別」「在籍人数」は、DB に列が無い(種別 = アプリ独自、在籍人数 = 集計)。実現には、DB(列またはビュー)か、画面の独自の定義が要る。

### 2-4. 部署(`design_departments.png`・`design_departments_edit.png` / `flutter_department.png`・`flutter_department_edit.png`)
- 画面案: ツリーの枠に、行ごとに「コード 名称」・部署区分のタグ(複数)・「配下 N」のチップ。開閉は小さな山形で、行の左。編集モードで、ドラッグのハンドル・「親を変更」のボタン・最上位へのドロップ領域。
- 実物: 表の中のツリー(列は組織コード・名称・読み・略称・事業所)。先頭列の開閉の三角が文字より大きく、▷(子無し)と ▶(子有り)の差が分かりにくい(csv の指摘)。部署区分のタグ・配下の件数は無い。編集の画面は、入力欄 + 下に「割当」「承認できる人」の表(空のとき、大きな空白)。
- 差: R5・R4。ツリーの行の作りが違う。部署区分(`departmentkind`)は DB にあるが、タグとして出していない。

### 2-5. 承認パターン(`design_approval.png` / `flutter_approval.png`・`flutter_approval_edit.png`)
- 画面案: 一覧は、検索の枠 + 表(パターン名称・読み・備考・承認の範囲(件数)・承認できる人(件数))。**3 階層**: 承認パターン → **承認の範囲**(段階 1〜9・承認する役職・対象の組織・配下を含むか)→ 承認できる人。
- 実物: 一覧は表だけ(3 列)。編集は、パターンの入力欄 + 「承認できる人」の表。**「承認の範囲」の階層が無い**(`approvalpattern` と `approver` の 2 つの実体だけ。DB と GraphQL のモデル `ApprovalScopePage` には、範囲がある)。
- 差: R3・R4 に加えて、**機能の欠け**(承認の範囲の画面が無い)。

### 2-6. サイドメニュー・タイトルバー(`flutter_*.png` の左・上)
- メニュー: 項目にアイコンが無い(csv の指摘)。グループは、開閉の山形だけ。並びは、画面案の「ダッシュボード → 資源 → システム → 品目 → 工程 → 営業 → 出荷 → 購買 → 生産計画 → … → 会社情報」と違い、「会社情報 → 品目 → 購買 → 資源 → 営業 …」。選択中の項目の強調が無い。
- 画面案には、メニューの上部にロゴと担当者の枠(顔写真・名前・所属)がある。実物は、タイトルバーの右に顔写真と「管理者」だけ。
- タイトルバーの担当者のメニュー(位置・ログアウト・設定・自分のイメージが動かない)は、csv の 1〜4 行目。会社情報の範囲ではなく、**枠(`app_shell`)の不具合**として、別に扱う(下の 4 章)。

## 4. 進め方の提案と、判断してほしいこと
**提案(推奨の順)**: 共通の部品から直す(R2 → R3 → R4 → R5)。画面案に合わせた部品を `entity_screens` に作ると、会社情報だけでなく、**ほかの 13 機能の台帳・編集にも効く**(全体の評価で、同じ指摘が繰り返されるのを防ぐ)。そのあと、R1(会社情報の入口の画面)を、独自の画面として作る。
1.  **R2(枠)**: 画面の見出し(パンくず・見出し・「時点」・戻るのボタン)を、`app_shell` の `ScreenScaffold` に足す。
1.  **R3(台帳)**: 台帳を「検索の枠(検索窓・チップ・表示する列)+ 一覧の枠」に変える。チップは、定義(`FieldKind.choice`・真偽)から作る。
1.  **R4(編集)**: 編集を「幅を絞ったカード・項目名が上・必須のチップ・保存の行が最後」に変え、子の一覧を同じ画面の枠に収める。
1.  **R5(ツリー・メニュー)**: ツリーの行に「コード 名称」・区分のタグ・配下の件数。開閉を小さな山形に。メニューにアイコン・並び・選択中の強調。
1.  **R1(入口)**: 会社情報の概要の画面を、新しく作る(サマリの元データが要る)。
1.  **機能の欠け**: 承認の範囲の画面(実体 `approvalscope`)を足す(モデルはある)。
**判断してほしいこと**:
1.  **J1(R1)**: 会社情報を、画面案のとおり**「1 つの入口 → 概要の画面」にする**でよいか(メニューのグループ「会社情報」(台帳が並ぶ)をやめる)。事業所・部署・承認は、概要から開く。**推奨: 画面案のとおり**。
1.  **J2(R3〜R5)**: 部品の作り直しを、**`entity_screens` の共通の部品として行い、全機能に効かせる**か、会社情報だけに限るか。**推奨: 共通(全機能)**。ただし、全機能の見た目が一度に変わるため、画面案が無い機能(画面案と同じ形の台帳・編集が無い機能)との整合を、評価で確認する必要がある。
1.  **J3(閲覧と編集のモード)**: 画面案は、事業所・部署・承認で、閲覧のまま「編集」を押して編集のモードになる(2 つのモード)。実物は、台帳 + 行で編集の別の画面。**画面案の 2 つのモードに揃える**か、実物の流れを残すか。**推奨: 画面案(誤操作を防げる。行ごとの操作をやめた方針と同じ)**。
1.  **J4(項目)**: 画面案は、所在地を 1 つの複数行にまとめ、DB に無い項目(代表者の役職・種別・在籍人数)を「アプリ独自」として持つ。実物は DB の列(国・郵便番号・住所 1・2・建物・電話・FAX)。**DB の列に合わせて画面案を直す**か、画面案に合わせて**実物の表示を組み立て直す**(所在地は列を連結して表示、種別・在籍人数は DB に依頼)か。**推奨: 表示は画面案(連結して出す)、入力は DB の列**(分けて入れる。住所の連結は画面側)。種別・在籍人数・代表者の役職は、DB への依頼(列・ビュー)の判断が要る。
1.  **J5(承認の範囲)**: 承認の範囲の画面を足してよいか(実体の追加。モデルは有る)。
1.  **枠の不具合(csv 1〜4)**: 会社情報の対応のあと、`app_shell` の担当者のメニューを、別に調査する(動かない原因は、まだ調べていない)。
